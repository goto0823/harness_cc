# spec — 対話で仕様を固めて書き出す

このスキルの仕事は **spec を書いて承認をもらうところまで**。plan も実装もしない。
spec は「これを満たせば完了」の合意であり、合意は人が確認して初めて成立する。
同じターンで実装に進むと、その確認が飛ぶ。

## 人が応答できない環境では使わない
`claude -p` などのヘッドレス実行やスケジュール実行では、このスキルは成立しない。往復が本体だから。
それでも呼ばれた、または途中で相手が返答できないと分かったときは、推測で埋めて確定にしない。
前提一覧と未決事項を出力し、「spec を固めるには回答が必要」とブロッカーとして止まる。

## 人に聞くとき
人が決めること・確かめること（未決事項、承認、「止まって聞く」もの）は、出力の文章に書くだけにしない。**AskUserQuestion で聞き、答えが返るまで次に進まない**。文章だけだと読み飛ばされ、そのまま進んでから戻ることになる。
- 1 回に 4 問まで。選択肢は 2〜4 個で、推奨があれば先頭に「（推奨）」を付けて置く。答えで次の質問が変わるなら分けて聞く
- コード・設計書・spec・plan で分かることは聞かない
- stash・破棄・force・push など、取り返しのつかない操作やこのスキルで禁じた操作を選択肢にしない
- 答えは spec の決定ログ（未決が残るなら「未決事項」）に書いてコミットする。`/clear` しても残り、次のスキルが読める
- ヘッドレス（`claude -p`）では聞けない。今までどおり出力に書いて止まる
- 「次は〜」（次に呼ぶスキルの案内）は質問にしない。別の会話で動かすものなので、出力の最後の 1 行に置く

## オーケストレーターから呼ばれたとき
プロンプトが「orchestrate から:」で始まるときは、`/orchestrate` のサブエージェントとして動いている。人とは直接話せない。
- AskUserQuestion は使わない。「人に聞くとき」で聞くことになっているものは、問いと選択肢を決めて、出力の最後に次の形で返して止まる（書く先は、答えを書くファイルと節）:

      ## 質問
      下書き: <このスキルが書いている（答えを書く）ファイル。例 docs/spec/<タスク名>-spec.md>
      ### 前提
      | # | 内容 | 根拠 |
      |---|---|---|
      | 1 | <読んで分かったこと> | <file:line／設計書の節／集計（何を、いつのデータで）> |
      ### 対象外にしたもの
      - <内容>（<根拠>）
      - Q1: <問い>（前提 #1〜#3）／ 選択肢: <A（推奨）>｜<B>｜<C> ／ 書く先: <ファイルと節>

- 人はこのスキルが読んだファイルを読んでいない。オーケストレーターは「## 質問」を見せるだけで、中身を補わない。人がこれだけで答えられるように書く:
  - 前提の表には、問いと選択肢の材料にした事実を 1 行に 1 つ並べる。内容は、そのファイルを読んでいない人に分かる文で書く（クラス名やメソッド名だけで済ませない）。根拠は空にしない
  - 問いは、それだけ読んで分かる文にし、使った前提の番号を添える
  - 調べたうえで対象外にしたものは「対象外にしたもの」に理由と根拠を書く。無ければ見出しごと省く。前提の要らない質問（承認だけなど）なら表も省く
- プロンプトに「## 人の答え」があれば、それを AskUserQuestion の答えとして扱う。書く先に書いてコミットしてから続ける
- 「次は〜」の行は今までどおり出力の最後に書く（オーケストレーターがそれを読んで次を決める。「## 質問」を返すときは、その下に置く）
- 入口・止まる条件・コミットの決まりは変えない。この会話はオーケストレーターとは別の会話なので、「この会話で build を回していない」などの入口はそのまま見る
- 次の会話は前の会話を覚えていない。前提の確認（2）や判断の質問（3）を返すときは、先に読んで分かったこと・前提一覧・質問を spec の下書き（`status: draft`。前提は「前提」、質問は「未決事項」）に書いて docs でコミットしてから返す。次の会話はその下書きと「## 人の答え」から続ける（答えは決定ログに書き、未決事項から消す）

## 進め方

### 既にある spec を呼ばれたとき（0 より先に見る）
`docs/spec/<タスク名>-spec.md` が既にあれば、新しく書かない。
- `draft` なら続きから。未決事項と決定ログを読んで、4〜6 に戻る
- `approved` なら、まず `docs/plan/<タスク名>-todo.md` の「spec への差し戻し」を読む（todo が無ければ差し戻しは無い）
  - `[ ]` の行があれば、それが今回直すこと。S-n ごとに内容と発覚した P-n を見せ、7 に入る
  - 無ければ「approved です」で終えない。「何を変えますか」と聞いて 7 に入る。変えることが無いと言われたら、何も触らずに終える
  - どちらの場合も、`scripts/ac-matrix.sh check <タスク名>` が `AUTHZ OK` でなければ（表が無い。この仕組みの前に approved になった spec もこれ）、5a も通す。
    `model: 要る` で `scripts/ac-model.sh check <タスク名>` が `MODEL OK` でなければ、5b も通す（`model:` が無い spec は `要らない` として扱う）。
    未決の答えで AC を書き足すなら、7 のとおり `status: draft` に戻してから直し、再承認をもらう。AC を変えずに `AUTHZ OK` になれば approved のまま

### 0. 規模を確かめる
CLAUDE.md の「規模と進め方」に当てはめる。
- 軽微（typo・文言・lint）なら「spec は要らないので直接直す」と伝えて終わる。既存のテストで再現できるバグなら「spec は要らない。`/debug <症状>` で直す」と伝えて終わる
- 迷うなら「spec 要る？」と 1 問だけ聞く
- **新しい URL・ルート・列・エラーコードが要るなら中以上**にする（plan の「外の約束」で決める。小のままだと build と accept-test が約束を共有できない）
- **大きすぎる**なら 1 本にしない。基準は「別々にテストでき、別々に完了と言える機能が複数あるか」だけ
  （例: ロールごとに別の機能になっている）。縦切りで画面・API・DB の全層に触るのは普通なので、分割の理由にしない。
  分けるなら、先に「何本に分けるか」と「作る順番」を提示して合意を取り、spec は 1 本ずつ書く

### 1. 読む
質問する前に、自分で分かることを集める。読んだ量がそのまま質問の質になる。
- `.claude/project.md`（置き場、ロール、外の約束の種類。PJ ごとの値はここにしか書かない）。「PR の向き先」は既定のベースブランチで、spec の `base:` の初めの値にする
- 関連するコード（画面・処理の本体・データ・テスト）。ロールの一覧は project.md の「ロール」が指す場所
- 設計書（project.md の「置き場」）の該当節（変更が設計書と矛盾しそうなら、ここで気づく）
- `docs/spec/` と `docs/plan/` の似たタスク（過去の決定を蒸し返さない）
- `docs/research/` の関連調査

### 2. 前提一覧を出して、止まる
読んで分かったことと、分からないので置いた仮定を **分けて** 並べて見せ、AskUserQuestion で確かめる。
コードから読んだことも「事実」ではなく「こう理解した」として見せる。読み違いは、質問の前に潰すのが一番安い。

```
## 前提の確認
### コードから読んだこと（違っていたら直してください）
- 予約のキャンセルは `CancelReservation` が担い、キャンセル後に返金の処理は走っていない
- キャンセルボタンは予約した本人と管理者にだけ出ている
### 置いた仮定（合っていますか）
- 今回はキャンセル直後の返金だけで、まとめての再返金は対象外
- 返金に失敗したときは予約の状態を「返金エラー」にするだけで、画面は開いたままにする
```

見せたら AskUserQuestion で聞いて、答えを待つ:
- 「コードから読んだこと」はまとめて 1 問（「違いは無い（推奨）／違うところがある」。違うなら Other に書いてもらう）
- 「置いた仮定」は 1 つ 1 問（「合っている／違う」。違うなら Other に正しい前提を書いてもらう）。4 問を超えるなら分けて聞く

前提が直ると、聞くべき質問が変わる。答えは決定ログの材料にする。

「置いた仮定」には、いつも **PR の向き先** を 1 つ入れる（例:「PR の向き先は `develop`（project.md の既定）」）。
タスクのブランチはここから切り、ac-review はここからの差分を採点し、deliver はここに PR を出す。build が始まると変えられないので、spec で決める。
- 違うと言われたら、答えのブランチが app の origin にあるかを確かめる（app の cwd で `git ls-remote --heads origin <ブランチ>`。空なら無い）。無ければ「まだ無いブランチ」と伝えて聞き直す。spec はブランチを作らない
- 決めた値を frontmatter の `base:` に書く。既定と違うなら、理由を決定ログに書く

### 3. 判断が要ることだけ聞く
聞くのは、コードにも設計書にも答えが無く、相手が決めるしかないこと。目的、完了の定義、スコープ外、
ロール別の可否、例外時の扱い、優先順位。
- AskUserQuestion で聞く。1 回に 4 問まで。選択肢を付け、推奨があれば先頭に置く
- 答えが分かっていることを確認のために聞かない。前提一覧で済んでいる
- 1 回で全部聞こうとしない。答えで次の質問が変わるなら、分けて聞く

質問が多いと相手は雑に答えるようになり、雑な答えは雑な spec になる。少なく、鋭く。

**状態のモデル（5b）を作るか** も、ここで人に決めてもらう（frontmatter の `model:`）。spec が自分で「要らない」と決めると、確かめたくないところを外せてしまうので、決めるのは人。
次のどれかに当てはまるなら「作る（推奨）／作らない」、当てはまらなければ「作らない（推奨）／作る」の順で 1 問で聞く:
- 同じものの状態が 3 つ以上あり、AC がその移り変わりを書いている（予約済み → キャンセル済み → 返金エラー → 返金済み）
- 同じ操作が 2 回・同時に来うる（二重クリック、再送、再試行、画面とバッチが同じものに触る）
- お金・在庫・回数のように、数がずれると困るものがある
問いには、当てはまったもの（か、当てはまるものが無いこと）を書く。答えを `model: 要る` か `model: 要らない` にし、決定ログにも書く

### 4. 固まった節から下書きを見せる
全部できてから見せると、ずれが大きくなってから直すことになる。受け入れ条件は特に、
固まった時点で見せて「このテストが通れば完了、で合っていますか」と確かめる。

### 5. 保存して、止まる
末尾の「確認項目」を通してから `docs/spec/<タスク名>-spec.md` に `status: draft` で保存し、docs リポジトリでコミットしてから
（`(cd docs && git add spec/<タスク名>-spec.md && git commit -m "docs(<略号>): spec <タイトル>（draft）" -- spec/<タスク名>-spec.md)`。docs は app とは別の git リポジトリ）、
要約を出して、AskUserQuestion で聞く。
- 未決事項が残っていれば、先に 1 つ 1 問で聞く。答えは決定ログに書き、下書きを直して保存・コミットし直す。答えで新しい未決が出たら、また聞く
- 未決が空になったら、**5a（認可の表）と、`model: 要る` なら 5b（状態のモデル）を通してから**（回し方は「5a と 5b の回し方」）、承認を 1 問で聞く:「確定する（推奨）／直したいところがある／保留」
  - 確定する → 6 へ。直したいところがある → Other の内容で直して、保存・コミットしてからもう一度聞く。保留 → draft のまま止まる

答えを待つ間もそのあとも、plan を書き始めない。コードに触らない。

### 5a と 5b の回し方（並べて回し、問いはまとめて聞く）
AC を直すたびに表とモデルを作り直すので、spec でいちばん往復が多いのはここ。往復の数を減らすために、回し方だけを次のようにする。
何を確かめ、結果をどう問いにするか（5a・5b の各節）は変えない。

1. **並べて回す。** `model: 要る` なら、`/ac-matrix` と `/ac-model` のサブエージェントを **1 つのメッセージで 2 つ同時に出す**（Agent ツールの呼び出しを同じメッセージに 2 つ）。
   片方の結果を待ってから、もう片方を出さない。2 つは AC を読むだけで、書くファイルも別（`-authz.md` と `-model.qnt`・`-model.md`）なので、ぶつからない。`model: 要らない` なら 5a だけ
   - 回し直すのは、要るほうだけ。AC を変えたら両方（両方とも「古い」になる）。AC を変えずに「形の誤り」で回し直すなら、その片方だけ
   - 2 つともコミットまでする。コミットの順番は前後してよい（ファイルが別で、`-- <パス>` でコミットする）。`index.lock` でぶつかったときは、それぞれが打ち直す（`/ac-matrix` の 4・`/ac-model` の 5「保存して、返す」）
2. **両方が返ってから、問いをまとめて聞く。** 2 つの `check` の出力を要約せずにそのまま見せてから、5a の 3 と 5b の 3 で「聞く」になったものを **全部** 集めて聞く。
   片方の問いだけ先に聞いて、答えを書いて回し直す、をしない（もう片方の問いが、古い AC のままもう 1 往復する）
   - 1 回の AskUserQuestion は 4 問まで。5 問以上なら、回し直さずに続けて何回かに分けて聞く
   - 並べ方は 5a の問い → 5b の問い。同じ AC についての問いは隣に置き、問いの頭に「認可の表:」「状態のモデル:」を付ける
   - ある答えで別の問いが要らなくなりそうでも（例: 「できない」になれば、2 回押される道すじも消えそう）、自分で外さずに聞く。要らなくなったかは、回し直しが決める。
     ただし、前の答えが無いと選択肢を作れない問いだけは、その回は聞かずに残す（次の回し直しで、また出てくる）
3. **答えをまとめて AC に書き、1 回だけ回し直す。** 全部の答えを AC と決定ログに書き、**1 つのコミット**にしてから 1 に戻る（両方を並べて回す）。答えを 1 つ書くたびに回し直さない
4. **最後の 2 つの問いも 1 回で聞く。** `AUTHZ OK` と（要るなら）`MODEL OK` がそろったら、5b の 4（どちらもありうるにしたこと）と、承認の問い（5）を、1 回の AskUserQuestion の 2 問にして聞く。
   `model: 要らない` なら承認の 1 問だけ。「AC に書きたいものがある」と答えられたら、承認の答えは使わずに、AC に書いてコミットし 1 に戻る

### 5a. 認可の表を、別の会話に埋めてもらう
AC どうしに抜けや食い違いが無いかを、「誰がどの操作をできる・できないか」の表で確かめる。
**この会話は表を書かない・直さない。** AC を書いた会話が表を作ると、AC の抜けは表でも同じように抜け、空いたマスはありそうな答えで埋まってしまう。
表は、AC の本文と枠だけを見る別の会話（`/ac-matrix`）が埋める。枠の行（「よそ」を含む）は `scripts/ac-matrix.sh` が project.md から作るので、行を落として埋まったように見せることもできない。

1. **サブエージェントで `/ac-matrix` を回す**（Agent ツール。`model` は作る側と別。orchestrate の「設定」の審判側）。プロンプトは次の 2 行だけにする。spec の中身・前提・自分の考え・「こう埋まるはず」を足さない（足すと別の会話にした意味が消える）:

       /ac-matrix <タスク名>
       .claude/skills/ac-matrix/SKILL.md を読んで、そのとおりに動く。読んでよいのは、そこに書いてあるものだけ。

2. **返ってきた `scripts/ac-matrix.sh check` の出力を、要約せずにそのまま人に見せる**。自分でも `scripts/ac-matrix.sh check <タスク名>` を回して、同じ結果か確かめる
3. 結果で分ける:
   - `AUTHZ OK` → 5b も済んでいれば（要らなければそのまま）承認の質問へ（「5a と 5b の回し方」の 4）
   - 「表の形の誤り」だけ（抜け・番号の打ち間違い）→ もう一度 1 から回す。2 回続いたら、出力を見せて人に聞いて止まる
   - 「人に聞くこと」（未決・矛盾）がある → 1 マス（か、同じ理由のマスのまとまり）を 1 問にする。5b の問いとまとめて聞く（「5a と 5b の回し方」の 2）。
     問いは「<行> は <操作> をできますか（<メモ>）」、選択肢は「できない／できる」（どちらが推奨かは決めない。人が決めること）。矛盾なら、食い違う AC を問いに書いて「AC-n に合わせる／AC-m に合わせる」
   - 「古い」→ 1 から回し直す
4. 答えは **AC に書き足す**（表には書かない）。5b の答えと一緒に 1 つのコミットにする。Then に「〜は 403（forbidden）」「〜には一覧に出ない」のように書くか、「よそ」のまとまりなら AC を 1 本足す（例: 「AC-XXX-n: 他の拠点の管理者と未ログインは返金の理由を保存できない」）。決定ログにも問いと答えを書き、spec を docs でコミットする
5. AC を変えたので、表もモデルも古くなった。**1 から回し直す**（`model: 要る` なら 5b と並べて。この会話で表を直さない）。`AUTHZ OK` になるまで繰り返す

表（`docs/spec/<タスク名>-authz.md`）は `/ac-matrix` がコミットする。この会話は、表のファイルを開いて書き換えない（打ち間違いを見つけても、1 から回し直す）。
build・accept-test・ac-review は AC を読む。表は AC の抜けを見つけるための道具で、答えの置き場は AC だけ。

オーケストレーターから呼ばれたとき（サブエージェントはサブエージェントを呼べない）は、5a と 5b をまとめて次のようにする。
まず `scripts/ac-matrix.sh check <タスク名>` と、`model: 要る` なら `scripts/ac-model.sh check <タスク名>` を自分で回して、今の結果を見る。
- 回し直しが要るもの（表・モデルが無い、「古い」、「形の誤り」だけ）がある → spec の下書きをコミットしてから、出力の最後に、要るものを並べた「次」の行を書いて止まる。
  両方なら「次は `/ac-matrix <タスク名>` と `/ac-model <タスク名>`（並べて）」、片方ならその 1 つ（orchestrate が審判側で並べて回し、`/spec` に戻ってくる）。
  片方が「人に聞くこと」を出していても、もう片方の回し直しが要るなら、先に回し直す（問いは両方そろってからまとめて返す）
- 「人に聞くこと」がある（回し直しが要るものは無い）→ 5a の 3 と 5b の 3 の問いを **全部** 1 つの「## 質問」で返す（4 問を超えてよい。orchestrate が分けて聞く）。
  前提の表には、`check` の出力の該当の行（認可の表なら 行 × 操作・答え・出典・メモ、モデルなら 該当の行と道すじ）をそのまま書く。書く先は「spec の受け入れ条件と決定ログ」
- 「## 人の答え」で答えが来たら、全部を 4 のとおり AC と決定ログに書いて 1 つのコミットにし、「次は `/ac-matrix <タスク名>` と `/ac-model <タスク名>`（並べて）」（`model: 要らない` なら `/ac-matrix` だけ）と書いて止まる
- `AUTHZ OK` で、要るなら `MODEL OK` → 「どちらもありうるにしたこと」（要るときだけ）と承認の問いを、1 つの「## 質問」で返す（「5a と 5b の回し方」の 4）

### 5b. 状態のモデルを、別の会話に書いて回してもらう（`model: 要る` のときだけ）
状態が移り変わるものや、同じ操作が 2 回・同時に来るものは、認可の表では事故が見つからない。
別の会話（`/ac-model`）が AC の本文だけから Quint のモデルを書き、`quint run` でランダムに何回も動かして、**AC のとおりに作っても起きてしまう事故** を探す。
考え方は 5a と同じ: **この会話はモデルを書かない・直さない**。答えは AC に書き足す。AC を変えたら、5a と 5b の両方を回し直す（並べて回す。「5a と 5b の回し方」）。

1. **サブエージェントで `/ac-model` を回す**（5a と同じく、`model` は作る側と別。5a の `/ac-matrix` と同じメッセージで出す）。プロンプトは次の 2 行だけ:

       /ac-model <タスク名>
       .claude/skills/ac-model/SKILL.md を読んで、そのとおりに動く。読んでよいのは、そこに書いてあるものだけ。

2. **返ってきた `scripts/ac-model.sh check` の出力を、要約せずにそのまま人に見せる**。自分でも `scripts/ac-model.sh check <タスク名>` を回して確かめる（ランダムなので、道すじは毎回違ってよい。OK か NG かが同じか）
3. 結果で分ける。どれも 1 つを 1 問にする。5a の問いとまとめて聞き、答えをまとめて AC と決定ログに書いて 1 つのコミットにしてから、1 から回し直す（「5a と 5b の回し方」の 2・3）:
   - **破れた**（起きてはいけないことが起きる道すじがある）→ 道すじを AC の言葉で問いにする（例:「返金エラーのときに再返金が 2 回押され、両方成功すると返金が 2 回になります。どうしますか」）。
     選択肢は「防ぎ方を AC に書く（例: 走っている再返金があるうちは押せない）／起きてもよい（起きてはいけないことの AC を直す）」。防ぎ方は人に Other で書いてもらうか、案を 1〜2 個出して選んでもらう
   - **たどり着かなかった**（AC の Then の状態に行けない）→「AC-n の『<状態>』には、AC のとおりだとたどり着けません。何が足りませんか」。AC どうしが食い違っていることが多い
   - **行き止まり**（終わりでないのに、何もできなくなる状態がある）→「<状態> になったあと、どうなりますか」。抜け方を AC に書く
   - **人に聞くこと**（モデルに書けなかったこと）→ 1 つずつ聞く
   - 「形の誤り」だけ・「古い」→ 1 から回し直す（2 回続いたら、出力を見せて人に聞いて止まる）
4. `MODEL OK` になったら、「どちらもありうるにしたこと」（AC が言っていない振る舞い）を人に見せて、1 問で聞く:「このままでよい（推奨）／AC に書きたいものがある」。
   `AUTHZ OK` もそろっていれば、承認の問いと同じ AskUserQuestion で聞く（「5a と 5b の回し方」の 4）。書きたいものがあれば、Other の内容を AC に書いて 1 から回し直す
5. 人に見せるときは、結果の言い方を変えない。`MODEL OK` は「**ランダムに試して見つからなかった。全部は調べていない**」で、「起きない」「安全」とは言わない

モデル（`docs/spec/<タスク名>-model.qnt` と `-model.md`）は `/ac-model` がコミットする。この会話は開いて書き換えない。
オーケストレーターから呼ばれたときは、5a の「オーケストレーターから呼ばれたとき」に 5b の分も書いてある（回し直しも問いも、5a とまとめて返す）。

### 6. 「確定」と言われたら（5 の質問で「確定する」を選ばれたときも）
未決事項が空で、`scripts/ac-matrix.sh check <タスク名>` が `AUTHZ OK`（終了コード 0）、`model: 要る` なら `scripts/ac-model.sh check <タスク名>` も `MODEL OK` であることを確かめて `status: approved` にし、`updated` を更新して docs でコミットし
（`(cd docs && git add spec/<タスク名>-spec.md && git commit -m "docs(<略号>): spec <タイトル>（approved）" -- spec/<タスク名>-spec.md)`）、
次を規模で分けて伝えて止まる。未決が残っているなら、approved にせず残りを聞く。
- 中以上: 「次は新しいセッションで `/plan <タスク名>`」。plan はブランチを見ないので、app は既定のベースブランチ（project.md の「PR の向き先」）のままでよい
- 小: 「受け入れテストを作るなら、次は別セッション（build と別のモデル）で `/accept-test <タスク名>`。作らないなら、次は新しいセッションで `/build <タスク名>`」。
  ブランチは build が入口で作る（app がこのタスクのベースブランチ（spec の `base:`。以下 `<base>`）か既定のベースブランチ（project.md の「PR の向き先」）にいて作業ツリーが空なら、`feat/<タスク名>` を `origin/<base>` から切る）ので、人は切り替えなくてよい。
  並行作業で worktree を使うときだけ、「`/build` の前に project.md の「並行作業」の始め方で `feat/<タスク名>` に入る」と添える。spec は自分でブランチを切り替えない

### 7. 確定後に変更が要るとき
実装中に spec と違うことをしたくなったら、**spec を先に直してから実装する**。
決定ログに変更と理由を追記し、`status: draft` に戻して docs でコミットし、再承認をもらう。承認が下りてから実装に戻る。
AC を変えたら認可の表と状態のモデルは古くなる（`check` が「古い」を出す）。再承認の前に 5a（と、`model: 要る` なら 5b）をもう一度通す。

`base:` は、build が始まったら（app にタスクのブランチがある。`git branch --list <ブランチ>` か `git ls-remote --heads origin <ブランチ>`）spec では変えない。
ブランチは前の `base:` から切ってあるので、`base:` だけ変えると、PR に別のブランチのコミットが混ざる。変えたいと言われたら、そう伝えて人に任せる（ブランチを切り直すか、`base:` を戻すか）。

差し戻し（todo の `[ ] S-n`）から入ったときは、こう進める:
1. S-n ごとに AskUserQuestion で「spec をこう直す（案を書く）／spec は今のままでよい」を聞いて決め、どちらも決定ログに書く。前提一覧（2）と質問（3）の進め方は新しく書くときと同じ
2. 直すものが 1 つでもあれば `status: draft` に戻して直し、5 と同じように保存・コミットして止まる。今のままでよいものだけなら approved のまま
3. 5 と同じ承認の質問で「確定する」を選ばれたら（今のままでよいものだけなら決めた時点で）approved にし、todo の該当行を `- [x] S-n <内容> → <決めたこと>（決定ログ YYYY-MM-DD）` にして、spec と一緒に docs でコミットする
   （`(cd docs && git add spec/<タスク名>-spec.md plan/<タスク名>-todo.md && git commit -m "docs(<略号>): spec <タイトル>（S-n を反映して approved）" -- spec/<タスク名>-spec.md plan/<タスク名>-todo.md)`）。
   `[ ]` を残したままだと、build も plan も入口で止まる。
   ui-check か ac-review で発覚した S-n で、その AC の「画面の確認」の行が「期待と違う」なら、行を「AC-XXX-n: 未確認: <内容>（S-n で AC を見直した。再確認）」に書き換えて同じコミットに入れる（そのままだと ac-review がまた必須にする）
4. 次をこの順で伝えて止まる（当てはまらないものは飛ばす）:
   - 外の約束（URL・項目名・画面に渡すデータの名前・エラーコード・列）か作業順が変わるなら「新しいセッションで `/plan <タスク名>`（plan を draft に戻して見直し、再承認）」
   - 変えた AC があり accept.md があるなら、下の `/accept-test` の案内
   - 最後に「`/build <タスク名>` で再開」（レビューの後なら `/build fix <タスク名>`。直すものが無ければ別セッションで `/ac-review <タスク名>`）。ブランチはそのまま（入り直さない）
   - ac-review の「AC の疑い」が「今のままでよい」と決まったなら、AC は正しく実装が違う。「別セッションで `/ac-review <タスク名>`（決定ログを根拠に必須として採点し直す）」と伝える

変えた AC があり、`docs/accept/<タスク名>/accept.md` があるなら（status の行だけ見る）、再承認のときに「次は別セッションで `/accept-test <タスク名>`（accept.md を `draft` に戻し、変えた AC のテストと『使った約束』を直して再承認）。その承認後に build に戻る」と伝える。
伝えないと、受け入れテストは古い AC のまま残り、ac-review で「draft に戻して直す」が出るまで誰も気づかない。build は受け入れテストを読めないので、自分ではずれに気づけない。
build のセッションで人が spec を直すよう言っても、build は直さない。止まって `/spec <タスク名>` を案内する（build の 5）。
spec を置き去りにしてコードだけ変えると、AC と実装がずれて `/ac-review` の基準が消える。

## 書き方

### タスク名
英小文字とハイフン（例: `reservation-cancel-refund`）。ファイル名の先頭に付け、省略しない。
並列の worktree で同名ファイルが衝突するのを防ぐため。

### 受け入れ条件（AC）
spec の中で一番大事な節。実装側はここからテストを起こし、`/ac-review` はここに照らして diff を読む。
- `AC-<略号>-<番号>` で番号を振る（略号はタスク名から 2〜4 文字）
- Given / When / Then で書く。Then は **テストで確かめられる粒度** にする
  （「正しく動く」ではなく「422 が返り `errors['room_id']` がある」）
- ロールで振る舞いが変わるなら、ロールごとに AC を分けるか、Given にロールを書く
- 変えないこと（既存の振る舞いの維持）も AC にする。退行はここで防ぐ
- 実コードの骨格やシグネチャは書かない。実装詳細が主役になり、合意の文書でなくなる

```
### AC-RCR-2: 返金に失敗してもキャンセルは成立する
- **Given** 予約した本人として、決済サービスが 503 を返す状態で
- **When** 予約をキャンセルする
- **Then** 予約はキャンセルされ、状態は「返金エラー」。画面にはエラーのトーストが出て、再返金ボタンが表示される
```

### 境界
CLAUDE.md の共通の 3 段階（いつもやる／先に聞く／絶対やらない）は書き写さない。
**このタスクで追加される分だけ** 書く。例: 「既存の CSV の列順は変えない（絶対やらない）」
「送信先 URL の設定項目を増やすなら先に聞く」。

### 決定ログ
質問と回答の要点を表に残す。spec の価値の半分はここにある。
あとから読む人（未来の自分を含む）が「なぜこうなった」を辿れるようにする。確定後の変更もここに積む。

## 出力テンプレート
この構成で書く。節を増やすのはよいが、減らさない（空なら「なし」と書く）。課題のキー（project.md の「PR と課題管理」）は入れない。
frontmatter の値は次のとおりにする。
- `status`: `draft` か `approved`。表記を揺らさない。`grep -l '^status: approved' docs/spec/*-spec.md` で確定分を拾う
- `scale`: `小` か `中以上`（CLAUDE.md の「規模と進め方」と同じ呼び方。`中以上` は plan が要る）
- `model`: `要る` か `要らない`（3 で人が決めた値。5b を回すか）
- `base`: このタスクのベースブランチ（app の PR の向き先）。2 で確かめた値。既定と同じでも書く。`base:` が無い spec（この項目ができる前のもの）は、どのスキルも project.md の「PR の向き先」として扱う

```markdown
---
status: draft
scale: 小
model: 要らない
base: main
created: YYYY-MM-DD
updated: YYYY-MM-DD
---
# spec: <タイトル>

## 目的
なぜやるか。誰のどんな困りごとか。

## ゴール
何ができたら完了か。1〜3 行。

## 前提
### コードから読んだこと
### 合意した仮定

## 境界（このタスク固有の追加）
- 先に聞く:
- 絶対やらない:

## スコープ外

## 受け入れ条件
### AC-XXX-1: <見出し>
- **Given**
- **When**
- **Then**

## 影響範囲
- 画面:
- API / Port:
- DB:
- docs:

## 決定ログ
| 日付 | 問い | 決定 | 理由 |
|---|---|---|---|

## 未決事項
（approved にするときは「なし」）

## 次のセッションが最初に読むもの
- この spec
- 設計書の <該当ファイル> §<節>
- 関連コード: <パス>
- 確認コマンド: `scripts/check.sh`（外さない。DB に触らないなら `--quick`。追加で見るものがあれば書く。例: 特定のテストクラス、開く URL）
- 完了の見た目: <AC がすべて green で、画面でこう見える>
```

## よくある言い訳
| 言い訳 | 反論 |
|---|---|
| コードを読めば分かるから前提確認は要らない | 読み違いを一番安く直せるのは今。「読んだつもり」が一番高くつく |
| 小さい変更だから spec は大げさ | 規模は CLAUDE.md の表で決める。「先に聞く」に触るなら小さくても要る |
| 質問をまとめて一度に聞いたほうが早い | 答えで次の質問が変わる。まとめると雑な答えが返り、雑な spec になる |
| 承認を待つ間に plan を書いておけば効率的 | spec が直れば plan は捨てる。待つのが仕事 |
| 相手が忙しそうだから仮定で進める | 仮定で進めた spec は合意ではない。未決として止まる |
| 認可の表くらい、自分で埋めたほうが早い | AC を書いた頭で埋めると、AC と同じところが抜ける。別の会話が埋めるから、抜けが見える |
| 未決のマスは常識で決まるから、表に答えを書いておく | 表に書いた答えは誰も読まない。人に聞いて、AC に書き足す |
| サブエージェントに spec の考えを伝えたほうが正確に埋まる | 伝えると、こちらの読み方がそのまま写る。プロンプトは決めた 2 行だけ |
| 状態のモデルは大げさだから、要らないことにしておく | 作るかどうかは人が決める。当てはまるものがあれば、推奨は「作る」 |
| MODEL OK だから、2 回返金は起きないと伝える | ランダムに試して見つからなかっただけ。言い方を変えない |

## Red Flags
- 1 回に 5 問以上聞いた
- 前提一覧を出す前に質問した
- 未決事項や承認を、AskUserQuestion で聞かずに文章に書いただけで止まった（対話なのに）
- 保存と同じターンで plan やコードに触った
- 未決事項が残ったまま approved にした
- 保存した spec を docs でコミットせずに止まった（build は docs の `git status --porcelain` が空であることを入口にしている）
- 相手の返答が無いのに「置いた仮定」を「合意した仮定」に移した
- ブランチがベースブランチだからと spec や plan への引き継ぎを止めた（spec と plan はブランチを見ない）
- PR の向き先を確かめずに、`base:` を既定のまま書いた。origin に無いブランチを `base:` に書いた
- build が始まったあとに `base:` を書き換えた
- approved の spec を呼ばれて「approved です」で終えた。todo の「spec への差し戻し」を読まなかった
- 差し戻しを反映したのに、todo の S-n を `[x]` にしてコミットしなかった
- 認可の表（`docs/spec/<タスク名>-authz.md`）をこの会話で書いた・直した
- `/ac-matrix` のサブエージェントに、決めた 2 行のほかのこと（spec の中身・期待する答え）を渡した
- 未決・矛盾の答えを、AC に書かずに決定ログや表だけに書いた。AC を変えたのに表を作り直さずに承認を聞いた
- `AUTHZ OK` でないのに approved にした
- 状態のモデルを作るかを、人に聞かずに決めた。`model: 要る` なのに `MODEL OK` でないまま approved にした
- 状態のモデル（`-model.qnt`・`-model.md`）をこの会話で書いた・直した。事故の道すじを人に見せずに、AC を自分で直した
- `MODEL OK` を「起きない」「安全」と言い換えた
- `model: 要る` なのに、`/ac-matrix` と `/ac-model` を別々のメッセージで順に回した（片方を待ってからもう片方を出した）
- 5a と 5b の問いを片方ずつ聞いた。答えを 1 つ書くたびに回し直した。答えが要らなくしそうな問いを、聞かずに自分で外した

## 確認項目（承認を求める前に）
- 対話中の決定で規模が変わっていないか。最初の判定のままにせず `scale` を見直したか（小のつもりが画面に渡すデータの約束や複数のテストに及んでいたら 中以上。新しい URL・ルート・列・エラーコードが要るのに 小 にしていないか）
- すべての AC が Given/When/Then で、Then はテストで確かめられる粒度か
- ロールで振る舞いが変わる箇所に、ロールごとの AC があるか。変えない振る舞いも AC にあるか
- 認可の表を `/ac-matrix`（別の会話）が埋め、`scripts/ac-matrix.sh check <タスク名>` が `AUTHZ OK` か（承認の質問の前に。未決・矛盾の答えは AC に書いたか）
- frontmatter の `model:` を人に決めてもらったか。`要る` なら、`/ac-model`（別の会話）が書いたモデルが `MODEL OK` か（承認の質問の前に）
- 境界（このタスク固有の追加）を書いたか。無ければ「なし」と書いたか
- 決定ログに質問と回答の要点が入っているか
- frontmatter に `base:` があり、「置いた仮定」で確かめた PR の向き先と同じか。既定と違うなら、決定ログに理由があるか
- 「次のセッションが最初に読むもの」に、設計書の節とコードのパスが具体的に書いてあるか
- docs でコミットしたか（`(cd docs && git status --porcelain)` に spec が残っていないか）
