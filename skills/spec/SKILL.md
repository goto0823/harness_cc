# spec — 対話で仕様を固めて書き出す

このスキルの仕事は **spec を書いて承認をもらうところまで**。plan も実装もしない。
spec は「これを満たせば完了」の合意であり、合意は人が確認して初めて成立する。
同じターンで実装に進むと、その確認が飛ぶ。

## 人が応答できない環境では使わない
`claude -p` などのヘッドレス実行やスケジュール実行では、このスキルは成立しない。往復が本体だから。
それでも呼ばれた、または途中で相手が返答できないと分かったときは、推測で埋めて確定にしない。
前提一覧と未決事項を出力し、「spec を固めるには回答が必要」とブロッカーとして止まる。

## 進め方

### 0. 規模を確かめる
CLAUDE.md の「規模と進め方」に当てはめる。
- 軽微（typo・文言・lint）なら「spec は要らないので直接直す」と伝えて終わる。既存のテストで再現できるバグなら「spec は要らない。`/debug <症状>` で直す」と伝えて終わる
- 迷うなら「spec 要る？」と 1 問だけ聞く
- **新しい URL・ルート・列・エラーコードが要るなら中以上**にする（plan の「外の約束」で決める。小のままだと build と accept-test が約束を共有できない）
- **大きすぎる**なら 1 本にしない。基準は「別々にテストでき、別々に完了と言える機能が複数あるか」だけ
  （例: ロールごとに別の機能になっている）。縦切りで画面・API・DB の全層に触るのは普通なので、分割の理由にしない。
  分けるなら、先に「何本に分けるか」と「作る順番」を提示して合意を取り、spec は 1 本ずつ書く

### 1. 読む
質問する前に、自分で分かることを集める。読んだ量がそのまま質問の質になる。
- `.claude/project.md`（置き場、ロール、外の約束の種類。PJ ごとの値はここにしか書かない）
- 関連するコード（画面・処理の本体・データ・テスト）。ロールの一覧は project.md の「ロール」が指す場所
- 設計書（project.md の「置き場」）の該当節（変更が設計書と矛盾しそうなら、ここで気づく）
- `docs/spec/` と `docs/plan/` の似たタスク（過去の決定を蒸し返さない）
- `docs/research/` の関連調査

### 2. 前提一覧を出して、止まる
読んで分かったことと、分からないので置いた仮定を **分けて** 並べ、「違ったら今直して」と頼む。
コードから読んだことも「事実」ではなく「こう理解した」として見せる。読み違いは、質問の前に潰すのが一番安い。

```
## 前提の確認
### コードから読んだこと（違っていたら直してください）
- 予約のキャンセルは `CancelReservation` が担い、キャンセル後に返金の処理は走っていない
- キャンセルボタンは予約した本人と管理者にだけ出ている
### 置いた仮定（合っていますか）
- 今回はキャンセル直後の返金だけで、まとめての再返金は対象外
- 返金に失敗したときは予約の状態を「返金エラー」にするだけで、画面は開いたままにする
```

ここで返答を待つ。前提が直ると、聞くべき質問が変わる。

### 3. 判断が要ることだけ聞く
聞くのは、コードにも設計書にも答えが無く、相手が決めるしかないこと。目的、完了の定義、スコープ外、
ロール別の可否、例外時の扱い、優先順位。
- 1 回に 4 問まで。選択肢を付け、推奨があれば先頭に置く（AskUserQuestion が使える）
- 答えが分かっていることを確認のために聞かない。前提一覧で済んでいる
- 1 回で全部聞こうとしない。答えで次の質問が変わるなら、分けて聞く

質問が多いと相手は雑に答えるようになり、雑な答えは雑な spec になる。少なく、鋭く。

### 4. 固まった節から下書きを見せる
全部できてから見せると、ずれが大きくなってから直すことになる。受け入れ条件は特に、
固まった時点で見せて「このテストが通れば完了、で合っていますか」と確かめる。

### 5. 保存して、止まる
末尾の「確認項目」を通してから `docs/spec/<タスク名>-spec.md` に `status: draft` で保存し、docs リポジトリでコミットしてから
（`(cd docs && git add spec/<タスク名>-spec.md && git commit -m "docs(<略号>): spec <タイトル>（draft）")`。docs は app とは別の git リポジトリ）、
要約と未決事項を出して承認を求める。**そのターンはここで終える。** plan を書き始めない。コードに触らない。

### 6. 「確定」と言われたら
未決事項が空であることを確かめて `status: approved` にし、`updated` を更新して docs でコミットし
（`(cd docs && git add spec/<タスク名>-spec.md && git commit -m "docs(<略号>): spec <タイトル>（approved）")`）、
次を規模で分けて伝えて止まる。未決が残っているなら、approved にせず残りを聞く。
- 中以上: 「次は新しいセッションで `/plan <タスク名>`」
- 小: 「受け入れテストを作るなら、次は別セッション（build と別のモデル）で `/accept-test <タスク名>`。作らないなら、次は新しいセッションで `/build <タスク名>`」。
  `/build` に直接進むなら、build の入口（app が `feat/<タスク名>` にいる・app と docs の `git status --porcelain` が空）も一緒に伝える。build は自分でブランチを切り替えない

### 7. 確定後に変更が要るとき
実装中に spec と違うことをしたくなったら、**spec を先に直してから実装する**。
決定ログに変更と理由を追記し、`status: draft` に戻して docs でコミットし、再承認をもらう。承認が下りてから実装に戻る。
spec を置き去りにしてコードだけ変えると、AC と実装がずれて `/ac-review` の基準が消える。

## 書き方

### タスク名
英小文字とハイフン（例: `reservation-cancel-refund`）。ファイル名の先頭に付け、省略しない。
並列の worktree で同名ファイルが衝突するのを防ぐため。

### 受け入れ条件（AC）
spec の中で一番大事な節。実装側はここからテストを起こし、`/ac-review` はここに照らして diff を読む。
- `AC-<略号>-<番号>` で番号を振る（略号はタスク名から 2〜4 文字）
- Given / When / Then で書く。Then は **テストで確かめられる粒度** にする
  （「正しく動く」ではなく「422 が返り `errors['room_id']` がある」）
- ロールで振る舞いが変わるなら、ロールごとに AC を分けるか、Given にロールを書く
- 変えないこと（既存の振る舞いの維持）も AC にする。退行はここで防ぐ
- 実コードの骨格やシグネチャは書かない。実装詳細が主役になり、合意の文書でなくなる

```
### AC-RCR-2: 返金に失敗してもキャンセルは成立する
- **Given** 予約した本人として、決済サービスが 503 を返す状態で
- **When** 予約をキャンセルする
- **Then** 予約はキャンセルされ、状態は「返金エラー」。画面にはエラーのトーストが出て、再返金ボタンが表示される
```

### 境界
CLAUDE.md の共通の 3 段階（いつもやる／先に聞く／絶対やらない）は書き写さない。
**このタスクで追加される分だけ** 書く。例: 「既存の CSV の列順は変えない（絶対やらない）」
「送信先 URL の設定項目を増やすなら先に聞く」。

### 決定ログ
質問と回答の要点を表に残す。spec の価値の半分はここにある。
あとから読む人（未来の自分を含む）が「なぜこうなった」を辿れるようにする。確定後の変更もここに積む。

## 出力テンプレート
この構成で書く。節を増やすのはよいが、減らさない（空なら「なし」と書く）。課題のキー（project.md の「PR と課題管理」）は入れない。
frontmatter の値は次の 2 つだけを使う。
- `status`: `draft` か `approved`。表記を揺らさない。`grep -l '^status: approved' docs/spec/*-spec.md` で確定分を拾う
- `scale`: `小` か `中以上`（CLAUDE.md の「規模と進め方」と同じ呼び方。`中以上` は plan が要る）

```markdown
---
status: draft
scale: 小
created: YYYY-MM-DD
updated: YYYY-MM-DD
---
# spec: <タイトル>

## 目的
なぜやるか。誰のどんな困りごとか。

## ゴール
何ができたら完了か。1〜3 行。

## 前提
### コードから読んだこと
### 合意した仮定

## 境界（このタスク固有の追加）
- 先に聞く:
- 絶対やらない:

## スコープ外

## 受け入れ条件
### AC-XXX-1: <見出し>
- **Given**
- **When**
- **Then**

## 影響範囲
- 画面:
- API / Port:
- DB:
- docs:

## 決定ログ
| 日付 | 問い | 決定 | 理由 |
|---|---|---|---|

## 未決事項
（approved にするときは「なし」）

## 次のセッションが最初に読むもの
- この spec
- 設計書の <該当ファイル> §<節>
- 関連コード: <パス>
- 確認コマンド: `scripts/check.sh`（外さない。DB に触らないなら `--quick`。追加で見るものがあれば書く。例: 特定のテストクラス、開く URL）
- 完了の見た目: <AC がすべて green で、画面でこう見える>
```

## よくある言い訳
| 言い訳 | 反論 |
|---|---|
| コードを読めば分かるから前提確認は要らない | 読み違いを一番安く直せるのは今。「読んだつもり」が一番高くつく |
| 小さい変更だから spec は大げさ | 規模は CLAUDE.md の表で決める。「先に聞く」に触るなら小さくても要る |
| 質問をまとめて一度に聞いたほうが早い | 答えで次の質問が変わる。まとめると雑な答えが返り、雑な spec になる |
| 承認を待つ間に plan を書いておけば効率的 | spec が直れば plan は捨てる。待つのが仕事 |
| 相手が忙しそうだから仮定で進める | 仮定で進めた spec は合意ではない。未決として止まる |

## Red Flags
- 1 回に 5 問以上聞いた
- 前提一覧を出す前に質問した
- 保存と同じターンで plan やコードに触った
- 未決事項が残ったまま approved にした
- 保存した spec を docs でコミットせずに止まった（build は docs の `git status --porcelain` が空であることを入口にしている）
- 相手の返答が無いのに「置いた仮定」を「合意した仮定」に移した

## 確認項目（承認を求める前に）
- 対話中の決定で規模が変わっていないか。最初の判定のままにせず `scale` を見直したか（小のつもりが画面に渡すデータの約束や複数のテストに及んでいたら 中以上。新しい URL・ルート・列・エラーコードが要るのに 小 にしていないか）
- すべての AC が Given/When/Then で、Then はテストで確かめられる粒度か
- ロールで振る舞いが変わる箇所に、ロールごとの AC があるか。変えない振る舞いも AC にあるか
- 境界（このタスク固有の追加）を書いたか。無ければ「なし」と書いたか
- 決定ログに質問と回答の要点が入っているか
- 「次のセッションが最初に読むもの」に、設計書の節とコードのパスが具体的に書いてあるか
- docs でコミットしたか（`(cd docs && git status --porcelain)` に spec が残っていないか）
