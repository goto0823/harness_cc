# pm — 要望をタスクに分けて並べ、Backlog とつなぐ

spec は 1 つのタスクの「何を」を決める。その前に、大きい要望を **spec 1 本ずつのタスク** に分け、作る順番と優先度を決める人が要る。
作り始めたら、「どこまで終わったか」を docs から拾って、チームが見る Backlog に映す人が要る。pm はその 2 つをやる。

- pm が書くのは `docs/pm/<要望名>.md` と Backlog だけ。spec・plan・todo・review・コードは書かない。読むだけ
- 分け方・順番・優先度・PR の向き先は **案を出して、人が決める**。pm が自分で決めて進めない
- Backlog はチームに通知が飛び、取り消しがききにくい。**書く前に、書く中身を全部ターミナルに出して確かめる**（「Backlog に書くとき」）

## 呼び方

| 呼び方 | やること |
|---|---|
| `/pm plan <要望名> <やりたいこと>` | 新しい要望をタスクに分ける。`docs/pm/<要望名>.md` を作り、Backlog にマイルストーンと親課題を作る |
| `/pm plan <課題キー>` | Backlog にある課題（例 `PROJ-123`）を要望として読み、同じように分ける |
| `/pm plan <要望名>` | 既にある `docs/pm/<要望名>.md` を開き直す。タスクの追加・分け直し・並べ替え・優先度の変更 |
| `/pm status [<要望名>]` | 進み具合をまとめ、Backlog に反映する。要望名が無ければ `docs/pm/*.md` の全部 |
| `/pm run <要望名>` | herdr でタスクごとに worktree のワークスペースを開き、そのパネルの cc に `/orchestrate pm <タスク名>` を渡して並べて走らせる。子が持って帰った質問を人に聞いて、答えを子のパネルに返す |
| 「<タスク名> マージした」（`/pm run` の会話で、人がそう言う。いくつ並べてもよい） | そのタスクの子を止め、ワークスペースと worktree を片付ける（run 6）。`/pm close <要望名> <タスク名>…` と打っても同じ |

要望名はタスク名と同じ書き方（英小文字とハイフン。例 `member-portal-renewal`）。

## 人が応答できない環境では使わない
ヘッドレス（`claude -p`）やスケジュール実行では使わない。分け方の合意と、Backlog に書く前の確認が本体だから。
呼ばれたら、読んで分かったこと（`/pm status` ならまとめの表）だけを出し、「人の確認が要る」と書いて止まる。Backlog には書かない。`/pm run` も、子の質問に答える人がいないので使わない。

## 人に聞くとき
人が決めること・確かめること（分け方、順番、優先度、PR の向き先、Backlog に書いてよいか）は、出力の文章に書くだけにしない。**AskUserQuestion で聞き、答えが返るまで次に進まない**。
- 1 回に 4 問まで。選択肢は 2〜4 個で、推奨があれば先頭に「（推奨）」を付けて置く。答えで次の質問が変わるなら分けて聞く
- コード・設計書・docs・Backlog で分かることは聞かない
- 課題の削除・`--yes` が要る操作・force など、取り返しのつかない操作を選択肢にしない
- 答えは `docs/pm/<要望名>.md` の決定ログに書いてコミットする。`/clear` しても残る
- 「次は〜」（次に呼ぶスキルの案内）は質問にしない。出力の最後の 1 行に置く

## 使うもの

### project.md の「課題管理（Backlog）」
PJ ごとの値はここから読む。`<ここに: …>` のままの項目があれば、下の「ID の調べ方」で調べた一覧を出し、どの項目に何を書けばよいかを伝えて止まる。project.md は pm が書き換えない。

- スペース（`xxx.backlog.com`）、プロジェクトキー
- 親課題の種別 ID、子課題の種別 ID
- 状態 ID: `未対応`・`処理中`・`処理済み`・`完了`
- 説明の記法（`markdown` か `backlog`）
- 課題の URL の形（例 `https://xxx.backlog.com/view/<課題キー>`）
- docs のファイルの URL（project.md の「置き場」。説明に spec・plan のリンクを書くのに使う。無ければパスだけ書く）

### bee（Backlog の CLI）
- 入口で `bee auth status -s <スペース>` を打ち、ログインしていなければ「`bee auth login` が先」と伝えて止まる。`--show-token` と `bee auth token` は使わない（トークンが画面に出る）
- どのコマンドにも `-s <スペース>` と `-p <プロジェクトキー>`（課題キーを渡すコマンドは要らない）を付ける。環境変数 `BACKLOG_SPACE`・`BACKLOG_PROJECT` に頼らない（別の PJ の値が残っていることがある）
- 結果は `--json` で受け取る（課題キーと ID を控えるため）
- **省略した必須の項目は、bee が対話で聞いてくる**（Claude からは答えられず止まる）。`bee issue create` には `-p`・`-t`・`--type`・`--priority` を必ず渡す
- 状態・種別・マイルストーン・担当者は **数字の ID** で渡す（`--status open` のような名前は通らない）。担当者は自分なら `@me`
- **`--parent-issue` は課題キーでなく、親課題の数字の ID**。`bee issue view <親課題キー> --json id` で調べる
- 優先度は名前で渡す（`high`・`normal`・`low`）
- 長い説明は、app のルートの `local/pm/<要望名>/` にファイルで書き、`-d "$(cat local/pm/<要望名>/<ファイル>)"` で渡す（`local/` は git 管理外）
- `--notify` は、人に言われたときだけ付ける
- 使わない: `bee issue delete`、`bee * delete`、`--yes`、`bee api` での書き込み（`-X POST` など）。消したい・まとめて直したいと言われたら、コマンドを出して人に任せる

### ID の調べ方（読むだけ）

    bee issue-type list -p <プロジェクトキー> -s <スペース> --json
    bee status list -p <プロジェクトキー> -s <スペース> --json
    bee milestone list -p <プロジェクトキー> -s <スペース> --json
    bee project users -p <プロジェクトキー> -s <スペース> --json

## Backlog に書くとき（plan と status で共通）
1. 書くものを全部、**この形でターミナルに出す**。要約しない。説明の本文も全文出す

       ## Backlog に書く下書き（<n> 件）
       | # | 操作 | 対象 | 中身 |
       |---|---|---|---|
       | 1 | マイルストーンを作る | <要望名> | 期限: <日付か「なし」> |
       | 2 | 親課題を作る | <タスク名> | 優先度: normal / 種別: <ID> / マイルストーン: 1 |
       | 3 | 状態を変える | PROJ-130（P-1） | 処理中 → 完了 |
       | 4 | コメントする | PROJ-128 | 下の本文 |

       ### 2 の説明（全文）
       <本文>

       ### 実行するコマンド
       bee milestone create -p <プロジェクトキー> -s <スペース> -n "<要望名>" --json
       bee issue create -p <プロジェクトキー> -s <スペース> -t "<タイトル>" --type <ID> --priority normal --milestone <1 の ID> -d "$(cat local/pm/<要望名>/<タスク名>.md)" --json
       ...

   前の番号の結果（マイルストーンの ID、親課題の ID）を使う行は、`<1 の ID>` のように書いておき、実行するときに埋める
2. AskUserQuestion で 1 問だけ聞く:「書く（推奨）／直したいところがある／書かない」
   - 直したいところがある → Other の内容で直して、もう一度 1 から出す
   - 書かない → Backlog に触らずに止まる。docs の変更はそのままコミットしてよい
3. 「書く」なら、上から 1 つずつ実行する。1 つ終わるたびに、返ってきた課題キー・ID・状態を `docs/pm/<要望名>.md` に書く（「Backlog に書いたこと」と、タスクの表・子課題の表）
4. 途中で失敗したら、そこで止まる。済んだものはやり直さない（二重に作らない）。済んだところまでを docs でコミットし、失敗したコマンドとエラーをそのまま出す
5. 全部済んだら docs でコミットする

        (cd docs && git add pm/<要望名>.md && git commit -m "docs(pm): <要望名> Backlog に反映" -- pm/<要望名>.md)

書く直前に、相手の今の状態を `bee issue view <課題キー> --json` で読み直す。`docs/pm/<要望名>.md` に控えた「最後に書いた状態」と違う（人が Backlog で手で変えた）なら、その課題は書かずに、違いを出して聞く。人の手の変更を上書きしない。

## 進め方

### 0. 入口を確かめる（1 つでも満たさなければ止まる）
- `.claude/project.md` の「課題管理（Backlog）」が埋まっている（`/pm run` は Backlog に書かないので見ない）
- `bee auth status -s <スペース>` でログインしている（`/pm run` は見ない）
- docs が docs のベースブランチ（project.md）にいて、`pm/` に未コミットの変更が無い（`(cd docs && git status --porcelain)`。ほかの行は、並行作業のタスクの書きかけなので見ない）。pm は docs のブランチを切り替えない。docs のコミットが `index.lock` で断られたら、少しおいて 1 回だけやり直す
- `/pm status` で、`docs/pm/` に要望が 1 つも無い: 「先に `/pm plan`」と伝えて止まる

### plan 1. 読む
- 要望。`<課題キー>` なら `bee issue view <課題キー> --comments --json` で、本文とコメントを読む
- `.claude/project.md`（「PR の向き先」は PR の向き先の既定。「ロール」）
- 関わりそうなコードと設計書（project.md の「置き場」）。どこに手が入るか、の当たりを付けるだけ。深く読まない（それは spec の仕事）
- `docs/pm/`・`docs/spec/` の似た要望とタスク（同じものを二重に作らない。決まったことを蒸し返さない）
- `/pm plan <要望名>` で既にあるなら、その `docs/pm/<要望名>.md` と、各タスクの今の状態（下の「status 1」と同じ読み方）

### plan 2. 分け方の案を出して、止まる
分ける基準は spec と同じ:「**別々にテストでき、別々に完了と言える**か」だけ。縦切り（画面・API・DB の全層に触る）は普通なので、分ける理由にしない。
大きすぎるタスクを 1 本にしない。小さすぎて単独で完了と言えないものは、まとめる。

タスクごとに、次を案として並べる:
- タスク名（英小文字とハイフン。spec のファイル名になる）と、目的を 1 行
- 規模の見込み（CLAUDE.md の「規模と進め方」の `小` か `中以上`。見込みであって、決めるのは spec）
- 依存（そのタスクのコードが base に入っていないと build できないタスク。`/pm run` は、依存先がマージされるまで build の前で待たせる。spec・plan・受け入れテストは並べて進める。コードが要らない順番の希望は、依存でなく「順」で表す）
- PR の向き先（既定は project.md の「PR の向き先」。違う向き先がよさそうなら理由を添える。決めるのは spec の `base:` で、ここに書くのは案）
- 優先度の案（`high`・`normal`・`low`）と、その理由（使う人への価値、リスクの大きさ、ほかのタスクを止めているか）

順番は、依存を崩さない範囲で、優先度の高いもの・リスクの大きいもの（早く分かったほうが安い）を先にする。

出したら AskUserQuestion で聞く:
- 分け方: 「この分け方でよい（推奨）／分け方を変えたい」
- 順番と優先度: 「この順番と優先度でよい（推奨）／変えたい」
- 案で既定と違う PR の向き先を出したタスクがあれば、1 つ 1 問
- 要望の期限（マイルストーンの期限）: 「なし（推奨）／決まっている」

答えで変わったら、出し直して聞き直す。決まったことは決定ログに書く。

### plan 3. 保存する
`docs/pm/<要望名>.md` を「出力テンプレート」の形で書き、`status: approved` にして docs でコミットする。

    (cd docs && git add pm/<要望名>.md && git commit -m "docs(pm): <要望名> タスクに分ける" -- pm/<要望名>.md)

### plan 4. Backlog に書く
「Backlog に書くとき」の手順で、次を書く。既にある（表に課題キーがある）ものは作らない。
- マイルストーン（要望 1 つに 1 つ。名前は要望名か、人が決めた名前。期限があれば `--release-due-date`）
- 親課題（タスク 1 つに 1 つ。マイルストーンに入れる。子課題はまだ作らない。作業ステップは plan か build が todo を作ってから決まる）
  - タイトル: `<タスクの目的>（<タスク名>）`
  - 説明: 目的、依存（ほかのタスクの親課題のキー）、PR の向き先の案、spec の置き場（`docs/spec/<タスク名>-spec.md`。まだ無い）、「進み具合は `/pm status` がこの課題のコメントに書く」
  - 優先度: 決めた優先度
- 元の課題（`/pm plan <課題キー>` のとき）: コメントで、分けた親課題のキーの一覧とマイルストーンを書く。元の課題の状態は変えない
- `/pm plan <要望名>` で変えたとき: 増えたタスクの親課題を作る。優先度・順番が変わった親課題は優先度を直し、なぜ変えたかをコメントする。タスクを消したときは課題を消さず、「このタスクはやめた」とコメントし、閉じるかを人に聞く

### plan 5. 伝えて止まる
タスクの表（親課題のキーつき）を出して、最後に 1 行:「次は新しいセッションで `/spec <最初のタスク名>`」。
spec に `base:` を決めてもらうため、案で既定と違う向き先にしたタスクなら「PR の向き先は `<案>` の案（pm の決定ログ）」と添える。

### status 1. 各タスクの今を読む
`docs/pm/<要望名>.md` のタスクごとに、次だけを読む（中身・コード・テストは読まない。決めない）:
- spec（`docs/spec/<タスク名>-spec.md`）の frontmatter の `status`・`scale`・`base`
- plan（`docs/plan/<タスク名>-plan.md`）の `status`、受け入れテスト（`docs/accept/<タスク名>/accept.md`）の `status`
- todo（`docs/plan/<タスク名>-todo.md`）の「作業順」の `- [ ]` / `- [x]` の行、「spec への差し戻し」の `- [ ]` の行、「画面の確認」の行の頭、申し送りの最新の行と deliver の行
- 最新のレビュー（`docs/review/<タスク名>-review-<n>.md`）の 1〜2 行目
- 出したか（orchestrate の「出したかの見分け方」と同じ）: 「docs の出し方」が `PR` なら docs に `deliver/<タスク名>` ブランチがあるか（`(cd docs && git branch --list deliver/<タスク名>)`）。`直接 push` なら todo の deliver の行に app の PR の番号があるか

上から当てはめて、最初に当たった行を「今どこ」にする:

| 状態 | 今どこ | 次のコマンド |
|---|---|---|
| spec が無い | 未着手 | `/spec <タスク名>` |
| spec が `draft` | spec を書いている | `/spec <タスク名>` |
| todo の「spec への差し戻し」に `[ ]` がある | spec の直し待ち（S-n） | `/spec <タスク名>` |
| `中以上` で plan が無いか `draft` | plan を書いている | `/plan <タスク名>` |
| accept.md が `draft` | 受け入れテストの承認待ち | `/accept-test <タスク名>` |
| 「作業順」に仕上げより前の `[ ]` がある | build（<済み>/<全部>） | `/build <タスク名>` |
| 「画面の確認」に `未確認`・`期待と違う` がある | 画面の確認 | `/ui-check <タスク名>` |
| レビューが無いか、最新が `fail` | レビュー（fail なら直し） | `/ac-review <タスク名>`（fail なら `/build fix <タスク名>`） |
| 最新のレビューが `pass` で、まだ出していない | 出す前 | `/deliver <タスク名>` |
| 出した | PR のレビュー待ち | 人のレビューとマージ |

申し送りの最新の行の「引っかかったこと」が埋まっていれば、「止まっている理由」に写す。

### status 2. まとめを出す
Backlog に書く前に、ターミナルにまとめの表を出す。ここまでは読むだけなので、ヘッドレスでもここまでは出してよい。

    ## <要望名> の進み具合（YYYY-MM-DD）
    | 順 | タスク | 親課題 | 今どこ | 作業ステップ | 止まっている理由 | 次のコマンド |
    |---|---|---|---|---|---|---|
    | 1 | reservation-cancel-refund | PROJ-128 | build | 3/5 | なし | `/build reservation-cancel-refund` |

### status 3. Backlog との違いを出す
タスクごとに、Backlog に書くべきことを拾う。前回書いたこと（`docs/pm/<要望名>.md` の表）と同じものは書かない。
- **子課題を作る**: todo の「作業順」があって、まだ子課題が無い行（`P-n`・`CP-n`。仕上げの `P-n` も 1 つの子課題）
  - タイトル: `<タスク名> <P-n> <見出し>`。説明: todo と plan の置き場、AC の番号
  - 親は親課題の数字の ID（`--parent-issue`）。マイルストーンは親と同じ。優先度は親と同じ
  - 作業順に行が増えた（build が分けた `P-3a` など）ら、その分を作る。行が消えたら、子課題は消さず「このステップは無くなった」とコメントし、閉じるかを人に聞く
- **子課題の状態**:
  - `[x]` → 完了（`bee issue close <子課題キー> -c "<コミットか、todo の申し送りの行>"`）
  - build が進めている最初の `[ ]` → 処理中（`bee issue edit <子課題キー> --status <処理中の ID>`）
  - それ以外の `[ ]` → 未対応のまま（変えない）
- **親課題の状態**:
  - 未着手 → 未対応
  - spec を書いているところから、出す前まで → 処理中
  - 出した → 処理済み（PR の URL か番号をコメントに書く）
  - 完了にはしない。マージを確かめて閉じるのは人
- **親課題のコメント**: 前回のコメントから「今どこ」か作業ステップの数が変わったときだけ、次の形で 1 つ書く

      進み具合（/pm status YYYY-MM-DD）
      - 今どこ: build（3/5）
      - 終わった: spec・plan・P-1・P-2・CP-1
      - 止まっている理由: なし
      - 次: /build reservation-cancel-refund

違いが無ければ「Backlog は今のままでよい」と出して終わる。

### status 4. Backlog に書く
「Backlog に書くとき」の手順で書く。書いたら最後に 1 行:「次は <止まっているタスクの次のコマンド>」（いちばん順番が前のもの）。

### run 0. 入口（plan・status の入口に足す）
- 人が `/pm run <要望名>` を打った。app の本体（worktree でない。`git rev-parse --git-dir` と `--git-common-dir` が同じ）のルートにいる
- **herdr のパネルの中で動いている**（`test "${HERDR_ENV:-}" = 1`）。違えば「herdr のパネルで cc を立ち上げてから `/pm run`」と伝えて止まる。`herdr status` でサーバーが動いているかも見る。herdr の命令の書き方は、入っている `herdr --help` と `herdr agent`・`herdr worktree` などのグループの表示が正（素の `herdr` は打たない。画面が立ち上がる）
- `docs/pm/<要望名>.md` が `status: approved`
- project.md の「並行作業」の「置き場」「始め方」「終わり方」「worktree ごとに分けるもの」「同時に回すタスクの数」「子の cc の起動」が埋まっている。「同時に回すタスクの数」が `1` なら、並べずに 1 つずつ回す
- 「worktree の中の docs」が共有（シンボリックリンク）なら、「docs の出し方」が `直接 push`。`PR` のままなら、理由（deliver が docs のブランチを切り替えると、ほかのタスクのコミットが PR に混ざる）を出して止まる
- 本体へのシンボリックリンクで共有するもの（「worktree の中の docs」が共有なら `docs`。「始め方」で `ln -s` しているものがあれば、それも。ふつうは `local`）が、子の cc から確認なしで読み書きできるか。
  cc はリンク先の実体で作業ディレクトリの中かを見るので、足りないと子が docs や `local/orchestrate/` に触るたびに、auto でも確認のダイアログで止まる。共有しないなら飛ばす
  - 「子の cc の起動」に、共有するものごとに `--add-dir <本体の絶対パス>/<それ>` がある。パスは絶対パス（`/` で始まる）で、`realpath` が本体の `$(pwd -P)/<それ>` と同じ（この会話は本体のルートにいる）
  - 本体のルートそのもの（`$(pwd -P)`）を `--add-dir` にしていない（子が本体の app のコードを書けてしまう）
  - docs を共有するなら、`.claude/headless-build.json` の `permissions.additionalDirectories` にも本体の docs の絶対パスがある（build の `claude -p` は子の `--add-dir` を引き継がない。無いと build が todo.md を書けずに止まる。絶対パスの deny も要る。README §3 の「足すもの」）
  - 足りなければ、子を立ち上げずに止まる。足りないものを、そのまま貼れる形で出す（例: 「子の cc の起動」に `--add-dir /home/me/app/docs --add-dir /home/me/app/local` を足す）。project.md は install.sh で上書きされないので、テンプレに例が入る前に埋めた project.md では抜けていることが多い
- 回している状態の置き場 `local/pm/<要望名>/` を作る（`mkdir -p`）。`local/` は git 管理外。前に回した `local/pm/<要望名>/state.md` があれば読んで、続きから始める（`herdr agent list` で、子がまだ生きているかを見る）

### run 1. 始めるタスクを決める
タスクの表を順番に見て、「status 1」の読み方で今どこかを出し、次の順で決める:
- 「出した」か `state.md` で「終わり」のタスクは飛ばす。`state.md` で「走っている」「質問待ち」「人の確認待ち」「依存待ち」のものは数に入れる
- 走っているものが「同時に回すタスクの数」に届くまで、順番の前のものから始める
- 依存があるタスクも、ほかのタスクと同じブランチの決まりで始める（ブランチはどれも build が入口で `origin/<base>` から切る。依存先のブランチの上には積まない）。ただし、依存先がまだ base にマージされていなければ、**build の前で止まる** ように子に伝える（run 2 のプロンプト）。spec・plan・受け入れテストは先に進めてよい
- 始めるものが無く、走っているものも無ければ run 5 へ

### run 2. worktree とパネルを作って、子の cc を立ち上げる
herdr の命令は JSON を返す。ID は返ってきた JSON から読む（例から決めつけない）。フォーカスは人のパネルから動かさない（`--no-focus`）。
1. worktree が無ければ、project.md の「始め方」のとおりに作る（`<置き場>/<タスク名>`。`--detach` でブランチは切らない）。打ったコマンドを画面に出す
2. worktree を herdr のワークスペースとして開く。返ってきた JSON の root pane の ID（`.result.root_pane.pane_id`。無ければ `herdr pane list --workspace <ワークスペースの ID>` で）を控える

       herdr worktree open --path <置き場>/<タスク名> --label <タスク名> --no-focus

3. そのパネルで、子の cc を立ち上げる。名前は `<タスク名>` を 32 文字までに切ったもの（`[a-z][a-z0-9_-]{0,31}`。ほかの子と重ならないように）。`--` の後ろは project.md の「子の cc の起動」の引数

       herdr agent start <名前> --kind claude --pane <root pane の ID> -- <「子の cc の起動」の引数>

   `agent_not_ready`（起動で許可のダイアログが出た）が返ったら、「人の確認待ち」として run 3 の blocked と同じに扱う
4. 子にタスクを渡す。`--wait` は付けない（子のターンが終わるまで pm が止まってしまう）

       herdr agent prompt <名前> "/orchestrate pm <タスク名>"

   依存先がまだマージされていないときだけ、2 行目に「依存: <依存先のタスク名>」を足す
5. 子を待つのを、**Bash のバックグラウンド**で始める（`sleep` で待たない。ポーリングしない。終わりの通知で起きる）。子が動き出してから、次に落ち着く（idle・done・blocked）までを待つ:

       herdr agent wait <名前> --until working --timeout 60000; herdr agent wait <名前>

6. `state.md` に 1 行足す: `| <タスク名> | <worktree> | <ワークスペースの ID> | <名前> | 走っている | 0 |`（最後の列は、読んだ pm-<n>.md の n）

### run 3. 子が落ち着いたら
`herdr agent get <名前>` で状態を見る。画面の中身（コード・テスト・レビュー）は読まない。判断しない。
- **blocked**（許可のダイアログか、子が自分で聞いている）: pm は答えない（ほかの会話からの答えは同意にならない。許可は人が決める）。「<タスク名> のパネルで確認が要る。`herdr agent focus <名前>` で開いて答えてください」と出し、`state.md` を「人の確認待ち」にして、run 2 の 5 の待ちをもう一度始める
- **idle・done**: 子の worktree の `local/orchestrate/<タスク名>/pm-<n>.md` に、前に読んだものより新しいファイルがあるかを見る
  - 無い: 子が build などを裏で待っているだけ。run 2 の 5 の待ちをもう一度始める
  - ある: 新しい順でなく、番号の小さい順に 1 つずつ読む。ファイルの先頭の見出しで分ける（中身は下のとおり、そのまま出すだけ）。読んだ番号を `state.md` に書く

見出しごとの扱い:
- **「## pm へ: 質問」**: orchestrate の「人に聞くとき」と同じに聞く
  - 聞く前に、見出しの下（タスク名・前提の表・下書き）を、書き換えず・要約せずにそのまま画面に出す。いくつものタスクが並ぶので、最初に「### <タスク名> から」と見出しを付ける
  - AskUserQuestion で聞く。問いと選択肢はそのまま使う。問いの末尾に「（タスク: <タスク名>）」だけ添える
  - 答えを子のパネルに送る（`--wait` は付けない）。そのあと run 2 の 5 の待ちを始め、`state.md` を「走っている」にする

        herdr agent prompt <名前> "pm から:
        ## 人の答え
        - Q1: <問い> → <選ばれた答え。Other ならその文>（書く先: <ファイルのとおり>）"

- **「## pm へ: 終わり」**: 中身（deliver の出力）をそのまま出す。`state.md` を「終わり」にする。依存しているタスクがあれば、run 4 でマージを確かめる
- **「## pm へ: 止まった」**: 理由をそのまま出す
  - 理由が「依存 <X> のマージ待ち」: `state.md` を「依存待ち」にする。run 4 で確かめる
  - それ以外: AskUserQuestion で「続ける（pm から: 続けて）／<タスク名> のパネルで人が見る／ここでこのタスクを止める」を聞く。勝手に回し直さない
- **見出しが無い、ファイルが読めない、`herdr agent get` で子がいない（落ちた）**: 分かったことだけを出して、「<タスク名> のパネルで人が見る／ここでこのタスクを止める」を聞く

いくつもの子が同時に落ち着いたら、届いた順に 1 つずつ聞く（1 回に聞くのは 1 つのタスクのことだけ。4 問まで）。聞いている間に落ち着いたものは、次に回す。
聞き終えたら run 1 に戻って、空いた分を始める。

### run 4. 依存のマージを確かめる
「依存待ち」のタスクの依存先が「終わり」になったら、AskUserQuestion で聞く:「<依存先> の PR は <base> にマージされましたか？（マージされた／まだ）」。
pm はマージを自分で確かめない（PR を出す先は PJ ごとに違う）し、マージもしない。
「マージされた」なら、待っていた子のパネルに「pm から: 依存 <依存先> は <base> にマージされた。続けて」を送り、run 2 の 5 の待ちを始める。build は入口で `git fetch origin` してから `origin/<base>` から切るので、依存先のコードが入る。
この「マージされた」は、人が「<依存先> マージした」と言ったのと同じに扱い、依存先を run 6 で片付ける。

### run 5. 終わったら
全部のタスクが「終わり」か止めたものになったら、まとめの表（タスク・今どこ・PR・止めた理由）を出す。
- パネル・ワークスペース・worktree は、ここでは閉じない。PR がマージされたら、人が「<タスク名> マージした」と言えば run 6 で片付ける。そう伝える
- Backlog に反映するなら `/pm status <要望名>` を案内する（Backlog に書くのは status の手順だけ）
- 途中でやめたときは `state.md` を残し、「再開は `/pm run <要望名>`」と出す。子のパネルは生きたまま残る

### run 6. 「マージした」と言われたら、片付ける
人が「<タスク名> マージした」と言ったタスクだけを片付ける（いくつ並んでいてもよい。1 つずつ、順に）。
**マージされたことは、人のその言葉で決める**（squash や rebase でマージすると、元のコミットは base に入らないので、git では確かめられない）。
人が言っていないタスクは、PR が閉じたように見えても片付けない。
`/pm close <要望名> <タスク名>…` で新しい会話から呼ばれたときは、run 0 の入口を見てから、`local/pm/<要望名>/state.md` の行（worktree・ワークスペース・子の名前・状態）を使う。state.md に無いタスクは片付けない（どのワークスペースか分からない）。

worktree を消すと、そこにしか無いもの（未コミットの変更、push していないコミット、コピーの docs）も一緒に消えて戻せない。
だから、消す前に次を全部見る。**どれか 1 つでも引っかかったら、そのタスクは消さずに、見つけたものをそのまま出して** AskUserQuestion で「消す／残す（人が見る）」を聞く。推奨は付けない。
1. `state.md` でそのタスクが「終わり」（deliver まで済んだ）。ほかの状態なら、「まだ <状態>。それでも片付けますか」と聞く
2. 子が動いていない: `herdr agent get <子の名前>` が idle か done（working なら build などがまだ走っている）
3. app に未コミットの変更が無い: `git -C <worktree> status --porcelain` が空。
   本体へのシンボリックリンク（`docs`・`local` など、「始め方」で `ln -s` したもの）の行は見ない
4. app に push していないコミットが無い: `git -C <worktree> log --oneline HEAD --not --remotes` が空（HEAD までのコミットが、どれかのリモートのブランチに全部ある）。
   **この前に `git fetch --prune` を打たない**（マージでリモートのブランチが消えていると、prune で手元の追跡ブランチも消え、push 済みのコミットまで「push していない」に見える）
5. docs をシンボリックリンクでなくコピーで持っている（`test -L <worktree>/docs` が偽で、`<worktree>/docs/.git` がある）なら、docs も 3 と 4 を見る（`git -C <worktree>/docs …`）。
   「docs の出し方」が `PR` なら、docs の PR もマージされたかを人に聞く（app の「マージした」だけでは決めない）

全部通ったら、次の順で片付け、打ったコマンドを全部画面に出す:
1. 子の cc を止める（`herdr agent` のグループの、子を止める命令。書き方は `herdr agent --help` が正）
2. project.md の「終わり方」に、消す前の手順（app を止める、テストの DB を消す、など）があれば、それを打つ
3. ワークスペースと worktree を消す: `herdr worktree remove --workspace <ワークスペースの ID>`（checkout も消える。書き方は `herdr worktree --help` が正）。
   herdr で消せなかったときだけ `git worktree remove <worktree>` を打つ
   - 「未追跡のファイルがある」で断られたら、それが本体へのシンボリックリンクだけなら、リンクだけを消してからもう一度打つ: `test -L <worktree>/docs && rm <worktree>/docs`（`rm` に `-r` を付けない。リンクに `-r` を付けて消すと、たどった先の本体の docs が消えることがある）
   - それ以外で断られたら、出力をそのまま出して止まる。`--force` を付けない
4. `git worktree prune` を打ち、`git worktree list` にもう出ないことを確かめる
5. `state.md` のそのタスクを「片付け済み」にする（ワークスペースの ID と子の名前は消さずに残す）

ローカルのブランチ（`feat/<タスク名>`）は消さない。squash でマージしていると `git branch -d` は「マージされていない」で断り、`-D` は push していないコミットごと消すので、人に任せる。
最後に、片付けたタスクと、残したタスク（と理由）の表を出す。Backlog の子課題を閉じるなら `/pm status <要望名>` を案内する。

`state.md` の形:

    | タスク | worktree | ワークスペース | 子の名前 | 状態 | 読んだ pm-<n> |
    |---|---|---|---|---|---|
    | booking-list | ../wt/booking-list | w2 | booking-list | 終わり | 4 |
    | booking-cancel | ../wt/booking-cancel | w3 | booking-cancel | 依存待ち | 2 |

## よくある言い訳
| 言い訳 | 実際 |
|---|---|
| 分け方は明らかだから、聞かずに Backlog に作ってしまう | 作った課題はチームに通知が飛ぶ。分け直すと課題が散らかる。案を出して止まるのが仕事 |
| 優先度はこちらで決めたほうが早い | 優先度は事業の判断。pm は理由を添えた案まで |
| 下書きは長いので要約して見せる | 見せていない中身は確かめていない。全文出す |
| 子課題は plan を読めば先に全部作れる | 作業ステップは build が分けたり増やしたりする。todo を正にする |
| Backlog の状態が docs と違うので、docs に合わせて上書きする | 人が手で変えたのかもしれない。違いを出して聞く |
| 消したほうがきれいなので課題を消す | 消すと履歴も消える。コメントして、閉じるかを人に聞く |
| ついでに spec の下書きも書いておく | spec は `/spec` が人と対話して書く。pm は書かない |

## Red Flags
- 人の「書く」の前に、Backlog に書いた（課題・マイルストーン・コメント・状態）
- 下書きを要約して見せた。実行するコマンドを見せなかった
- `bee issue create` に必須の項目を渡さず、対話のプロンプトで止まった
- `--parent-issue` に課題キーを渡した。`--status` に状態の名前を渡した
- 課題やマイルストーンを消した。`--yes` を付けた。`bee api` で書き込んだ
- 途中で失敗したのに、済んだものをやり直した（課題の二重作成）
- 人が Backlog で変えた状態を、docs に合わせて上書きした
- 親課題を完了にした
- spec・plan・todo・review・コードを書き換えた。docs のブランチを切り替えた
- 優先度・順番・PR の向き先を、人に聞かずに決めた
- トークンを画面に出した（`--show-token`、`bee auth token`）
- ヘッドレスで Backlog に書いた
- `/pm run` で、子の pm-<n>.md 以外（パネルの画面、コード・テスト・レビューの中身）を読んで判断した。子の質問に自分で答えた。問いや選択肢を書き換えた
- `/pm run` で、子の許可のダイアログ（blocked）に `herdr agent send-keys` などで答えた
- `/pm run` で、docs や `local` をシンボリックリンクで共有しているのに、「子の cc の起動」に本体のそれの `--add-dir` が無いまま子を立ち上げた。本体のルートごと `--add-dir` にした
- `/pm run` で、子を `sleep` やポーリングで待った。`herdr agent prompt` に `--wait` を付けて pm が止まった。止まった子を聞かずに回し直した
- 人が作っていないパネル・ワークスペースを閉じた。`herdr server stop` を打った
- 依存先のマージを人に確かめずに、依存しているタスクの build を進めさせた。マージを自分でした
- 人が「マージした」と言っていないタスクの worktree を消した（`herdr worktree remove` を含む）
- run 6 のチェック（子が動いていない・未コミットが無い・push していないコミットが無い・コピーの docs）を飛ばして消した。引っかかったのに聞かずに消した
- 片付けで `--force`、`rm -r`、`git branch -D` を使った。チェックの前に `git fetch --prune` を打った

## 確認項目（下書きを見せる前に）
- 各タスクが「別々にテストでき、別々に完了と言える」か。依存が循環していないか。順番が依存を崩していないか
- タスク名が英小文字とハイフンで、`docs/spec/` の既存のタスクと重なっていないか
- 下書きの全件に、実行するコマンドと説明の全文があるか。前の結果を使う行に `<n の ID>` があるか
- `bee issue create` に `-p`・`-t`・`--type`・`--priority` と `-s` があるか
- 既に課題キーがあるものを、もう一度作ろうとしていないか

## 確認項目（書いたあと）
- 書いた件数が下書きの件数と同じか。失敗したものがあれば、それを出したか
- `docs/pm/<要望名>.md` の表に、作った課題のキーと ID、最後に書いた状態があり、docs でコミットしたか
- 最後の出力に「次」の 1 行があるか
