# arch — コードから設計書を起こし、規約は人が決める

設計書は「**これから書くコードが従う規約**」を書く文書。今のコードの説明書ではない。
コードから読めるのは**今の姿**だけで、それが決まりなのか、たまたまなのか、直したい例外なのかはコードに書いていない。
だから arch は、読んだことを数と根拠つきで出して止まり、**規約にするかどうかは人が決める**。人が決めたものだけを規約として書く。

ハーネスのほかのスキルは、設計書をこう使う。
- spec・plan は、設計書のどの型に乗るかを書く
- ac-review は、設計書に書かれた規約に反するものを**必須**にする。設計書に根拠を書けない設計の指摘は**任意**にしかならない

だから、大事な決まりが設計書に無いと、レビューで止められない。

## 人が応答できない環境では使わない
往復が本体なので、ヘッドレスでは成立しない。呼ばれたら、1〜2 の「読んだこと」までを出して、「規約を決めるには回答が必要」と止まる。設計書は書かない。

## 呼び方
- `/arch <層>`: その層の設計書を書く（無ければ作る。あれば 8 の「ずれを直す」）。層は PJ の言葉で（例: `backend`、`frontend`、`mobile`）
- `/arch contract <層A> <層B>`: 2 つの層の境界の契約（データの形、失敗の返し方、生成物、命名）
- `/arch test`: テスト方針（共通と層ごと）
- `/arch index`: `docs/design/README.md`（文書の一覧と読む順番）を、今ある設計書から作り直す
- 1 回に 1 つの文書だけ。全部を一度に書かない（読む量が文脈からあふれ、後半を雑に読む）

## 進め方

### 0. 入口を確かめる
- docs の作業ツリーが空（`(cd docs && git status --porcelain)`）。設計書は docs リポジトリに入る
- `.claude/project.md` の「置き場」の「設計書」を見る。`<ここに: …>` か「なし」なら、置き場を `docs/design/` にしてよいか 1 問だけ聞く
- 同じ層の設計書が既にあるか。`status: draft` で「作業メモ」があれば、5 の「続きから再開するとき」に進む。`approved` なら 8（ずれを直す）に進む
- 調査・討論の経緯を残す場所（例 `docs/research/`）があれば、そこも読む。設計書には結論だけを書き、経緯はそちらを指す

### 1. 読む（数える。全部は読まない）
**数えるのは grep、読むのは例の数ファイル。** 層の全ファイルを開かない。
1. ディレクトリの構成（2〜3 階層まで）。各ディレクトリのファイル数
2. フレームワークと主な依存（パッケージの定義ファイル、設定）
3. 静的解析・lint・アーキテクチャテストの設定（既に機械で守っている決まりがここにある）
4. 依存の向き: 層 × 層 で、import / use / require の行数を数えて表にする（「書き方」の依存の表）
5. 型（パターン）の多数派と例外: 例「コントローラーのうち、DB に直接触るもの」「処理の本体の戻り値の形」「エラーの返し方」。数と `ファイル:行` を控える
6. 既にある設計書・CLAUDE.md（ディレクトリごとのものも）・README の中の決まり
7. テストの置き場と種類（テスト方針を書くとき）

広い層では、数える作業を下調べのエージェントに分けてよい。返してもらうのは数と `ファイル:行` だけにし、ファイルの中身を丸ごと持ち帰らせない。

### 2. 読んだことを出して、止まる
事実（数と根拠）と、そこからの推測を**分けて**出す。推測は推測として書く。

```
## 読んだこと（違っていたら直してください）
### 構成
- app/ の下に 6 層: Http（42 ファイル）、UseCases（31）、Domain（18）、Infrastructure（22）、Models（12）、Support（3）

### 依存の向き（import の行数。行 → 列を参照）
|            | Http | UseCases | Domain | Infrastructure | Models |
|---|---|---|---|---|---|
| Http       | -    | 40       | 12     | 0              | 9      |
| UseCases   | 0    | -        | 35     | 2              | 6      |
| Domain     | 0    | 0        | -      | 0              | 0      |
- Domain から外への参照は 0。Infrastructure を参照する UseCases が 2 ファイル（RegisterRoom.php:8、CancelReservation.php:11）

### 型の多数派と例外
- コントローラー 14 個のうち 12 個は処理の本体を呼ぶだけで、DB に触っていない（例: RoomController.php:20）
- 残り 2 個は、コントローラーの中で直接クエリを書いている（ReportController.php:45、ExportController.php:31）

### 既に機械で守っている決まり
- 静的解析の level 8。アーキテクチャテストは無い

### 推測（決まりかどうかは分からない）
- Domain は外を知らない作りを狙っているように見える
```

ここで返答を待つ。読み違いは、規約を決める前に直すのが一番安い。

### 3. 1 節ずつ、決めて、見せる
2 の読み違いが直ったら、節を**決まった順に 1 つずつ**進める。前の節が決まると、次の節で聞くことが変わるから。
1 つの節で「聞く → 答え → その節の下書きを見せる → 合っていると言われる」まで回してから、次の節に進む。全部の節を一度に聞かない。全部できてから見せない。

**順番**（設計書の種類ごと。テンプレートの節の並びと同じ）

| 設計書 | 順番 |
|---|---|
| 層（architecture） | ① 目的と範囲 → ② 設計原則 → ③ ディレクトリの木と責務 → ④ 各層が知っていること / 知らないこと → ⑤ 主要な設計（3-1、3-2 … を **1 つずつ**）→ ⑥ 命名 → ⑦ 禁止事項（機械で検査している / していない）→ ⑧ 既知の違反と移行ロードマップ → ⑨ ADR の見直し |
| 境界の契約（contract） | ① 対象 → ② 共有するデータの形 → ③ 画面ごとのデータ → ④ 失敗の返し方 → ⑤ 成功の知らせ方 → ⑥ 名前の付け方 → ⑦ 生成物 → ⑧ 名前の安定性 → ⑨ 範囲 → ⑩ ADR の見直し |
| テスト方針（test） | ① 共通の原則 → ② ピラミッド → ③ 用語 → ④ しないこと → ⑤ 実行 → 層ごとに（⑥ スイート → ⑦ どこで何を → ⑧ ダブル → ⑨ アーキテクチャテスト → ⑩ 書き方 → ⑪ 認可の表 → ⑫ しないもの） |

飛ばしてよいのは、人が「この節は要らない」と言った節だけ。飛ばした節は「なし」と書いて残す。

**1 つの節での聞き方**
- 聞くのは、コードからは分からず、人が決めるしかないこと。1 回に 4 問まで。選択肢を付け、推奨があれば先頭に（AskUserQuestion が使える）。答えで次の質問が変わるなら、分けて聞く
- 多数派と例外が見えたところは、4 つの選択肢で聞く:
  - **規約にする**（例外は「既知の違反」として書き、移行ロードマップに載せる）
  - **規約にする。例外も許す**（例外の条件を規約に書く）
  - **規約にしない**（書かない。たまたま）
  - **決めない**（未決に残す）
- 規約にするものには、**理由**を聞く。理由が無い規約は、守る人が判断できず、破る理由のほうが強く見える。
  却下した代替案があれば、それも聞く（ADR に残す）。答えが無ければ「なし」と書く。作らない
- 決まったら、その節の下書きを見せて「この節はこれで合っていますか」と聞く。直しがあれば直して、もう一度見せる。合っていると言われてから次の節へ

**節ごとの書き方**
- 原則は 3〜8 個。1 行の原則と 1 行の理由
- ディレクトリ構成は木で書き、各ディレクトリに 1 行の責務を添える。「各層が知っていること / 知らないこと」の表を必ず付ける（レビューの根拠になる）
- 主要な設計は、型 1 つで 1 節。規約・短い例・やってはいけない形
- 禁止事項は、機械で検査しているもの・していないものを分けて書く。検査していないものは、検査の候補として 6 の「次」に出す
- 既知の違反は、ファイルと場所まで書き、いつ直すか（移行ロードマップのどこか）を書く
- ADR は、それまでの節で決めたことを 1 行ずつ。最後の節（ADR の見直し）で、漏れと理由・却下した代替案を人と確かめる。番号は通し番号で、消さない

### 4. 毎ターン、「決めたこと」を出す
往復が長くなると、何を決めたかを見失う。節を進めるたびに、ターンの最後に次を出す。

```
## 決めたこと（/arch backend）
- 済んだ節: ① 目的と範囲 ／ ② 設計原則（5 個）／ ③ ディレクトリの木
- 今の節: ④ 各層が知っていること / 知らないこと
- 残りの節: ⑤ 主要な設計（3-1〜3-4）／ ⑥ 命名 ／ ⑦ 禁止事項 ／ ⑧ 既知の違反 ／ ⑨ ADR の見直し
- 規約: 7 ／ 例外つきの規約: 1 ／ 規約にしない: 2 ／ 未決: 1（Infrastructure を UseCases から参照してよいか）
- 既知の違反: 2（ReportController.php:45、ExportController.php:31）
- ADR の候補: 4
```

数は下書きと一致させる。直したら、ここも直す。

### 5. 区切りで保存する（途中で止めても、続きから再開できる）
次のどれかに当たったら、そこまでの下書きを `docs/design/<文書>.md` に `status: draft` で保存し、docs でコミットする。
- 人が「今日はここまで」「続きは次で」と言った
- 3 つの節が済んだ（区切りごとに残すため）
- 全部の節が済んだ

保存するときは、文書の末尾に「作業メモ」の節を置く。続きのセッションは、ここから再開する。

```markdown
## 作業メモ（/arch が使う。approved にするときに消す）
- 済んだ節: ①〜③
- 次の節: ④ 各層が知っていること / 知らないこと
- 決めたこと: <4 の一覧をそのまま>
- 読んだこと: <2 で出した数と ファイル:行 のうち、まだ使っていないもの>
- 聞いている途中の問い: <答えを待っている質問。無ければ「なし」>
```

    (cd docs && git add design/<文書>.md && git commit -m "docs(design): <文書>（draft。<済んだ節>まで）")

途中で保存したら、4 の一覧と「続きは `/arch <層>` で、<次の節> から」を出して止まる。
全部の節が済んで保存したら、末尾の「確認項目」を通してから、要約（原則の数、層の数、禁止事項の数（うち機械で検査しているもの）、既知の違反の数、ADR の数、未決の数）を出して承認を求める。
**どちらも、そのターンはここで終える。** コードもテストも書かない。

**続きから再開するとき**（`/arch <層>` を呼んだら、その文書が `status: draft` で「作業メモ」がある）
1. 作業メモと、済んだ節の下書きを読む
2. 作業メモの「読んだこと」が古くなっていないか、1 の数え方で次の節に要る分だけ数え直す。変わっていたら、変わった数を出して止まる（前の節の決定に響くなら、その節に戻る）
3. 4 の一覧を出してから、「次の節」から 3 を続ける

### 6. 「確定」と言われたら
未決が空であることを確かめ、「作業メモ」の節を消して `status: approved` にし、確定日を書いて docs でコミットする。未決が残っているなら approved にせず残りを聞く。続けて:
1. `docs/design/README.md` の一覧と読む順番に、この文書を足す（無ければ `/arch index` と同じ形で作る）
2. 層のディレクトリに置く CLAUDE.md の下書きを見せる（harness_cc の `templates/dir-CLAUDE.md` の形）。中身は「どの設計書の、どの節を読むか」の指し先と、「規約とタスクの指示が矛盾したら、勝手に判断せず報告する」の 1 行だけ。規約の本文も要約も書かない。人が「置いて」と言ったら app に置く。app のコミットは人に任せる（ブランチの都合があるので、ファイルを置くだけ）
3. `.claude/project.md` の「置き場」の「設計書」と「ディレクトリごとの CLAUDE.md」が `<ここに: …>` なら、書き入れてよいか聞く
4. 「次」を出して止まる:
   - 機械で検査していない禁止事項があれば「アーキテクチャテストにするなら `/spec <タスク名>`（例: 依存の向きのテスト）」
   - 既知の違反があれば「直すなら、移行ロードマップの順に `/spec`」
   - 境界の契約やテスト方針がまだ無ければ「次は `/arch contract …` か `/arch test`」

### 7. 確定後に規約を変えるとき
規約を変えるのは、コードより先。
- 文書の先頭の「改訂」に、日付と変えた節と ADR 番号を足す
- ADR に新しい行を足す。前の決定を置き換えるなら、前の行の決定の末尾に「（ADR <n> で置換）」と書く。**前の行は消さない**（なぜ変わったかを辿れなくなる）
- `status: draft` に戻して再承認をもらう
- 境界の契約を変えるときは、両側の設計書と同じ PR で変える。片側だけ変えない

### 8. 設計書が既にあるとき（ずれを直す）
ずれも 1 つずつ聞く。4 の一覧と 5 の区切りの保存も同じ。
1 と同じように数え、設計書の規約ごとに、コードが従っているかを照らす。ずれを 3 つに分けて出して止まる:
- **コードが規約に反している**（新しい違反）→ 既知の違反に足すか、直すタスク（`/spec`）にするか
- **設計書が古い**（コードのほうが新しい決定に従っている）→ 規約を直す（7 の手順。ADR を足す）
- **設計書に無い型が増えている** → 3 の「決まりか、たまたまか」で聞く

ずれごとに根拠（規約の節と `ファイル:行`）を付ける。どちらが正しいかは人が決める。ここでもコードは直さない。

## 書き方

### 依存の表の作り方
層ごとのディレクトリ（または名前空間）を決め、層 × 層 で「行の層のファイルが、列の層を参照している行数」を数える。

    # 例: Domain から Http を参照している行（あれば、内側が外側を知っている）
    grep -rn 'import .*\/http\/' src/domain | wc -l

0 の組は「たぶん決まり」、少しだけある組は「例外か違反か、人に聞く」候補、多い組は「普通の向き」。
数えたコマンドは設計書に書かない（数は変わる）。決まった向きだけを「各層が知っていること / 知らないこと」に書く。

### 現状と規約を混ぜない
- 規約の節（原則・構成・主要な設計・横断ルール）は、人が「規約にする」と答えたものだけ。言い切りで書く（「〜する」「〜しない」）
- 今のコードが規約と違うところは「既知の違反」と「移行ロードマップ」に書く。規約の節に「今は〜だが」と混ぜない
- 経緯・討論・却下の詳しい理由は、経緯の置き場（例 `docs/research/`）に書き、設計書からは指すだけ

### 根拠の書き方
- 読んだことには、数と `ファイル:行` を付ける。「だいたい」「ほとんど」と書かない
- 規約の理由は、人が言ったことを書く。言い換えて強めない

## テンプレート
`templates/` の 4 つ。節を増やすのはよいが、減らさない（空なら「なし」）。
- `templates/architecture.md` … `<層>-architecture.md`
- `templates/contract.md` … `<層A>-<層B>-contract.md`
- `templates/test-strategy.md` … `test-strategy.md`
- `templates/README.md` … `docs/design/README.md`

frontmatter の `status` は `draft` か `approved` の 2 つだけ。`grep -l '^status: approved' docs/design/*.md` で確定分を拾う。

## よくある言い訳
| 言い訳 | 反論 |
|---|---|
| コードがこうなっているから、これが決まり | コードは今の姿。決まりかどうかは人が決める。たまたまを規約にすると、直したい例外まで守らされる |
| 理由は見れば分かるので、こちらで書いておく | 書いた理由が人の理由と違えば、規約の意味が変わる。理由は聞く。無ければ「なし」 |
| 全部の層を一度に書いたほうが整合がとれる | 読む量があふれて後半が雑になる。1 文書ずつ。整合は境界の契約で取る |
| 節をまとめて聞いたほうが早い | 前の節の答えで次の節の問いが変わる。まとめると雑な答えが返り、雑な規約になる |
| 途中で保存すると中途半端な文書が残る | draft で、作業メモがあるので中途半端だと分かる。保存しないと、セッションが切れたときに決めたことが消える |
| 例外の 2 ファイルはついでに直しておく | arch はコードを直さない。既知の違反に書き、直すのは `/spec` から |
| 古い ADR は紛らわしいので消す | 消すと、なぜ今こうなのかを辿れない。置き換えた印を付けて残す |
| 数えるのは大変なので、だいたいで | 数が無いと、人は「決まりか、たまたまか」を判断できない |

## Red Flags
- 人が「規約にする」と答えていないものを規約の節に書いた
- 人が言っていない理由・却下した代替案を書いた
- 読んだことに数か `ファイル:行` が無い。「ほとんど」「だいたい」と書いた
- 規約の節に「今は〜だが」と現状を混ぜた。既知の違反にファイルと場所が無い
- コード・テスト・設定を書き換えた。アーキテクチャテストを書いた（書くのは `/spec` から）
- 1 回に 2 つ以上の文書を書いた
- 節を順番どおりに進めなかった。前の節の下書きに「合っている」をもらう前に次の節へ進んだ
- 節を進めたターンに「決めたこと」の一覧を出さなかった。一覧の数が下書きと合わない
- 途中で止めるのに保存しなかった。保存したのに作業メモを書かなかった
- 再開のときに、作業メモの「読んだこと」を数え直さずに続けた
- approved にするときに作業メモを消さなかった
- ADR の行を消した・番号を振り直した
- 境界の契約を片側の設計書だけ変えた
- 未決が残ったまま approved にした。保存した文書を docs でコミットせずに止まった
- ディレクトリごとの CLAUDE.md に、設計書の本文や要約を書いた。指し先に節の番号が無い

## 確認項目（承認を求める前に）
- 規約の節のすべての項目が、3 で人が「規約にする」と答えたものか
- 原則のすべてに理由があるか。ADR のすべてに理由があり、却下した代替案が「なし」を含めて埋まっているか
- 「各層が知っていること / 知らないこと」の表があり、層の構成の木と一致しているか
- 禁止事項が「機械で検査している / していない」に分かれているか
- 既知の違反に、ファイルと場所、移行ロードマップのどこで直すかがあるか
- 読んだことの数と根拠を、2 で出したとおりに使っているか（下書きの途中で数を変えていないか）
- 未決事項が節として残っているか（無ければ「なし」）
- 順番のすべての節が済んでいるか（飛ばした節は、人が「要らない」と言ったもので、「なし」と書いてあるか）
- 4 の一覧の数と、下書きの数が合っているか
- docs でコミットしたか
