# ac-matrix — AC の本文だけから、認可の表を埋める

spec を書いた会話が自分で表を作ると、AC の抜けは表でも同じように抜け、空いたマスはありそうな答えで埋まる。表は通るのに、誰も決めていない答えが混ざる。
だから表は、**spec を書いた会話とは別の会話** が、**AC の本文と枠だけ** を見て埋める。AC から読み取れないマスが残れば、それが AC の抜けそのもの。
このスキルは表を埋めて確かめるだけで、AC を直さない。未決と矛盾は spec の会話が人に聞き、答えを AC に書き足す。表はそのあと、また別の会話で作り直す。

## 入口（1 つでも満たさなければ止まる）
- spec を書いた会話ではない（この会話で spec を書いたり直したりしていない）。書いていたら「新しい会話で」と伝えて止まる
- `docs/spec/<タスク名>-spec.md` がある
- `.claude/project.md` の「## ロール」に「### 認可の表の行」の表があり、`<ここに: …>` のままでない。無ければそう伝えて止まる（`scripts/ac-matrix.sh new` が教えてくれる）
- `scripts/ac-matrix.sh` がある。無ければ「先に install.sh で入れて」と伝えて止まる

## 読んでよいもの（これだけ）
- `scripts/ac-matrix.sh ac <タスク名>` が出す、spec の「## 受け入れ条件」の節
- `scripts/ac-matrix.sh new <タスク名>` が作る枠（`docs/spec/<タスク名>-authz.md`）。行の名前と説明は project.md から来ている

**読まないもの**: spec のほかの節（目的・前提・決定ログ・スコープ外など）、spec のファイルそのもの、plan、コード、設計書、受け入れテスト。
決定ログに答えがあっても、AC に書いていなければ、build も accept-test も ac-review も AC から読むので、無いのと同じ。AC に無ければ「未決」にして、AC に書き足してもらう。

## 進め方

### 1. 枠を作って、AC を読む
    scripts/ac-matrix.sh new <タスク名>
    scripts/ac-matrix.sh ac <タスク名>

`new` は前の表があっても作り直す。表はいつも AC から作り直すもので、前の答えを引き継がない。

### 2. 埋める
枠の中の説明のとおりに、「## 行」「## 操作」「## 答え」を埋める。
- **行**: project.md から来た行は消さない・名前を変えない。AC にしか出てこない相手（「予約した本人」など）は足してよい。出典に AC の番号を書く
- **操作**: AC の When から、人によってできる・できないが分かれうる操作を 1 行ずつ（例: 「返金の理由を保存する」「予約の一覧を見る」）。同じ操作を言い換えて 2 行にしない。出典に AC の番号を書く。
  そういう操作が 1 つも無い（夜間のバッチだけ、など）なら、表の行を書かずに「操作なし: <理由>」と 1 行書く
- **答え**: 操作 × 行 のすべての組み合わせを 1 行ずつ。答えは 4 つだけ:
  - `できる`／`できない`: AC の Given・Then にそう書いてある。出典に、そう読んだ AC の番号を書く
  - `未決`: AC から読み取れない。メモに「AC のどこまでは書いてあって、何が無いか」を書く
  - `矛盾`: AC どうしで食い違う。出典に食い違う AC を 2 つ以上書き、メモに何が食い違うかを書く

**推測で埋めない。** ここがこのスキルの全部。
- 「ふつう未ログインはできない」「管理者ならできるはず」は、AC に書いていなければ `未決`
- 「本人と管理者ができる」とだけ書いてあるとき、ほかの人が「できない」とは読まない。`未決` にして、メモに「できる人だけが書いてあり、ほかの人のことは書いていない」と書く。
  AC に「ほかの人はできない」「〜だけ」「403」「見えない」のように書いてあれば `できない`
- 「同じ拠点の管理者」とだけ書いてあれば、「他の拠点の管理者」は `未決`
- 未決が多くなるのは失敗ではない。AC の抜けが見えただけ。数を減らすために答えを寄せない

### 3. 確かめる
    scripts/ac-matrix.sh check <タスク名>

- 「表の形の誤り」が出たら直して、もう一度回す（抜け・消した行・出典の番号の打ち間違いなど）。直してよいのは表の形だけで、答えを変えて通すのではない
- 「人に聞くこと」（未決・矛盾）は直さずに残す。それを返すのがこのスキルの仕事
- 「古い」が出たら、`new` からやり直す

### 4. 保存して、返す
authz.md を docs リポジトリでコミットする（spec はこのスキルではコミットしない。authz.md だけ）:

    (cd docs && git add spec/<タスク名>-authz.md && git commit -m "docs(<略号>): 認可の表（未決 <n>・矛盾 <n>）" -- spec/<タスク名>-authz.md)

`/ac-matrix` と `/ac-model` は並べて回るので、もう片方のコミットとぶつかって `index.lock` があると言われることがある。そのときは数秒おいて同じコマンドをもう一度打つ（3 回まで）。`index.lock` を消さない（もう片方のコミットを壊す）。
`-- <パス>` を付けてコミットするので、もう片方のファイルがこのコミットに混ざることは無い。

出力には、`scripts/ac-matrix.sh check` の出力をそのまま（要約しない）載せ、最後の行に「次は `/spec <タスク名>`（認可の表の結果を見る）」と書いて止まる。
人には聞かない。未決や矛盾をどう決めるかは、spec の会話が人に聞く。

## オーケストレーターから呼ばれたとき
プロンプトが「orchestrate から:」で始まるときは、`/orchestrate` のサブエージェントとして動いている。進め方は同じ。人には聞かないので「## 質問」は返さない。
出力の最後の「次は `/spec <タスク名>`」の行を、orchestrate が読んで spec に戻る。

## よくある言い訳
| 言い訳 | 反論 |
|---|---|
| 未ログインができないのは当たり前だから、できないで埋める | 当たり前でも AC に無ければ、accept-test は確かめる根拠を持てない。未決にして AC に書いてもらう |
| 決定ログに答えが書いてあるから、そこから埋める | 決定ログは読まない。AC に無い答えは、build も審判も見ない。AC に書き足してもらうのが筋 |
| 未決が多いと spec の人が困るから、寄せて埋める | 寄せた答えは誰も決めていない答え。表が通っても、AC の抜けは残る |
| 前の表の答えを引き継げば早い | 前の表は前の AC から作った。AC が変わったなら、AC から読み直す |
| spec の会話でついでに埋める | 書いた本人が埋めると、AC と同じところが抜ける。別の会話で埋めるから意味がある |

## Red Flags
- AC の節のほか（spec の決定ログ・前提、plan、コード）を読んだ
- AC に書いていない答えを `できる`／`できない` にした。出典の AC がその答えを言っていない
- project.md の行を消した・名前を変えた
- 「表の形の誤り」を、答えを変えて消した
- 未決・矛盾を、人に聞かずに自分で決めた。AC や spec を書き換えた
- spec を書いた会話の中で動いた
