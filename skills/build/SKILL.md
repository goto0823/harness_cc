# build — approved な plan に沿って 1 ステップずつ回す

spec が「何を」、plan が「どう」を決めた。build はそれを **決めたとおりに** 作る。
新しい判断はしない。判断が要る場面に当たったら、自分で決めずに止まる。
止まるのは失敗ではない。黙って進んだ分は、あとで人が戻す分になる。
push と PR はしない。仕上げの `/ship` がやる。
ヘッドレスでは `git add -A`・`commit -a`・rebase・amend・stash・push・PR と、受け入れテスト（`docs/accept/`、`tests/Acceptance/`、`scripts/accept.sh`）の読み書きと実行を設定で禁止している。対話でもスキルのルールとして使わない。弾かれたら、別の書き方で回避せずに止まる。

## モード
- `/build <タスク名>`: todo の次の未完了ステップを 1 つ終えて止まる
- `/build auto <タスク名>`: 「止まる条件」に当たるまで、todo の順に全ステップを進める
- `/build fix <タスク名>`: 最新のレビューの「必須」の指摘を 1 件ずつ直す（下の「fix モード」）
- 承認は plan.md の `status: approved` で済んでいる。auto でも追加の確認を求めない
- タスク名が無いときは、`docs/plan/*-todo.md` のうち未完了のチェックがあり、対になる plan.md（小なら spec）が approved のものを探す。
  1 件なら「これを進める（推奨）／やめる」、複数なら候補を選択肢にして AskUserQuestion で聞く。0 件なら「進められる todo が無い」と止まる

## ヘッドレスでも動く
人が返答できない環境でも、入口の条件を満たせば auto で進む。止まる条件に当たったら「止まるときの出し方」の形で出力して終える。返答を待たない。

## 人に聞くとき
人が決めること・確かめること（未決事項、承認、「止まって聞く」もの）は、出力の文章に書くだけにしない。**AskUserQuestion で聞き、答えが返るまで次に進まない**。文章だけだと読み飛ばされ、そのまま進んでから戻ることになる。
- 1 回に 4 問まで。選択肢は 2〜4 個で、推奨があれば先頭に「（推奨）」を付けて置く。答えで次の質問が変わるなら分けて聞く
- コード・設計書・spec・plan で分かることは聞かない
- stash・破棄・force・push など、取り返しのつかない操作やこのスキルで禁じた操作を選択肢にしない
- 答えは todo.md の申し送りに書いてコミットする。`/clear` しても残り、次のスキルが読める
- ヘッドレス（`claude -p`）では聞けない。今までどおり出力に書いて止まる
- 「次は〜」（次に呼ぶスキルの案内）は質問にしない。別の会話で動かすものなので、出力の最後の 1 行に置く

## 進め方

### 0. 入口を確かめる（1 つでも満たさなければ止まる）
- plan.md が `status: approved`。`scale: 小` で plan が無いなら spec が `status: approved`
- spec が `status: approved`（中以上でも見る）で、todo.md の「spec への差し戻し」に `[ ]` の行が無い。
  あれば「spec の直しが先」と S-n を示し、「次は新しいセッションで `/spec <タスク名>`（差し戻し S-n を直す）」と案内して止まる。spec が `draft` のときも同じ
- `docs/accept/<タスク名>/accept.md` があるなら `status: approved`。`draft` なら「受け入れテストの承認を先に」と伝えて止まる。無ければそのまま始める（中身は読まない。status の行だけ見る）
- app のブランチ（app の cwd で打った `git branch --show-current`（`(cd docs && ...)` の中ではない）で見る）。<branch> は plan.md の `branch:`。小なら `feat/<タスク名>`。`<base>` は project.md の「PR の向き先」（app のベースブランチ）。docs のブランチは見ない（docs は docs のベースブランチのままが正しい。ship がそこから `ship/<タスク名>` を切る）
  - <branch> にいる: そのまま（並行作業で project.md の「並行作業」の始め方で入ったときもここ）
  - `<base>` にいて、app の `git status --porcelain` が空: **build が入る**。`git fetch origin` のあと、
    <branch> が手元か origin にあれば（`git branch --list <branch>`、`git branch -r --list origin/<branch>`）`git switch <branch>`、
    どちらにも無ければ `git switch -c <branch> origin/<base>`。入ったら、停止の出力の「ここまで」に「ブランチ <branch> を作った／に入った」と書く
  - `<base>` にいて、app に未コミットの変更がある: 止まって聞く（次の項目と同じ）。stash も破棄もしない
  - 別のブランチにいる: 別のタスクの途中かもしれないので、止まって聞く。切り替えない
- app と docs（`(cd docs && git status --porcelain)`）の両方で `git status --porcelain` が空。関係ない変更があれば止まって聞く。stash も破棄もしない。
  `docs/` は app とは別の git リポジトリ（project.md の「置き場」）で、spec・plan・todo・review はそちらに入る
- 何も変えていない状態で `scripts/check.sh --quick` が通る。通らなければ「着手前から落ちている」として止まる。直さない
- 小で todo が無い、または todo に「作業順」が無い（差し戻しの節だけの todo）ときは、spec の AC を番号順に 1 本 1 ステップにした `docs/plan/<タスク名>-todo.md` を作ってから始める（最後に CP を 1 つと仕上げを置く。plan.md は作らない）。形は plan の todo.md と同じ。「spec への差し戻し」は、既にある行を残し、無ければ「なし」で置く。
  「画面の確認」も plan と同じ基準で作る: 画面に関わる AC（Then に画面の表示・操作があるもの、または「完了の見た目」に関わるもの）の行をすべて「AC-XXX-n: 未確認: <実機で見ること>」で

### 1. 読む（この順で）
1. plan.md の「使い方」と「外の約束」（新しい URL・項目名・画面に渡すデータの名前・エラーコード・列は、ここにあるものだけを使う）。小で plan が無ければ、spec の「次のセッションが最初に読むもの」
2. todo.md の「申し送り」の最新の行
3. todo.md の次の未完了ステップと、その中身（plan.md の「作業順」。分割したものは todo.md の「実装中に変えたステップ」）
4. そのステップの対象 AC（spec）と、「作る順」に書かれたファイル

### 2. 「先に聞く」の印
ステップに **先に聞く** の印があれば、そのステップに入る前に止まる。印の内容（migration が要る、など）を示し、AskUserQuestion で「進める／止める」を聞く。
進めるなら、答えを申し送りに「先に聞く 承認: P-n <内容>（日付）」と書いて、そのステップに入る（ac-review がこの記録を見る）。止めるなら 6 の形で止まる。
auto でも聞く。ヘッドレスでは聞けないので 6 の形で止まる。印が無いステップでも、「止まる条件」に当たったら止まる。

### 3. 1 ステップの回し方（順番を変えない）
1. **red**: plan の「テスト一覧」に書かれたテストを書く。実行して落ちることを確かめる
   - 落ちる理由が「まだ実装が無いから」であることを確かめる。構文エラー・import 漏れ・設定ミスで落ちているなら、それを直してから red を確かめ直す
   - 書いた時点で通ってしまったら止まる。テストが AC を確かめていないか、もう実装済みかのどちらかで、どちらも判断が要る
2. **green**: テストを通す最小のコードを書く。作る順は plan の「作る順」に従う
   - green の間はテストを書き換えない。red に戻って直してよいのは **テストのミス**（書き間違い、テストデータの準備の誤り）だけで、直した理由を申し送りに書く
   - テストが確かめている中身（期待値、AC の意味）を変えたくなったら、直さず止まる
   - 「触るファイル」に無いファイルを少し触ったら（既存の呼び出し元の引数を合わせる、型を足す）、申し送りに書く。新しいファイルを作る、または振る舞いが変わる変更が要るなら止まる
3. **確認**: plan の「確認」に書かれたコマンド → `scripts/check.sh --quick`
   - 自動で回せない確認（実機で見る、画面で目視する）は、この場ではやらない。「画面の確認」のその AC の行（plan が「未確認」で作ってある）の <内容> を、確かめることが具体になった分だけ書き換える。行が無い画面の AC を見つけたときだけ「AC-XXX-n: 未確認: <内容>」で作る。行は AC ごとに 1 つ。仕上げの `/ui-check` が消化する
   - 落ちたらコードを直してから回し直す。コードを変えずに同じコマンドを回し直さない
4. **コミット**（確認がすべて通ったときだけ）
   - そのステップで触ったファイルだけを `git add <path>` する。`git add -A` と `git add .` は打たない
   - todo.md の該当ステップにチェックを付け、docs リポジトリで同じ P-n を付けてコミットする（`(cd docs && git add plan/<タスク名>-todo.md && git commit -m "docs(<略号>): P-n todo")`）。docs は app とは別の git リポジトリなので、app のコミットには入らない
   - app のコミットを revert したら、docs の todo の該当チェックも外して、docs で別にコミットする（`(cd docs && git add plan/<タスク名>-todo.md && git commit -m "docs(<略号>): P-n todo を戻す")`）
   - docs の git 操作は `(cd docs && git ...)` の形で書く。`-C docs` を付けた git は deny のパターンに一致しないので使わない（deny はサブシェルの中にも効く）
   - メッセージは `<type>(<略号>): P-n <見出し> (AC-XXX-n)`。type は変更の性質で選ぶ（feat / fix / test / refactor）。テストしか書かないステップは test
5. 次のステップへ。`/build` なら、ここで止まる。止まる条件ではないが、出し方は 6 と同じ（理由: 「1 ステップ完了」）

範囲外で気づいたこと（別のバグ、古いコメント、設計書とのずれ）は、触らずに申し送りに「気づいたが触っていない: <内容>」と書く。

### 4. チェックポイント（CP-n）
全体の `scripts/check.sh` を回す。通れば todo にチェックを付け、そのチェックは次のステップのコミットに含める。
落ちたら直す。直したら `fix(<略号>): CP-n <直したこと>` で、CP だけのコミットを切る。直せなければ止まる。

### 5. 止まる条件（auto でもここで止まる）
- 「先に聞く」の印があるステップに入る
- **（spec のこと）** spec に書いていない判断が要る。spec と plan が食い違う。どちらも自分で直さない
  - 人が裁定して「spec を直して進めて」と言っても、build のセッションでは直さない。裁定を申し送りに書いて止まり、「次は新しいセッションで `/spec <タスク名>`（決定ログ → draft → 再承認。受け入れテストがあれば `/accept-test` も）。承認後に `/build <タスク名>` で再開」と案内する。
    build が直すと draft と再承認が抜け、受け入れテストが古い AC のまま残る
- 「外の約束」に無い新しい URL・項目名・画面に渡すデータの名前・エラーコード・列を決めないと作れない（accept-test が同じ約束でテストを書いているので、ここで決めると落ちる）
- **（spec のこと）** テストが確かめている中身（期待値、AC の意味）を変えないと green にならない
- 同じテストを 3 回直しても通らない。ビルドが壊れて直し方が明らかでない
- red で、書いた時点でテストが通ってしまった。テストが AC の Then どおりなら（AC が既に満たされている）**（spec のこと）**。テストが Then を確かめていないなら、テストのミスとして red に戻って直す
- 元に戻せない作業が要る（データを消す migration、権限の変更、デプロイ、秘密情報や .env に触る、`git revert` で戻せないもの）
- plan の「触るファイル」に無いファイルを新しく作る、または振る舞いが変わる変更が要る
- 確認のコマンドが環境の問題で動かない（DB が落ちている、生成物が無い）。環境は直さない
- 次が仕上げのステップ。仕上げ（check.sh 全体 → /ui-check → /ac-review → /ship）は人と別セッションの仕事で、build は入らない

**（spec のこと）** の印で止まるときは、止まる前に todo.md の「spec への差し戻し」に 1 行足す（6 の申し送りと同じコミットに入れる）:
`- [ ] S-n <spec に足りない判断・食い違い・おかしい AC。人の裁定があればそれも>（AC-XXX-n、P-n で発覚）`。番号は todo の中で続きから振る。
これが新しいセッションの `/spec` への伝言になる。停止の出力だけだと、別のセッションには届かない

### 6. 止まるときの出し方（毎回この形）
対話で「判断してほしいこと」があるなら、出力の前に AskUserQuestion で聞き、答えを申し送りに書く。
答えで進められるもの（入口の「止まって聞く」で、切り替えずに済む答え。先に聞くの承認）は進める。
spec のこと（5 の印）は、答えを人の裁定として S-n に書いて止まる。build は spec を直さない。
todo.md の「申し送り」に 1 行足してから、次の形で出力して終える。コードもテストも、この後は触らない。
未コミットの変更があっても捨てない。そのまま残して一覧に書く。

```
## build 停止: <タスク名>
- 理由: <止まる条件のどれか。1 行>
- 位置: <P-n / CP-n>（todo の次の未完了）
- ここまで: <このセッションで終えたステップと、そのコミットのハッシュ>
- 未コミット: <あり（ファイル一覧）／なし>
- 未確認: <「画面の確認」で未確認のままの AC と内容。無ければ「なし」>
- 判断してほしいこと: <選択肢を付ける。無ければ「なし」>
- 次: 再開なら `/build <タスク名>` か `/build auto <タスク名>`（このセッションでも新しいセッションでもよい）。仕上げの前なら 7 の案内、fix を全部直したときは fix の「止まる」の案内に置き換える
```

止まった理由が 5 の **（spec のこと）** の印のものなら、「次」は「新しいセッションで `/spec <タスク名>`（todo の差し戻し S-n を直す）。spec の再承認後、案内に従って `/plan`・`/accept-test` を挟んでから `/build <タスク名>` で再開」にする。

申し送りの 1 行は `| 日付 | P-n まで（最後のコミット） | 次: P-m | <止まった理由、触っていないこと、気づいたこと> |`。未確認は表には書かず、「画面の確認」の AC の行に置く。

理由が「着手前から落ちている」「同じテストを 3 回直しても通らない」「ビルドが壊れて直し方が明らかでない」のどれかなら、「次」は「新しいセッションで `/debug <タスク名>`（原因を調べる。直したら `/build <タスク名>` で再開）」にする。build は原因を探さない。

### 7. 仕上げの前まで終えたとき
6 と同じ形で出す。理由は「仕上げの前」。「判断してほしいこと」に、人がやる順を書く:
`scripts/check.sh`（全体）→ 新しいセッションで `/ui-check <タスク名>` → 別セッション（build と別のモデル）で `/ac-review <タスク名>` → pass なら新しいセッションで `/ship <タスク名>`。
「画面の確認」に「未確認」の行が 1 つでもあれば、「判断してほしいこと」の先頭に「次は新しいセッションで `/ui-check <タスク名>`（app は project.md の「app の起動と URL」のとおり人が上げてから）」と書く。
未確認が無く、画面に関わる AC も無ければ「`/ui-check` は不要。次は別セッション（build と別のモデル）で `/ac-review <タスク名>`」と書く。

## fix モード（`/build fix <タスク名>`）
レビューは別のセッションが書く。build はその指摘を直すだけで、指摘の当否を判断しない。

### 入口
- 0 の条件に加えて、`docs/review/<タスク名>-review-<n>.md` がある。`n` が最大のものを読む。無ければ止まる
- レビューの形は次のとおり。この形になっていなければ、直さず止まる
  - 先頭に `result: pass` か `result: fail`。2 行目に「採点が成り立たない: …」が来ることがある（下の止まる条件）
  - 指摘ごとに ID `R<n>-<番号>`、重さ（必須 / 任意）、根拠（AC か `ファイル:行`、ui-check 由来ならスクショのパス。パスの基準と開き方は project.md の「スクショ」）、何がおかしいか
- `result: pass` なら直すものは無い。7 と同じ形で「レビュー pass」と出して止まる

### 直し方
- 直すのは **必須** だけ。**任意** は直さず、申し送りに「任意（未対応）: R<n>-<番号> <内容>」と書く
- 必須を ID の順に 1 件ずつ。振る舞いの誤りなら、それを再現するテストを先に足して red を見る（3 と同じ）。規約違反・簡素化の指摘はテストを足さずに直す
- 1 指摘 = 1 コミット。触ったファイルだけを add する。メッセージは `fix(<略号>): R<n>-<番号> <直したこと>`
- **ui-check 由来の指摘**（根拠がスクショのパス）を直したら、「画面の確認」のその AC の行を「AC-XXX-n: 未確認: <内容>（R<n>-<番号> を直した。再確認）」に書き換える。行は足さない。
  ロールが並んでいる行は直したロールの部分だけを書き換え、行の頭は一番悪い状態にする（期待と違う ＞ 未確認 ＞ 確認済み。ui-check の書き方）。
  書き換えないと、次の ac-review が古い「期待と違う」をまた必須にして、fix が「前回と同じ」で止まる。
  todo は docs リポジトリで別にコミットする（`(cd docs && git add plan/<タスク名>-todo.md && git commit -m "docs(<略号>): R<n>-<番号> 再確認待ち")`）
- 各コミットの前に `scripts/check.sh --quick`。全部直したら全体の `scripts/check.sh`

### 止まる（6 の形で）
- レビューの 2 行目に「採点が成り立たない:」の行がある（差分に受け入れテストの写しがある）。直さず止まる。その回の採点は無効で、人が確かめる
- 直すのに spec か plan と違うことが要る。直さず止まる。spec と違うことなら **（spec のこと）** として、5 と同じように S-n を書いてから止まる（P-n の代わりに `R<n>-<番号> の fix で発覚`）
- **必須**の指摘が前の回と同じ（レビューに「前回 R<n-1>-<k> と同じ（未修正）」とある）。直さず止まる。直し方か前提のどちらかが間違っている。未対応の任意はレビューの「参考」に回るだけなので、止まらない
- 3 回直しても指摘のテストが通らない
- 全部直したら、7 と同じ形で止まる。「判断してほしいこと」は「次は別セッション（build と別のモデル）で `/ac-review <タスク名>`（再レビュー）」。
  画面に関わる指摘（根拠がスクショのパス）を直していたら、先頭に「次は新しいセッションで `/ui-check <タスク名> <直した AC>`（app は人が上げてから）→ 別セッション（build と別のモデル）で `/ac-review <タスク名>`」と書く。
  ui-check を飛ばして `/ac-review` に行くと、「未確認（再確認）」が参考に残るだけで、直ったことは誰も確かめていない

## 書き方

### テスト
- ケース名に AC 番号を入れる（plan の「テスト一覧」のとおり）。1 つのテストが複数の AC を担うときは全部書く
- 置き場と書き方は project.md の「テストの書き方の決まり」。plan に無いテストを足したくなったら、todo.md の「実装中に変えたステップ」に書いてから足す

### コミット
```
feat(rcr): P-1 キャンセルで予約の状態がキャンセル済みになる (AC-RCR-1, AC-RCR-2)
test(rcr): P-10 キャンセルが他の予約に触れないのを番人で固定する (AC-RCR-14, AC-RCR-16)
fix(rcr): CP-1 ReservationListTest の並び順を直す
fix(rcr): R1-3 空白だけの理由を trim してから判定する
```

## よくある言い訳
| 言い訳 | 反論 |
|---|---|
| テストを先に書いても結局同じコードになる | red を見ないと、テストが AC を測っているか分からない。書いた時点で通るテストは番人にならない |
| ついでに隣のファイルも直しておく | 触るファイルは plan にある。新しいファイルや振る舞いの変更は止まる条件。1 ステップ 1 コミットが崩れる |
| この判断は小さいから spec を見なくていい | 小さい判断の積み重ねが spec と実装のずれになる。spec に無ければ止まる |
| テストが通らないので期待値を直す | 期待値は AC の写し。実装に合わせて変えた時点でテストは何も守らない。直してよいのはテストのミスだけ |
| auto なのだから止まらず進んだほうが速い | 止まる条件は速さより先。止まらずに進んだ分は、人が後で戻す分 |

## Red Flags
- red で落ちるのを確かめずに実装を書いた
- テストを弱めた・消した・skip した・期待値を実装に合わせて書き換えた
- green の間にテストのミス以外を書き換えた
- `git add -A` / `git add .` を打った。todo のチェックを docs リポジトリでコミットしなかった
- push、PR、force push、rebase など、履歴を書き換える・外に出す操作をした
- 入口で `<base>` と <branch> 以外のブランチから切り替えた。未コミットの変更があるのに切り替えた
- 禁止されたコマンドを、別の書き方で回避しようとした（`git add -A` を `git add .` に、`--force` を `+refspec` に、など）
- 自分の実装をレビューして合格扱いにした
- コードを変えていないのに同じ確認コマンドを繰り返した
- 「先に聞く」の印を越えて進んだ
- spec か plan を書き換えた（人に言われて直したのも含む）
- spec のことで止まったのに、todo の「spec への差し戻し」に S-n を書かなかった
- 受け入れテスト（`docs/accept/`、`tests/Acceptance/`）を読んだ・回した。`scripts/accept.sh` を打った
- docs で todo の `add` / `commit` 以外の git 操作（`show`、`log -p`、`diff`）をした
- 「外の約束」に無い URL・項目名・画面に渡すデータの名前・列を決めた
- plan の「触るファイル」に無いファイルを新しく作った、または振る舞いを変えた
- 止まるときに申し送りを書かなかった。6 の形で出さなかった。未コミットの変更を捨てた
- 仕上げのステップに入った
- fix で「任意」を直した。前の回と同じ必須を黙って直した
- ui-check 由来の指摘を直したのに、「画面の確認」の行を「未確認（再確認）」に書き換えなかった。直した AC の `/ui-check` を案内しなかった

## 確認項目（コミットの前に、毎ステップ）
- red で落ちるのを見たか。落ちた理由は実装の不在か
- green でテストに触ったなら、それはテストのミスの修正だけか
- plan の「確認」のコマンドと `scripts/check.sh --quick` が通ったか
- add したのは、このステップで触ったファイルだけか。todo.md は docs リポジトリでコミットしたか
- todo のチェックを付けたか。メッセージに P-n と AC（fix なら R<n>-<番号>）があるか
- 「触るファイル」に無いファイルに触ったなら、申し送りに書いたか
- 使った URL・項目名・画面に渡すデータの名前・エラーコード・列は、「外の約束」か既存のものだけか
- 自動で回せなかった確認を「画面の確認」の AC の行（未確認）に書いたか。行を足していないか（無い画面の AC を見つけたときだけ作る）
