# orchestrate — スキルを順に回し、人には質問だけ出す

spec・plan・accept-test・build・ui-check・ac-review・deliver は、それぞれ別の会話で動かす前提で作ってある。
人がやっていた「`/clear` → 次のスキルを打つ → ペインを行き来する」を、このスキルが代わりにやる。
**このスキルは判断しない。** 次に何を回すかはファイルの状態と各スキルの「次」の行で決め、人の判断が要るものは全部質問にする。
中身（コード、テスト、受け入れテスト、レビューの当否）を読むと、作る側と審判の両方の考えを持つことになり、会話を分けた意味が無くなる。

## 人が応答できない環境では使わない
ヘッドレス（`claude -p`）では使わない。質問に答える人がいないと、承認も deliver の「出す」も通らない。

## 設定（変えるときはここだけ直す）
- 作る側のモデル（spec・plan・build・build fix・debug・deliver）: `opus`
- 審判側のモデル（accept-test・ui-check・ac-review）: `fable`。作る側と同じにしない
- fail → build fix → 再レビューの周回の上限: **2 周**。超えたら人に聞く
- build のログの置き場: app のルート直下の `local/orchestrate/<タスク名>/`（git 管理外。app の `.gitignore` に `/local/` を入れておく）。サンドボックスで書けなければ、書ける場所を人に聞く

## 回し方（どこで動かすか）
| スキル | 動かし方 | モデル |
|---|---|---|
| spec・plan・debug・deliver | サブエージェント（Agent ツール。`model` に作る側） | 作る側 |
| accept-test・ui-check・ac-review | サブエージェント（Agent ツール。`model` に審判側） | 審判側 |
| build・build fix | `claude -p` を Bash で（下の形） | 作る側 |

build だけ `claude -p` にするのは、受け入れテストを見えなくする deny（`Read(docs/accept/**)` など）が `headless-build.json` を読ませたときだけ効くから。
サブエージェントはこの会話の権限を引き継ぐので、deny が効かない。build は app のルートで起動する（README §3 のパスの基準）:

    claude -p "/build auto <タスク名>" --settings .claude/headless-build.json --model <作る側> > local/orchestrate/<タスク名>/build-<n>.log 2>&1

`fix` のときは `/build fix <タスク名>`。時間がかかるので Bash のバックグラウンド実行で回し、終わりの通知を待つ（`sleep` で待たない、ポーリングしない）。
終わったらログの「## build 停止」の節だけを読む。ログのほかの部分（コードの差分、テストの出力）は読まない。
`<n>` は 1 から。ディレクトリが無ければ先に `mkdir -p local/orchestrate/<タスク名>` を打つ。

サブエージェントへのプロンプトは、毎回この形にする（前の会話のことは書かない。引き継ぎはファイルでする）:

    orchestrate から: /<スキル> <タスク名>（<モード>）
    このスキルの「オーケストレーターから呼ばれたとき」に従う。AskUserQuestion は使わず、聞くことは「## 質問」の形で返して止まる。
    （ac-review のとき）scripts/check.sh は背景に回さず前景で待つ（timeout 600000）。終わったらレビューの作成とコミットまで進めて止まらない。
    （deliver のとき）app PR（docs の出し方が `PR` なら docs PR も）のタイトルと本文の全文を、要約せずにそのまま返す。
    （人の答えがあるときだけ）
    ## 人の答え
    - Q1: <問い> → <選ばれた答え。Other ならその文>（書く先: <ファイルと節>）

## 人に聞くとき
- サブエージェントが「## 質問」を返したら、**このスキルが AskUserQuestion で聞く**。問いと選択肢は返ってきたものをそのまま使う。書き換えない・選択肢を足さない・推奨を変えない
- 聞く前に、「## 質問」の Q の行より前（下書き・前提の表・対象外にしたもの）を、書き換えず・要約せずにそのまま画面に出す。サブエージェントの出力は人には見えず、問いだけ出すと人は何を根拠にした話か分からない。そのまま見せるだけなので、中身を読んで判断することにはならない
- AskUserQuestion のダイアログが開いている間は、上に出した表が見えないことがある。問いの文に付いている「（前提 #n）」は消さずに聞き、問いの末尾に「（下書き: <パス>）」だけ添える。問いの文そのものは変えない
- 前提の表や根拠が無いまま問いが返ってきても、自分で補わない。そのまま聞き、問いの前に「根拠の表が返ってこなかった。要るなら『根拠を出して』と答えてください」と添える（Other でそう答えられたら、同じスキルに「## 人の答え」でそのまま渡す）
- 1 回に 4 問まで。5 問以上返ってきたら分けて聞く
- 答えは、同じスキルの次のサブエージェントに「## 人の答え」で渡す。答えをファイルに書くのはサブエージェント（このスキルは書かない。例外は下の build の 2 つだけ）
- deliver の「出す」の答えは、新しいサブエージェントでなく、下書きを返した同じ deliver のエージェントに SendMessage で渡す（承認した本文がそのまま使われる）
- このスキルが自分から聞くのは、下の「止まって聞く」に書いたものだけ

## 進め方

### 0. 入口
- 人が `/orchestrate` を打った（このスキルは自分からは呼ばない）
- app のルートにいる（`docs/` と `.claude/headless-build.json` と `.claude/project.md` が見える）。違えば止まる
- 1 回に回すのは 1 タスク。同じ作業ツリーで別のタスクを回さない（docs の `git status` の入口が互いに止める）

### 1. 次を決める
直前に回したスキルの出力の**最後の「次」の行**が、名前の付いたスキル（`/plan`、`/build`、`/ui-check` など）を指していれば、それを次にする。
「次」の行が無い、再開したばかり、「次」が人の作業（app の起動、マージ、worktree の作成）のときは、ファイルの状態を上から見て、最初に当てはまるものにする:

| 状態（読むのはこの行だけ） | 次 |
|---|---|
| spec が無い、または `status: draft` | spec |
| todo の「spec への差し戻し」に `[ ]` | spec（差し戻し） |
| spec が中以上で、plan が無いか `status: draft` | plan |
| accept.md が無い（中以上）か `status: draft` | accept-test。小で accept.md が無いときは「作る（推奨は CLAUDE.md の「規模と進め方」による）／作らない」を聞く |
| todo の作業順で、仕上げより前に `[ ]` がある（todo が無い小も） | build（auto） |
| 仕上げより前がすべて `[x]` で、レビューがまだ無く、この会話で全体の `scripts/check.sh` を回していない | `scripts/check.sh` を Bash の前景で回す（timeout 600000。結果の最後の行だけ見る）。落ちたら debug |
| 「画面の確認」に頭が `未確認` か `期待と違う` の行がある | ui-check（入る前に「app は上がっていますか（project.md の「app の起動と URL」）」を聞く） |
| 最新のレビューが無い、または `head:` が `git rev-parse HEAD` と違う | ac-review |
| 最新のレビューが `result: fail` | build（fix）。AC の疑いで S-n が付いていれば spec（差し戻し） |
| 最新のレビューが `result: pass` で、まだ出していない（下の「出したかの見分け方」） | deliver |
| 出してある | 終わり（6） |

出したかの見分け方は、project.md の「docs の出し方」で分かれる（無い・`<ここに: …>` のままなら `PR`）:
- `PR`: docs に `deliver/<タスク名>` ブランチがあれば出してある（`(cd docs && git branch --list deliver/<タスク名>)`）。deliver の PR 番号は `deliver/<タスク名>` 側の todo にあり、docs のベースブランチには無い
- `直接 push`: todo の申し送りの deliver の行に app の PR の番号があれば出してある。deliver の行が「下書き」のままなら、deliver が下書きで止まっている（deliver を回す。deliver の入口が聞いて止まる）

読むのは、frontmatter の `status`・`scale`、project.md の「docs の出し方」、docs のブランチの一覧、todo の `- [ ]` / `- [x]` の行と「画面の確認」の行の頭と deliver の行、レビューの 1〜2 行目と `head:`、build のログの「## build 停止」の節だけ。

### 2. 回す
1 で決めたスキルを、「回し方」の表のとおりに動かす。返ってきた出力で分ける:
- 「## 質問」がある → 「人に聞くとき」のとおりに聞き、答えを付けて同じスキルをもう一度回す
- 「## 質問」が無く、止まった（入口で止まった、止まる条件に当たった） → 出力の「次」の行で 1 に戻る。「次」がスキルを指していなければ、止まって聞く
- 終わった（「次」がスキルを指している） → 1 に戻る

### 3. build のとき
build は `claude -p` なので人に聞けない。止まったら、ログの「## build 停止」の節を読んで分ける:
- 「判断してほしいこと」がある → このスキルが AskUserQuestion で聞く（問いと選択肢は書かれたものをそのまま使う）。答えは todo の申し送りに書いて docs でコミットしてから、build を回し直す:
  - 「先に聞く」の印への答え: `| 日付 | P-n の前 | 次: P-n | 先に聞く 承認: P-n <内容>（人の答え: <答え>） |`
  - それ以外: `| 日付 | <位置> | 次: <位置> | 人の判断: <問い> → <答え> |`
  - コミットは `(cd docs && git add plan/<タスク名>-todo.md && git commit -m "docs(<略号>): <位置> 人の判断")`
  - このスキルが todo に書くのはこの 2 つだけ。チェックや「画面の確認」には触らない
- 理由が spec のこと（S-n が書かれている）→ 人の答えがあれば上の形で todo に書いてコミットしてから、1 に戻る（spec の差し戻しになる。差し戻しは fix の周回に数えない）
- 理由が debug を指している（「次」が `/debug`）→ debug を回す
- 理由が「仕上げの前」→ 1 に戻る
- それ以外（環境の問題、元に戻せない作業が要る など）→ 止まって聞く

### 4. fix の周回
- build（fix）に入るたびに数える。上限（2 周）を超える fix に入る前に止まり、「もう 1 周回す／ここで止めて人が見る」を聞く
- build が「前回と同じ（未修正）」で止まったら、周回の数に関係なく止まって聞く
- 数は会話に持つだけでよい。再開したときは `docs/review/<タスク名>-review-*.md` の数から数え直す（fail のレビューの数 = fix に入った数）

### 5. 止まって聞く（このスキルが自分から聞くもの）
- 「次」がスキルを指していない、ファイルの状態が表のどれにも当てはまらない
- サブエージェントや `claude -p` が失敗した（エラーで終わった、出力が決まった形になっていない）。回し直さずに聞く
- ui-check の前に、app が上がっているか（project.md の「app の起動と URL」）
- 小で受け入れテストを作るか
- fix の周回の上限
- 選択肢は「回し直す／ここで止める」などに限る。stash・破棄・force・push を選択肢にしない

### 6. 終わったら
deliver が終わったら、deliver の出力（app PR の URL、`PR` なら docs PR の URL とマージの順番、`直接 push` なら push した docs のハッシュ）をそのまま出して止まる。
途中で止めたときは、どこまで回したか（スキルと結果の一覧）と、再開のコマンド `/orchestrate <タスク名>` を出して止まる。

## よくある言い訳
| 言い訳 | 反論 |
|---|---|
| build もサブエージェントで回したほうが早い | deny が効かず、受け入れテストを読めてしまう。審判の独立が崩れる |
| 中身を見たほうが次をうまく決められる | 見ると作る側と審判の両方の考えを持つ。次は状態と「次」の行だけで決まる |
| この質問は答えが明らかなので聞かずに進める | 決めるのは人。返ってきた質問は全部聞く |
| 選択肢を分かりやすく言い換える | 言い換えると、サブエージェントが書いた意味とずれる。そのまま出す |
| fix をもう 1 周回せば直りそう | 上限で止めて聞く。同じところを回り続けるのが一番高い |

## Red Flags
- コード・テスト・受け入れテスト・レビューの指摘の中身を読んだ。ログの「## build 停止」以外を読んだ
- build・build fix を `claude -p --settings .claude/headless-build.json` 以外で回した
- 審判側を作る側と同じモデルで回した
- サブエージェントの質問を聞かずに自分で答えた。問いや選択肢を書き換えた
- 「## 質問」の前提の表を画面に出さずに、問いだけを聞いた。表を要約した
- spec・plan・todo（申し送りの 2 つの行を除く）・レビューを自分で書き換えた
- 失敗したサブエージェントを、聞かずに回し直した
- fix の周回の上限を超えて回した
- 2 つのタスクを同じ作業ツリーで並べて回した

## 確認項目（スキルを 1 つ回すたびに）
- 回したスキル・モデル・動かし方が「回し方」の表のとおりか
- 返ってきた「## 質問」を全部聞いたか。聞く前に前提の表をそのまま出したか。答えを「## 人の答え」で渡したか
- 次を、「次」の行か状態の表で決めたか（中身で決めていないか）
