# plan — approved な spec から実装の手順書を書く

spec は「何を・なぜ」を凍結した文書。plan は「どう作るか」で、実装するセッションが迷わず進めるための
**作業の順番**と、**AC をテストに落とした一覧**を持つ。コードは書かない。骨格やシグネチャも書かない。
plan も人が承認して初めて成立する。承認前にテストやコードに手を付けると、plan が直ったときに捨てることになる。

出力は 2 ファイル。
- `docs/plan/<タスク名>-plan.md` — 使い方・方針・spec との照合・触るファイル・テスト一覧・作業順の中身。`status` を持ち、承認後は変えない
- `docs/plan/<タスク名>-todo.md` — 作業順のチェックボックス・チェックポイント・実装中に変えたステップ・申し送り。`status` は持たず、実装中に毎コミット動く

## 人が応答できない環境では approved にしない
ヘッドレス実行でも draft までは書ける（spec が approved なら材料は揃っている）。approved にするのは人の仕事。
spec とのずれが見つかったら推測で吸収せず、ずれを列挙してブロッカーとして止まる。

## 進め方

### 0. 入口を確かめる
- spec の `status` が `approved` か。`draft` なら「先に spec を確定して」と伝えて止まる。spec が無ければ `/spec` へ
- `scale: 小` なら「plan 無しで実装に入れる」と伝える。それでも頼まれたら書く
- **同じタスク名の `todo.md` に未完了のチェックが残っていないか。** 残っていたら、同じ作業の見直しなら plan と todo を更新する。
  別の作業なら止まって聞く（タスク名を変えるか、前の作業を閉じるか）。黙って上書きすると前の進捗が消える
- spec を読み直す。特に AC、境界、決定ログ、「次のセッションが最初に読むもの」

### 1. 読む
- `.claude/project.md`（検査、1 本だけ回す、外の約束の種類、並行作業）
- spec が指す設計書の節と関連コード。テストの置き場と書き方は project.md の「テストの書き方の決まり」
- 似たタスクの plan（`docs/plan/*-plan.md`。frontmatter が無いものは旧形式）で、順番の相場と粒度を知る
- AC に近い既存テスト（書き方を揃える。消す・書き換えるテストは spec の影響範囲に書いてあるはず）

### 2. spec と現実のずれを先に報告する
コードを読むと、spec の前提が古い、AC が今のコードでは成り立たない、境界に触らずには作れない、が見つかることがある。
**plan で吸収しない。** ずれを列挙して止まり、spec を直してもらう（決定ログに追記、`draft` に戻して再承認。spec スキルの 7）。
ずれが無ければ「照合: ずれなし」と一言添えて先へ進む。ここで止まるのはずれがあるときだけ。

### 3. 外の約束を決めて、AC をテストに落とす
- 先に plan.md の「外の約束」を埋める。AC を外から確かめるのに要る **新しい** URL・ルート名・HTTP メソッド・パラメータ名・画面に渡すデータの名前・エラーコード・列（と project.md の「外の約束の種類」に足したもの）を、番号付きで書く。
  既存のもの（もうあるルート、既存のエラーコード、既存の列）は書かない。ここに無いものは build も accept-test も決めない
- 約束を決めるのに spec に無い判断が要る（どのロールに許すか、エラーを何で返すか）なら、2 に戻って止まる
- ルート・権限・migration に触る約束は、4 で「先に聞く」の印を付ける材料になる
- **すべての AC に少なくとも 1 つのテスト**を対応づける。ファイル・クラス・ケース名まで書く。1 つのテストが複数の AC を担ってもよい
- 置き場はテストの書き方の決まり（project.md）のとおり
- テストで確かめられない AC が出たら、それは AC の問題。2 に戻って止まる

### 4. 作業順を切る
- **縦切り。** 1 ステップ = 1 つの振る舞い（AC）を、型から画面まで通す単位。終わった時点で、対象の AC が画面（または外から呼べる口）から確かめられる。近い AC を 1 ステップにまとめるのはよい
- 依存の順（型 → データの出し入れ → 処理の本体 → 入口（コントローラーなど）→ 画面）は、**ステップの中で作る順番**に使う。ステップを層で分けない
- 大きさの目安: 触る**本体**のファイル 5 つまで（テストと migration は数えない）、完了条件 3 つ以内。見出しに「と」が入ったら分ける
- **リスクの高いステップを前に置く。** 外部との境界、初めて触る部品、設計書の解釈が割れそうな所。後ろに置くと、崩れたときに積み上げた分が無駄になる
- ステップごとに書くこと: 対象 AC、作る順（触るファイル）、書くテスト、終わりの確認
- **「先に聞く」に当たるステップには印を付ける**（CLAUDE.md の 3 段階の「先に聞く」。例: migration、依存の追加、外部との契約、権限、`.env` や起動の設定）。
  実装セッションはその印で止まって聞く。印が無いと、止まらずに進む
- 1 ステップ = `scripts/check.sh --quick` が通る単位。2〜3 ステップごとに全体の `scripts/check.sh` を回す**チェックポイント**を todo に置く
- 最後のステップは固定: `scripts/check.sh`（全体）→ `/ui-check` → `/ac-review` → `/ship`（docs の更新と PR）。
  `/ui-check` は、画面に関わる AC と申し送り「画面の確認」の「未確認」を動いている app で確かめてスクショを残す（画面に関わる AC が無ければ飛ばす）
- todo.md の「画面の確認」に、画面に関わる AC（Then に画面の表示・操作があるもの、または「完了の見た目」に関わるもの）の行をすべて「AC-XXX-n: 未確認: <実機で見ること>」で作る。
  build・ui-check・fix はこの行を書き換えるだけで、行を足さない（行が無い画面の AC を見つけたときだけ作る）

### 5. 保存して、止まる
末尾の「確認項目」を通してから plan.md（`status: draft`）と todo.md を保存し、docs リポジトリでコミットしてから
（`(cd docs && git add plan/<タスク名>-plan.md plan/<タスク名>-todo.md && git commit -m "docs(<略号>): plan <タイトル>（draft）")`。docs は app とは別の git リポジトリ）、
要約（ステップ数、テスト数、外の約束の数、「先に聞く」の印の数、チェックポイントの位置、spec との照合結果）を出して承認を求める。
**そのターンはここで終える。** テストもコードも書かない。

### 6. 「確定」と言われたら
plan.md を `status: approved` にし、`updated` を更新して docs でコミットし
（`(cd docs && git add plan/<タスク名>-plan.md && git commit -m "docs(<略号>): plan <タイトル>（approved）")`）、次を伝えて止まる:
「受け入れテストを作るなら、次は別セッション（build と別のモデル）で `/accept-test <タスク名>`。その承認後に新しいセッションで `/build <タスク名>`。作らないなら、次は新しいセッションで `/build <タスク名>`。作るかどうかは CLAUDE.md の規模の表で決める（中以上は作る）。入り方は plan の冒頭の『使い方』」
`/build` に直接進むなら、build の入口（app が plan の `branch:` にいる・app と docs の `git status --porcelain` が空）も一緒に伝える。ブランチは `git switch -c <branch>` か、並行作業なら project.md の「並行作業」の始め方で人が入る。build は自分で切り替えない

### 7. 実装中に plan が変わるとき
- ステップの分割・順番の入れ替え・テストの追加は **todo.md の変更**として扱う。並べ替えは「作業順」で行い、
  分割・追加したステップの作る順・red・確認は todo.md の「実装中に変えたステップ」に書く（`P-3a` / `P-3b` のように増やす）。
  plan.md は承認時のまま直さない。理由は「申し送り」に書く
- AC・境界・スコープに関わる変更は **spec を先に直す**（spec スキルの 7）。plan はその後に追従させる

## 書き方

### 作業順の 1 ステップ（縦切り）
```
### P-2: 返金に失敗してもキャンセルは成立し、状態が返金エラーになる（AC-RCR-2）
**先に聞く:** 状態の列を足す migration が要る
- 作る順: `RefundState`（状態の型）→ 予約のリポジトリ → `CancelReservation` の失敗の分岐 → 予約の詳細画面のトースト
- red: `CancelReservationTest` に「決済が 503 でもキャンセルされ、状態は返金エラー」、詳細画面のテストに「エラーのトーストと再返金ボタン」
- 確認: project.md の「1 本だけ回す」で `CancelReservationTest` → 画面のテスト → `scripts/check.sh --quick`
```
本体のファイルは 4 つ（migration とテストは数えない）、完了条件は「キャンセルされる・状態が返金エラー・トーストが出る」の 3 つ、
見出しに「と」は無い。目安に収まっている。

### 1 ステップ = 1 コミット
- そのステップで触ったファイルだけを `git add <path>` で積む。`git add -A` はしない（生成物や隣のステップの変更を巻き込む）
- todo.md のチェックの更新は docs リポジトリで、同じ P-n を付けて別にコミットする（`(cd docs && git add plan/<タスク名>-todo.md && git commit -m "docs(<略号>): P-n todo")`）。docs は app とは別の git リポジトリなので、app のコミットには入らない。`-C docs` を付けた git は deny に一致しないので使わない
- メッセージは `<type>(<略号>): P-n <見出し> (AC-XXX-n)`。例: `feat(rcr): P-2 返金失敗時もキャンセルして返金エラーにする (AC-RCR-2)`
- チェックポイントで直すものが無ければコミットは無し。直したら `fix(rcr): CP-1 <直したこと>`

### 「使い方」ブロック
plan.md の冒頭に、実装するセッションへの約束を固定文で置く。実装セッションは plan スキルを読まないので、plan 自身に入り方を書く。

## 出力テンプレート
2 ファイルともこの構成で書く。節を増やすのはよいが、減らさない（空なら「なし」）。`status` は `draft` か `approved` の 2 値だけ。

### plan.md
```markdown
---
status: draft
spec: docs/spec/<タスク名>-spec.md
todo: docs/plan/<タスク名>-todo.md
branch: feat/<タスク名>
created: YYYY-MM-DD
updated: YYYY-MM-DD
---
# plan: <タイトル>

## 使い方（実装するセッションへ）
- spec（approved）・この plan・todo を読んでから始める。`docs/accept/<タスク名>/accept.md` があるなら approved になってから。並行作業なら project.md の「並行作業」の始め方で入る
- 新しい URL・項目名・画面に渡すデータの名前・列は、この plan の「外の約束」にあるものだけを使う。無いものが要ったら、決めずに止まって聞く（accept-test も同じ約束でテストを書いている）
- todo の順に 1 ステップずつ。1 ステップ = 1 コミット（触ったファイルだけを add）。todo のチェック更新は docs リポジトリで別にコミット（docs は app とは別の git リポジトリ）
- 各ステップの終わりに `scripts/check.sh --quick`。チェックポイント（CP-n）では全体の `scripts/check.sh`
- 実機で見る確認はステップの中ではやらず、todo の申し送り「画面の確認」の行（画面に関わる AC の分を plan が「未確認」で作ってある）に残す。行は書き換えるだけで足さない。行が無い画面の AC を見つけたときだけ「AC-XXX-n: 未確認: <内容>」で作る。仕上げの `/ui-check` が消化する
- **先に聞く** の印があるステップは、入る前に止まって聞く
- spec と違うことをしたくなったら、コードではなく spec を先に直す（決定ログ → draft → 再承認）
- ステップの分割・入れ替えは todo で行い、分けたステップの中身は todo の「実装中に変えたステップ」に書く。理由は申し送りに。plan は直さない
- セッションを閉じるときは todo の「申し送り」に、どこまで終わったか・次にやること・引っかかったことを書く

どう作るか。3〜5 行。設計書のどの型に乗るか。

- ずれ: なし
- 判断が要ったこと: なし
```

## よくある言い訳
| 言い訳 | 反論 |
|---|---|
| spec を読めば分かるから plan は要らない | 順番と AC→テストの対応は spec に無い。無いまま始めると実装から入り、テストが後回しになる |
| ついでに spec のここも直しておく | plan は spec を変えない。ずれは報告して止まる。直すのは spec の側 |
| 層ごとにまとめて作ったほうが効率的 | 層で切ると最後まで何も動かず、崩れたら全部やり直し。縦に通せば 1 ステップごとに AC が 1 つ動く |
| ステップを細かくすると面倒 | 1 ステップが大きいほど、壊れたまま進む時間が長くなる。本体 5 ファイル・3 条件・「と」で分ける |
| 骨格を plan に書いたほうが実装が速い | 速いのは最初だけ。骨格が主役になると AC と設計書から目が離れる |

## Red Flags
- plan にクラスの骨格・シグネチャ・実コードを書いた
- テストに対応していない AC がある
- 画面に関わる AC に「画面の確認」の行が無い
- 「外の約束」に無い新しい URL・項目名・画面に渡すデータの名前・列を「作る順」や「red」で使った
- 終わった時点で、対象の AC が画面（または外から呼べる口）から確かめられないステップがある（CP-n と仕上げは対象外）
- 触る本体のファイルが 6 つ以上のステップ、または見出しに「と」が入ったステップがある（テスト・migration は数えない）
- 「先に聞く」に当たるステップに印が無い
- 3 ステップ以上チェックポイントが無い
- 未完了の todo.md が残っているのに新しい todo.md を書いた
- plan のセッションで spec を書き換えた
- 保存と同じターンでテストやコードに触った
- 保存した plan.md・todo.md を docs でコミットせずに止まった（build は docs の `git status --porcelain` が空であることを入口にしている）

## 確認項目（承認を求める前に）
- すべての AC が「テスト一覧」で少なくとも 1 つのテストに対応しているか
- 画面に関わる AC（Then に画面の表示・操作、または「完了の見た目」）すべてに「画面の確認」の行があるか
- テストや画面から AC を確かめるのに要る新しい URL・項目名・画面に渡すデータの名前・エラーコード・列が、すべて「外の約束」に番号付きであるか。既存のものを書いていないか
- 各ステップが終わった時点で、対象の AC を画面か外から呼べる口から確かめられるか（CP-n と仕上げは除く）
- 各ステップが本体 5 ファイル・3 条件以内（テスト・migration は数えない）で、見出しに「と」が無いか
- リスクの高いステップが前にあるか
- 「先に聞く」に当たるステップすべてに印があるか
- 2〜3 ステップごとにチェックポイントがあるか
- docs でコミットしたか（`(cd docs && git status --porcelain)` に plan.md・todo.md が残っていないか）
- 「spec との照合」に「ずれ: なし」と書けるか（ずれがあれば止まっているはず）
- 同じタスク名の古い todo.md を確かめたか
- plan.md に「使い方」、todo.md に「実装中に変えたステップ」、「申し送り」の表、「画面の確認」があるか
