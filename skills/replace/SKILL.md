# replace — 設計書に沿って、振る舞いを変えずに 1 つの機能を作り直す

リファクタでいちばん高くつくのは、「ついでに」直して振る舞いが変わること、スコープが勝手に広がること。
replace は、**決めるまではターミナルで見せて話すだけ**にし、決まったことを md に書いてから、md に書いた範囲だけを直す。
書いた人と採点する人を分けるハーネスの決まりは、ここでは**人が md を決めること**で守る。md に無いことはしない。

## 人が応答できない環境では使わない
討論が本体なので、ヘッドレス（`claude -p`）では成立しない。呼ばれたら、2 の「見せる」までを出して「決めるには回答が必要」と止まる。md は書かない。コードも直さない。

## 呼び方
- `/replace <機能>`: 機能は PJ の言葉で。例: `/replace 予約の作成`、`/replace 会議室一覧の API`
- `/replace <機能名>` で `docs/replace/<機能名>-replace.md` が既にあれば、その `status:` から再開する（「再開するとき」）
- 引数が無いときは、どの機能かを聞く。設計書の「既知の違反」に載っているものがあれば、それを選択肢に出す

## 人に聞くとき
- 決めること（スコープ、論点、テストの扱い、改修してよいか）は AskUserQuestion で聞き、答えが返るまで次に進まない
- 1 回に 4 問まで。選択肢は 2〜4 個。推奨があれば先頭に「（推奨）」を付ける。答えで次が変わるなら分けて聞く
- コード・設計書で分かることは聞かない
- 取り返しのつかない操作（stash・破棄・force・push）を選択肢にしない

## 決めるまでの決まり
- **最終決定（4）までは、ファイルに書かない。** 読んだこと・改修案・論点は、すべてターミナルに「表示の形」で出す。md も、コードも、まだ書かない
- **振る舞いは変えない。** 読んでいて「これはバグでは？」と思っても、改修案に入れない。「見つけたこと」として出し、md にも「見つけたこと」として残すだけにする（直すのは `/debug` か `/spec`）
- **設計書が無い・規約が無いときも止まらない。** 討論で「こう直す」を決めてよい。ただし md の「根拠」に「設計書に書いていない（人が決めた）」と書く。設計書は直さない（規約にするなら `/arch`）

## 進め方

### 0. 入口を確かめる（1 つでも満たさなければ止まる）
- 作業ツリー: app と docs（`(cd docs && git status --porcelain)`）の両方で `git status --porcelain` を見る。docs の行のうち、ほかのタスク名・ほかの機能名が入る行と `pm/` の行は見ない。変更があれば止まって聞く。stash も破棄もしない
- ブランチ（app の cwd で `git branch --show-current`）: `refactor/<短い名前>` にいる。project.md の「PR の向き先」か HEAD が detached で、作業ツリーが空なら、`git fetch origin` のあと `git switch -c refactor/<短い名前> origin/<PR の向き先>` で入る（あれば `git switch refactor/<短い名前>`）。別のブランチにいるなら止まって聞く
- 頼まれたことが「新しい振る舞いが欲しい」なら replace ではない。`/spec` を案内して止まる。「壊れている」なら `/debug` を案内して止まる

### 1. 読む（数える。全部は読まない）
**数えるのは grep、読むのは要るファイルだけ。**
1. 設計書: project.md の「置き場」の「設計書」（無ければ `docs/design/`）の README → <機能> の層の architecture。<機能> が従うべき節と、§4-2 の既知の違反・§6 の移行ロードマップに <機能> が載っているかを見る。境界をまたぐなら contract も読む
2. <機能> の入口（ルート・画面・コマンド）から、通るファイルを辿る。各ファイルの行数を数える
3. 呼び出し元: <機能> の関数・クラスを使っている場所を grep で数える（触ると波及する範囲）
4. テスト: 2 のファイルを通るテストを探す。project.md の「1 本だけ回す」で回せる形にしておく
5. ディレクトリごとの CLAUDE.md の決まり

### 2. 見せる（ターミナルに出して止まる）
「表示の形」の **A（読んだこと）→ B（スコープ）→ C（改修案）→ D（論点）** の順に 1 回で出す。
- C の改修案は、**代表の 1〜2 ファイルだけ before / after の差分を全部**出す。残りは「同じ型で直す」ファイルの一覧と、変わる行の見込みの数だけにする（全部出すと読めず、討論できない）
- 差分は ```diff のブロックで出す。差分の前に、どの規約（設計書の節）に合わせたのかを 1 行で書く
- D の論点は、人が決めないと進めないことだけ。番号を付ける。テストの扱い（3 の表）も論点に入れる
- 出したら、まず「スコープはこれでいいか」を AskUserQuestion で聞く（はみ出し・足りないがあれば B から出し直す）

### 3. 討論する（1 論点ずつ）
- D の論点を 1 つずつ聞く。答えで改修案が変わったら、変わったファイルの差分だけを出し直す（全部は出し直さない）
- 人が別の案を出したら、その案の差分を出して、今の案と並べて比べる（「表示の形」の E）
- 決まったことは、毎回「表示の形」の F（決まったことの一覧）を出して積み上げる。人がいつでも全体を見られるようにする
- テストの扱いは、触るファイルごとに次から決める:

| 今の状態 | 選択肢 |
|---|---|
| 触るコードを通るテストがある | 改修の前に回して green を確かめる → 改修の各ステップのあとも green（推奨） |
| テストが無い・薄い | (a) 今の動きを固定するテスト（characterization test）を改修の前に足す（推奨）／ (b) 手で確かめる手順を md に書き、改修のあとにその手順で確かめる ／ (c) 確かめない（理由を md に書く） |

- (a) を選んだら、そのテストは改修の**前**のコードで green になることを確かめる（今の動きを固定するためのテストなので、今のコードで落ちたらテストの方が違う）
- 論点が全部決まったら、F を最後にもう一度出し、「これで md に書く」を聞く

### 4. 書く（最終決定）
- `docs/replace/<機能名>-replace.md` を「md のテンプレート」で書く。`status: approved`。討論で決まったことだけを書き、決まっていないことを書き足さない
- ステップは「1 ステップ = 1 コミット」で、テストの扱いのステップ（(a) のテストを足す）を先頭に置く
- `(cd docs && git add replace/<機能名>-replace.md && git commit -m "replace: <機能名> の改修を決める")`
- 「この md のとおりに改修していい？」を AskUserQuestion で聞く。「改修して」が返るまで、コードを直さない

### 5. 改修する（md の順に 1 ステップずつ）
各ステップで:
1. md のそのステップに書いたファイルだけを直す
2. `scripts/check.sh --quick` を回す。そのステップに関わるテストを project.md の「1 本だけ回す」で回す
3. green なら app でコミットする（`refactor: <機能名> <ステップの内容>`）。md の「進み具合」のそのステップに `done` とコミットのハッシュを書き、docs でコミットする
4. ステップの区切りで、何を直したかを 2〜3 行でターミナルに出す

**止まる（直さずに AskUserQuestion で聞く）:**
- md に無いファイルを触らないと進めない
- テストが落ちて、改修で振る舞いが変わったように見える（テストを書き換えて通さない）
- md の改修案のとおりに書けない（型が合わない、呼び出し元が想定より多い など）
- 同じ失敗を 3 回直しても通らない

止まったら、md の「進み具合」に止まった理由を書いて docs でコミットしてから聞く。答えで md を変えるなら、変える差分をターミナルに出して確かめてから md を直す（「改修中に決め直したこと」に残す）。

### 6. 終わる
- 全ステップのあと `scripts/check.sh`（全体）を回す
- テストの扱いが (b) のファイルは、md の手順で確かめ、結果を md に書く
- md を `status: done` にして、「結果」を書き、docs でコミットする
- ターミナルに「表示の形」の G（終わりの報告）を出す
- push・PR はしない。出すなら人が決める。設計書の既知の違反から消すなら `/arch <層>` を案内する（replace は設計書を直さない）

## 再開するとき
md の `status:` で決める。
- `approved`（改修の前）: md を読み、「この md のとおりに改修していい？」を聞くところから
- `in-progress`: 「進み具合」の最後の `done` の次のステップから。作業ツリーに未コミットの変更があれば、その一覧を出して止まって聞く
- `done`: 終わっている。G を出し直すだけ

## 表示の形
ターミナルに出すときの形。見出しと区切りをそろえ、表と ```diff を使う。長い説明の段落を書かない。

````
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
 replace: <機能名>
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

## A. 読んだこと
| 項目 | 内容 | 根拠 |
|---|---|---|
| 従う規約 | <設計書の節と要点> | docs/design/<file>.md §3-2 |
| 既知の違反 | 載っている / 載っていない | §4-2 |
| 入口 | <ルート・画面> | routes/web.php:42 |
| 呼び出し元 | <n> か所 | grep の結果 |
| テスト | ある <n> 本 / 無い | tests/... |

## B. スコープ
### 触る
| # | ファイル | 行数 | 何をするか | テスト |
|---|---|---|---|---|
| 1 | app/Http/Controllers/ReservationController.php | 180 | DB 直接 → UseCase に移す | ある |
| 2 | app/UseCases/CreateReservation.php | 新規 | 作る | 無い |
### 触らない（理由つき）
- app/Models/Reservation.php（規約に合っている）

## C. 改修案
### C-1. ReservationController.php（§3-2 Controller は DB に触らない）
```diff
- $room = DB::table('rooms')->find($id);
+ $room = $this->createReservation->handle($input);
```
### C-2. 同じ型で直すもの
| ファイル | 変わる行の見込み |
|---|---|

## D. 論点（決めること）
| # | 論点 | 案 | 推奨 |
|---|---|---|---|
| 1 | 戻り値の形 | DTO / 配列 | DTO（§3-3） |
| 2 | テストが無い #2 の扱い | (a) / (b) / (c) | (a) |

## 見つけたこと（今回は直さない）
- <バグかもしれないこと>（file:line）
````

- **E. 案の比べ**: 同じ箇所の「今の案」と「人の案」を ```diff で並べ、その下に 違い・良い点・気になる点 の表を出す
- **F. 決まったことの一覧**: `| # | 決めたこと | 理由 |` の表。決まっていない論点は `| 2 | （未決） | |` として残す
- **G. 終わりの報告**: ステップごとの `| # | 内容 | コミット | 確認 |` の表、`check.sh` の結果、「見つけたこと」、次の案内（`/arch <層>` で既知の違反を見直す など）

## md のテンプレート
節を減らさない（空なら「なし」）。

```markdown
# replace: <機能名>
date: YYYY-MM-DD
branch: refactor/<短い名前>
status: approved | in-progress | done

## 目的
<何を、どの規約に合わせて作り直すか。1〜3 行>

## 根拠
- <設計書の節>（設計書に無いなら「設計書に書いていない（人が決めた）」）

## スコープ
### 触る
| # | ファイル | 何をするか | テストの扱い |
|---|---|---|---|
### 触らない
- <ファイル>（<理由>）

## 決めたこと
| # | 決めたこと | 理由 |
|---|---|---|

## 改修の後の形
<代表のファイルの after のコード、または型の説明>

## テストの扱い
| ファイル | 今 | 扱い | 手で確かめる手順（(b) のとき） |
|---|---|---|---|

## ステップ（1 ステップ = 1 コミット）
1. <内容>（ファイル: …）
2. …

## 進み具合
| # | 状態 | コミット | メモ |
|---|---|---|---|

## 改修中に決め直したこと
なし

## 見つけたこと（今回は直さない）
なし

## 結果
<check.sh の結果、(b) の確認の結果>
```

## よくある間違い
| 間違い | どうするか |
|---|---|
| 討論の途中で md を書き始める | 最終決定までターミナルだけ。書くのは 4 |
| 全ファイルの差分を出す | 代表の 1〜2 ファイルだけ。残りは一覧と行数 |
| 改修中に「ついでに」直す | md に無いことはしない。止まって聞く |
| バグを見つけて直す | 「見つけたこと」に書くだけ。振る舞いは変えない |
| テストが落ちたのでテストを直す | テストを書き換えて通さない。振る舞いが変わった疑いとして止まる |
| characterization test を改修の後で書く | 改修の前のコードで green を確かめてから改修する |
| 設計書を直す | replace は設計書を直さない。`/arch` を案内する |
