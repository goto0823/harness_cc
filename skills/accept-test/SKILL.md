# accept-test — spec の AC から、build が触れない受け入れテストを書く

spec が「何を」を決めた。accept-test はそれを **外から確かめるテスト** に落とし、実装が無い今の時点で「落ちる」ことを見てから、人に承認してもらう。
build はこのテストを読まない・書き換えない。採点（ac-review）のときに回す。build が「テストに合わせた実装」をできないようにするための、独立した審判。
build とは別のセッション・別のモデル（build が Opus なら Fable など）で動かす。同じ文脈で書くと、実装の都合がテストに漏れる。

## いつ動かすか
- 中以上: spec が approved → plan が approved → **accept-test** → build
- 小: spec が approved → **accept-test** → build（plan は無い）
- この時点では新しい振る舞いの実装が無い。だから実装に合わせたテストにはなりようがない。build が 1 ステップでも進んだ後には書かない

## 一番大事なルール: 頼ってよいのは「外の約束」だけ
build はこのテストを見ない。テストが勝手に決めた URL・パラメータ名・画面に渡すデータの名前・文言に頼ると、build が別の正しい作り方をしたときに落ちる。build のせいではないのに fail になる。

**使ってよいもの（出典を書けるものだけ）**
- spec に書かれたもの: AC の Given / When / Then、画面の文言、エラーの見え方、ロールごとの可否、「変えないこと」
- plan の「外の約束」に書かれたもの: 新しい URL・ルート名・HTTP メソッド・パラメータ名・画面に渡すデータの名前・エラーコード・新しい列（plan.md にこの節を置く。build もここを読む）
- 既存のコードにあるもの: 今あるルート、テストデータの作り方（factory・seed）、テストの土台とヘルパー（project.md の「受け入れテスト」）、既存のエラーコード、文言のキー
- 既存のテストの書き方（project.md の「テストの書き方の決まり」、近い既存のテスト）

**文書の読み方も約束のうち**: 成果物が文書（調査レポート・設計書）のとき、節の見出しの形、表の列、どのコードブロックをコマンドとして回すか、数の書き方（小数・%・桁区切り）も、spec に無ければテストで決めない。
決めないと書けないなら、止まって「spec の AC に書いてほしい」と伝える（例: 「コマンドは ```` ```bash ```` のブロックに置く。出力の写しは ```` ```text ````」）。
テストだけが決めた読み方は build から見えない。build がふつうの書き方をしただけで落ち、build のせいではない fail になる

**使わないもの**
- クラス名・メソッド名・UseCase・Repository・内部の構造。外から振る舞いを確かめる（HTTP などの外から呼べる口を叩くテスト）
- plan の「作る順」「触るファイル」「テスト一覧」。読まない。読むと内部の構造に引きずられる
- 自分で決めた約束。新しい URL・項目名・画面に渡すデータの名前が要るのに spec にも plan にも無ければ、**決めずに止まる**。「plan（または spec）に次の約束を足してほしい」として、要るものを列挙して返す

## 呼び方
- `/accept-test <タスク名>`: spec の AC 全部に受け入れテストを書く（draft）
- `/accept-test <タスク名> AC-XXX-n`: その AC だけ足す・直す（draft のとき）
- 「確定」と言われたら approved にする（6）

## 人に聞くとき
人が決めること・確かめること（未決事項、承認、「止まって聞く」もの）は、出力の文章に書くだけにしない。**AskUserQuestion で聞き、答えが返るまで次に進まない**。文章だけだと読み飛ばされ、そのまま進んでから戻ることになる。
- 1 回に 4 問まで。選択肢は 2〜4 個で、推奨があれば先頭に「（推奨）」を付けて置く。答えで次の質問が変わるなら分けて聞く
- コード・設計書・spec・plan で分かることは聞かない
- stash・破棄・force・push など、取り返しのつかない操作やこのスキルで禁じた操作を選択肢にしない
- 答えは accept.md（承認は `status`、それ以外は「変更ログ」）に書いてコミットする。`/clear` しても残り、次のスキルが読める
- ヘッドレス（`claude -p`）では聞けない。今までどおり出力に書いて止まる
- 「次は〜」（次に呼ぶスキルの案内）は質問にしない。別の会話で動かすものなので、出力の最後の 1 行に置く

## 進め方

### 0. 入口を確かめる（1 つでも満たさなければ止まる）
- spec が `status: approved`。中以上なら plan も `status: approved` で、plan.md に「外の約束」の節がある（無ければ「plan に外の約束の節を足して」と伝えて止まる）
- todo.md があれば、「spec への差し戻し」に `[ ]` の行が無い。あれば「先に `/spec <タスク名>` で S-n を直して」と伝えて止まる
- build が始まっていない: `docs/plan/<タスク名>-todo.md` の作業順に `[x]` が無い（todo が無ければそれでよい）。app のブランチがあるなら `git log origin/<base>..HEAD`（`<base>` は project.md の「PR の向き先」）が空
- `docs/accept/<タスク名>/accept.md` が `approved` でない。`draft` があれば続きから
- spec が `scale: 小` なのに、AC を確かめるのに新しい URL・ルート・列・エラーコードが要る → 書かずに止まり、「中以上にして plan の『外の約束』で決めて」と伝える。小の受け入れテストは既存の約束だけで書く
- この会話で build も plan も回していない。回していたら「新しいセッションで」と伝えて止まる
- `.claude/project.md` の「受け入れテスト」が埋まっている。`<ここに: …>` のままなら、どの項目が無いかを伝えて止まる
- `scripts/accept.sh` と `.claude/harness.env`（`accept_run` がある）がある。無ければ「先に install.sh で入れて、harness.env を埋めて」と伝えて止まる
- テストが使う DB などが応答する（環境の変数は project.md の「app の起動と URL」）

### 1. 読む（この順で）
1. spec: 目的、AC（全部）、境界、スコープ外、「変えないこと」、完了の見た目、決定ログ
2. plan.md の「外の約束」と **先に聞く** の印だけ。他の節は読まない
3. `.claude/project.md` の「受け入れテスト」「ロール」と、そこが指すテストの書き方の決まり（書き方・認可の表）
4. テストの土台とヘルパー（ロールでログインする書き方、結果を比べる語彙）
5. 外から叩く既存のテストを 2〜3 本（同じ画面・同じルートのもの。書き方を揃える。写すのは形だけ）
6. 今あるルートの一覧、テストデータの作り方（factory・seed）、文言のキー

### 2. AC ごとにテストを書く
- 置き場は `docs/accept/<タスク名>/`。ファイル名・継承する土台・使うヘルパーは project.md の「受け入れテスト」のとおり
- ケース名は `test_<AC番号>_<何が>_<どうなる>`。1 テスト 1 振る舞い。Given / When / Then をコメントで区切る
- **ロールで振る舞いが変わる AC はロールごとに書く**（データの表で列挙する）。project.md の「ロール」にある「よそ」（他の組織・他の拠点のユーザー、ゲスト、未ログインなど）で「見えない／触れない」も必ず行に入れる
- **「変えないこと」の AC も書く**（既存の振る舞いが残ること）
- Then は中身まで見る。「200 が返る」で終わらない。DB に残った値、リダイレクト先、エラーの項目名、画面に渡すデータの中身（名前が約束にあるとき）、エラーコード
- 文言の比べ方は project.md の「受け入れテスト」のとおり（多くは文言を直接比べず、キーで比べる）。spec が文言を約束しているときだけ、その文言で比べる
- 画面でしか確かめられない AC（表示順、disabled、見た目）はテストにしない。accept.md の表に「画面（ui-check）」と書き、todo の「画面の確認」の行があることを確かめる
- 使った約束は、テストの冒頭のコメントに出典ごとに書く（`// 約束: POST /reservations/{id}/refund（plan 外の約束 1）、項目名 reason（同 2）、route reservations.show（既存）`）

### 3. 回して、落ちるのを確かめる
`scripts/accept.sh <タスク名>` で回す（docs から app の中のコピー先（project.md の「受け入れテスト」）にコピーして実行し、終わったら消す）。
- **新しい振る舞いの AC**: 落ちるのが正しい。落ちた理由が「機能がまだ無い」（ルートが無い 404、列が無い、画面に渡すデータが無い、期待の値が無い）であることを 1 本ずつ確かめる。構文エラー・テストデータの作り方・import 漏れで落ちているなら、それは直してから確かめ直す
- **書いた時点で通ってしまった**: そのテストは何も確かめていない。Then を直す。直せなければ「このテストは今も通る。AC が既に満たされているか、Then が弱い」として止まる
- **「変えないこと」の AC**: 今の時点で通るのが正しい。落ちたら、既存の振る舞いの読み違いか環境の問題。直さず止まる
- 落ちた理由をテストごとに記録する（accept.md の表に書く）
- **通る側も 1 回見る**: 新しい振る舞いのテストのうち、ファイルや文書の中身を読んで判定するもの（レポート・設定・生成物を正規表現や表の読み取りで見るもの）は、AC を満たす最小の例を手で作り、それを渡すと通ることを確かめる。
  落ちるのを見るだけでは、正しい実装でも永久に通らないテスト（数の拾い方、区切りの読み方、パスの形の決め打ち）を見分けられない。例は scratchpad に作り、docs にも app にも残さない。確かめたことは accept.md の表の「今の結果」に「落ちる（最小の例では通る）」と書く

### 4. 認可を見直す
すべての AC について「誰ができて、誰ができないか」が表にあるか。「よそ」（project.md の「ロール」）の行が無い AC は、spec の AC に認可の記述が無いということ。spec に無ければ、テストで決めずに「AC に認可を足してほしい」として止まる。

### AC のことで止まるとき（1〜4 のどこでも）
「spec の AC に書いてほしい」（文書の読み方）、「AC が既に満たされているか、Then が弱い」で Then を直せないとき、「AC に認可を足してほしい」は、どれも AC のことで止まる。
止まる前に、1 件ずつ todo.md の「spec への差し戻し」に `- [ ] S-n <AC に足りないこと>（AC-XXX-n、accept-test で発覚）` で書き、docs でコミットする
（todo.md が無ければ、見出しと「spec への差し戻し」の節だけの todo.md（`# todo: <タイトル>`・`plan: （未作成）`・`## spec への差し戻し`）を作る。`(cd docs && git add plan/<タスク名>-todo.md && git commit -m "docs(<略号>): spec への差し戻し S-n")`）。
書きかけのテストはコミットしない。「次は新しいセッションで `/spec <タスク名>`（差し戻し S-n を直す）。再承認後に `/accept-test <タスク名>`」と伝える。
plan の「外の約束」が足りないだけ（「plan に次の約束を足してほしい」）は spec のことではないので、差し戻しには書かない

### 5. 保存して、止まる
`docs/accept/<タスク名>/accept.md`（`status: draft`）とテストを docs リポジトリにコミットし、要約（AC の数、テストの数、ロール別の行の数、今の結果の内訳、止まった約束）を出して、AskUserQuestion で承認を聞く:
「確定する（推奨）／直したいところがある／保留」。直したいところがあるなら Other の内容で直し、コミットしてからもう一度聞く。保留なら draft のまま止まる。
答えを待つ間もそのあとも、実装もテストの追加もしない。

    (cd docs && git add accept/<タスク名> && git commit -m "test(<略号>): 受け入れテスト draft（<n> 本）")

### 6. 「確定」と言われたら（5 の質問で「確定する」を選ばれたときも）
accept.md を `status: approved` にして docs でコミットし、「次は新しいセッション（accept-test と別のモデル）で `/build <タスク名>`。採点は別セッションの `/ac-review <タスク名>` が `scripts/accept.sh` で回す」と伝えて止まる。
伝える前に **build の入口を確かめる**: spec（中以上なら plan も）が docs でコミット済みで `(cd docs && git status --porcelain)` が空、app の `git status --porcelain` が空、app がベースブランチ（project.md の「PR の向き先」）か `feat/<タスク名>`（plan があれば `branch:` のブランチ）にいる（app の cwd で打った `git branch --show-current`（`(cd docs && ...)` の中ではない）で見る。ベースブランチなら build が入口でブランチを作る。docs は docs のベースブランチのままでよい）。足りないものは「`/build` の前に <これ>」と列挙して渡す。approved 済みの spec が未コミットなら docs でコミットしてよい。ブランチはこのスキルでは切り替えない（build がやる）。小で todo が無いのは足りないものではない（build が作る）
**以後このスキルもテストを書き換えない。** 変えてよいのは、spec か plan の約束が変わったとき（決定ログ → draft → 再承認）と、テストのミス（約束の読み違い）が採点で見つかったときだけ。どちらも accept.md を `draft` に戻し、「変更ログ」に理由を書いてから直し、再承認を求める。
人が応答できない環境（ヘッドレス）では draft までで止まる。approved にするのは人の仕事。

## 置き場と採点のコマンド（このスキルの前提。app 側に先に入れる）
- テストと記録は docs リポジトリの `docs/accept/<タスク名>/`。app の履歴には入れない
- 採点のときのコピー先（project.md の「受け入れテスト」。既定は `tests/Acceptance/`）を app の `.gitignore` に足す。普段のテストの対象（テストランナーの設定や `scripts/check.sh` が回す範囲）には入れない。受け入れテストは普段の検査にも pre-push にも入らない
- `scripts/accept.sh <タスク名>`: `docs/accept/<タスク名>/` のテストをコピー先にコピー → そのディレクトリだけテストを回す → 結果を出す → コピーを消す（`--keep` で残す）。スクリプトはハーネスのもの。何で回すかは `.claude/harness.env` の `accept_run`（README §4）
- 回すのは accept-test（3 で）と ac-review（検査で）。build は回さない

## build から守る（どこまで隠せるか）
- **設定で止める**（`headless-build.json` の deny）: `Read(docs/accept/**)` `Edit(docs/accept/**)` `Read(tests/Acceptance/**)` `Edit(tests/Acceptance/**)`、`Bash(scripts/accept.sh*)` `Bash(./scripts/accept.sh*)` `Bash(bash scripts/accept.sh*)` `Bash(sh scripts/accept.sh*)`。
  コピー先を変えたら deny のパスも変える。受け入れテストを直接回すコマンド（project.md の「受け入れテスト」）も deny に足す（README §3 の「足すもの」）
- **`Read` の deny が止めるもの**: Read・Grep・Glob（best effort）、`@` の参照、Bash の `cat` `head` `tail` `sed` `tee` とリダイレクト。サンドボックスが有効なら、Read の deny はサンドボックスの読み取り禁止にも併合され、`cp` や Python からも読めない（公式ドキュメントの記述）
- **止められないもの**: `grep -r` のようにファイル名を書かない読み方（サンドボックス無しのとき）、**git の履歴**（`git show` `git log -p` `git diff` は `.git` の中身を読むので、パスの deny では止まらない）。だから app の履歴に入れない。docs の `.git` からは `(cd docs && git show …)` で読めるので、build の docs での git 操作は todo の add / commit だけに限る（build の Red Flags）
- **それでも完全には隠せない。** 同じマシンの同じユーザーが読める場所にある限り、読もうと思えば読める。守りの本体は「build がそれを読まない」というスキルのルールと、ac-review が差分に受け入れテストと同じ形のテストが無いかを見ることにある
- **もっと隠すなら**: `docs/accept` を Claude Code を起動するディレクトリの外（例: `~/accept/<タスク名>/`）に置き、headless-build.json に `sandbox.filesystem.denyRead: ["~/accept"]` を足し、`scripts/accept.sh` はそこからコピーする。採点のときだけ app の中に現れる

## 書き方

### テスト 1 本（例。書き方は project.md の「受け入れテスト」に合わせる）
架空の会議室予約の app で、「返金の理由を保存できるのは予約した本人と管理者だけ」という AC（AC-RCR-2）を確かめる例。
言語やテストランナーは PJ によって違う。形として見るのは「約束の出典をコメントに書く」「Given / When / Then で区切る」「ロールごとの期待を表で並べる」「Then で中身まで見る」の 4 つ。

```
// 約束: POST /reservations/{id}/refund（plan 外の約束 1）、項目名 reason（同 2）、
//       route reservations.show（既存）、エラーコード forbidden（既存）

test "AC-RCR-2 返金の理由は許されたロールだけが保存できる" for each (role, expected) in roles:
    // Given: 拠点 A の予約が 1 件
    reservation = 予約を作る(拠点 = A)

    // When: 返金の理由を保存する
    response = role でログインして POST /reservations/{reservation.id}/refund { reason: "体調不良" }

    // Then: 許された人だけ保存され、他は forbidden
    結果を比べる(response, expected)
    if expected == allowed:  DB の reservations に { id: reservation.id, refund_reason: "体調不良" } がある
    else:                    DB の reservations に { id: reservation.id, refund_reason: "体調不良" } が無い

roles:
    予約した本人      → allowed
    同じ拠点の別の利用者 → forbidden
    他の拠点の管理者   → forbidden
    同じ拠点の管理者   → allowed
    ゲスト           → forbidden
    未ログイン        → ログイン画面へ
```
URL・項目名・列名は、plan の「外の約束」にあるものだけ。表の期待値は spec の AC（ロール別の可否）からそのまま写す。
DB で確かめる列名も約束（新しい列は plan の外の約束に書いてあるはず）。無ければ止まる。

### 「変えないこと」のテスト
```
test "AC-RCR-14 キャンセルは同じ会議室の他の予約に触れない":
    // Given: 同じ会議室に別の予約がある
    // When: 1 件をキャンセルする（既存ルート reservations.cancel）
    // Then: 別の予約の状態は変わらない（今の時点でも通る）
```

## 出力テンプレート（`docs/accept/<タスク名>/accept.md`）
```markdown
---
status: draft
spec: docs/spec/<タスク名>-spec.md
plan: docs/plan/<タスク名>-plan.md | なし（小）
tests: docs/accept/<タスク名>/
created: YYYY-MM-DD
updated: YYYY-MM-DD
---
# 受け入れテスト: <タイトル>

## 使った約束（出典付き）
| 約束 | 出典 |
|---|---|
| POST /reservations/{id}/refund | plan 外の約束 1 |
| 項目名 reason | plan 外の約束 2 |
| route reservations.show | 既存（ルートの一覧） |

## AC → テスト → 今の結果
| AC | テスト（ファイル / ケース名） | 種別 | ロール別 | 今の結果 | 落ちた理由 |
|---|---|---|---|---|---|
| AC-RCR-2 | RefundAcceptanceTest / AC-RCR-2 … | 新しい振る舞い | 6 行 | 落ちる | ルートが無い（404） |
```

## よくある言い訳
| 言い訳 | 反論 |
|---|---|
| URL は普通こうなるから決めて書いておく | 外の約束に無いものは決めない。build が別の URL にしたら、build のせいでなく落ちる。plan に足してもらう |
| 実装を見ればテストが早く書ける | 実装はまだ無い。あるなら build が始まっている。それでも見たら、テストが実装の写しになる |
| 200 が返ればよい | 200 は「落ちなかった」だけ。中身を見ないテストは、間違った実装も通す |
| よその行は後で足す | 「見えない／触れない」は一番落ちやすい所。無い表は承認しない |
| 通ってしまったが、実装後に意味が出る | 今通るテストは今の実装で満たされている。AC が既に満たされているか、Then が弱い。どちらも承認前に直す |
| build のテスト一覧に合わせて書く | build のテストと同じ形にする理由は無い。独立しているから審判になる |

## Red Flags
- 外の約束に無い URL・項目名・画面に渡すデータの名前・文言に頼った
- クラス名・メソッド名・内部の構造に頼った。plan の「作る順」「触るファイル」「テスト一覧」を読んだ
- 書いた時点で通るテストを「新しい振る舞い」として残した。落ちた理由を確かめずに「落ちた」と書いた
- 「よそ」（project.md の「ロール」）の行が無い認可のテスト
- 実装のコードを読んで合わせた。build が始まった後に書いた
- 承認後に書き換えた（draft に戻さずに）
- テストを app のリポジトリにコミットした。`scripts/check.sh` や普段のテストの対象に入れた
- この会話で build や plan を回していた
- AC のことで止まったのに、todo の「spec への差し戻し」に S-n を書かなかった

## 確認項目（承認を求める前に）
- すべての AC が表にあり、画面のものは「画面（ui-check）」で todo の「画面の確認」に行があるか
- 「使った約束」の表に、テストで使った URL・項目名・画面に渡すデータの名前・列名・エラーコードが全部あり、出典が spec・plan・既存のどれかか
- 新しい振る舞いのテストは全部落ち、落ちた理由が「機能がまだ無い」か。変えないことのテストは全部通るか
- 文書を読んで判定するテストは、最小の例で通ることを見たか。文書の読み方（見出し・列・コマンドのブロック・数の書き方）は全部 spec にあるか
- 認可の AC にロール別の行（project.md の「よそ」を含む）があるか
- ケース名に AC 番号があるか。Then が中身を見ているか
- docs リポジトリでコミットしたか。app には何も残していないか（`git status --porcelain` が空）
