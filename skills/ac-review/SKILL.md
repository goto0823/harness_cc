# ac-review — approved な spec と plan に照らして採点する

spec が「何を」、plan が「どう」、build が「作った」。ac-review は、できたものが spec と plan のとおりかを
**別の目で**確かめて、結果を `docs/review/<タスク名>-review-<n>.md` に書く。コードは直さない。直すのは build の fix モード。
別のセッション（別のモデルのこともある）で動かす前提。実装した会話の続きでは使わない。同じ文脈で見ると、書いた理由がそのまま正しさに見える。
レビューは人の承認を待たない。書いて、docs リポジトリにコミットして、止まる。ヘッドレスでも同じ（ヘッドレスの禁止は `.claude/headless-review.json`。B で作る）。

## 呼び方
- `/ac-review <タスク名>`
- タスク名が無いときは、`docs/plan/*-todo.md` のうち、対になる plan.md（小なら spec）が approved で、仕上げの直前まで進んでいるものを探す。
  1 件なら「これを見る」と示して確認を取り、複数なら一覧を出して止まり、0 件なら「見るものが無い」と止まる

## 進め方

### 0. 入口を確かめる（1 つでも満たさなければ止まる）
- plan.md が `status: approved`。`scale: 小` で plan が無いなら spec が `status: approved`
- todo.md で、仕上げ（P-n）より前のステップと CP がすべてチェック済み。「spec への差し戻し」に `[ ]` の行が無い（あれば `/spec <タスク名>` が先）
- app の cwd で打った `git branch --show-current`（`(cd docs && ...)` の中ではない）が plan.md の `branch:`（<branch>。小なら `feat/<タスク名>`）と一致している。ベースブランチ（project.md の「PR の向き先」）にいて app の `git status --porcelain` が空、<branch> が手元にあれば `git switch <branch>` で入ってから続ける。<branch> が無い（build が回っていない）か、別のブランチにいるなら止まる。docs のブランチは見ない（docs は docs のベースブランチのままが正しい。ship がそこから `ship/<タスク名>` を切る）
- app と docs（`(cd docs && git status --porcelain)`）の両方で `git status --porcelain` が空。未コミットのものはレビューしない。
  `docs/` は app とは別の git リポジトリ（project.md の「置き場」）で、spec・plan・todo・review はそちらに入る
- この会話で build を回していない。回していたら「新しいセッションで `/ac-review` を」と伝えて止まる
- 比べる起点を出す。ベースは project.md の「PR の向き先」（以下 `<base>`）。
  `git fetch origin <base>` してから `git merge-base origin/<base> HEAD`。fetch できないときは手元の `<base>` で代用し、その旨をレビューに書く

### 1. 読む（この順で）
1. spec: 目的、AC、境界、スコープ外、決定ログ
2. plan.md: テスト一覧、触るファイル、「外の約束」、**先に聞く** の印
3. todo.md の申し送り: 「画面の確認」（画面に関わる AC ごとに 1 行。判定は**行の頭**の状態で: 期待と違う／未確認／確認済み。ロールが並んでいても頭を見る。表の文面にある結果は使わない）、気づいたが触っていない、任意（未対応）、触るファイル外に触ったこと
4. `docs/accept/<タスク名>/accept.md` と受け入れテスト（あれば。status、AC → テストの表、「使った約束」）。
   spec の決定ログに、accept.md の承認より後の日付で AC を変えた行があり、accept.md の「変更ログ」にそれを受けた行が無ければ、参考に「accept-test を draft に戻して直す: spec の <AC> が <日付> に改訂され、受け入れテストが追っていない」と書く
5. 同じタスクの過去のレビュー（`docs/review/<タスク名>-review-*.md`）。無ければ初回
6. `git log --oneline <起点>..HEAD`（コミットの並び）
7. `git diff <起点>..HEAD`。**テストを先に**読み、次に本体を読む。テストから読むと「何を守ろうとしたか」が先に分かり、本体の読み方が決まる

### 2. 自分で確かめる
- `scripts/check.sh`（全体）と、plan の「確認」に書かれたコマンドを回す。build の申告（申し送りの「通った」）をそのまま信じない
- 落ちたら、それだけで必須の指摘にする。原因の推測は書いてよいが、直さない
- `docs/accept/<タスク名>/accept.md` が `status: approved` なら `scripts/accept.sh <タスク名>` も回す。無い・`draft` なら回さず、「検査」に「なし」か「draft」と書く
- 受け入れテストが落ちたら必須。根拠はケース名と AC。「何がおかしいか」は AC と「外の約束」の言葉で書き、テストのコードは引用しない（build はテストを読めない）
- ただし、落ちた理由が受け入れテスト側の約束の読み違い（spec・plan の「外の約束」に無い URL・項目名・画面に渡すデータの名前に頼っている、既存の振る舞いの読み違い）と疑われるときは必須にしない。
  参考に「accept-test を draft に戻して直す: <ケース名> <何を読み違えたか>」と書いて人に回す。build はテストを書き換えられないので、fix では直せない
- ファイルを書き換えて試すこと（ミューテーションテストを含む）はしない。レビューの差分と実装の差分が混ざる

### 3. 見ること（この順で。上ほど重い）
1. **AC**: すべての AC について、テスト一覧のテストがあるか／そのテストが AC の Then を本当に確かめているか／実装が AC を満たすか。
   画面に関わる AC は「画面の確認」のその AC の行でも照らす。判定は行の頭で行う。頭が「期待と違う」なら必須（根拠はそのスクショのパス）。ただし行に「（AC の疑い: …）」があれば、5 の「AC の疑い」に当たるかを先に見る。
   頭が「未確認」（ui-check が回っていない、または fix 後の「未確認: …（R<n>-<k> を直した。再確認）」）なら、必須にせず参考に「ui-check 未実施: <AC> <内容>」と書く。
   画面に関わる AC（Then に画面の表示・操作があるもの、または「完了の見た目」に関わるもの）なのに行が無ければ、参考に「ui-check 未実施: <AC>（行が無い）」と書く。ui-check は自分では回さない
2. **テストが弱められていないか。受け入れテストの写しが無いか**: 差分でアサーションの削除、skip、期待値の書き換え、AC の Then とずれた期待値。
   受け入れテストとそっくりのテスト（同じ Given / When / Then、同じロールの表、同じケース名）が差分にあれば、build が受け入れテストを読んだ印で、その回の採点は成り立たない。
   指摘にはしない（直し方が「テストを消す」しかなく、build の Red Flag とぶつかる）。5 の「採点が成り立たない」の形で止まる
3. **境界とスコープ**: spec の「絶対やらない」「スコープ外」に触れていないか。**先に聞く** の印のステップに、承認の記録（申し送り）があるか
4. **セキュリティ**: 認可（ロールごとの可否、project.md の「ロール」にある「よそ」のデータが見えない／触れない）、入力の検証、秘密情報
5. **正しさ**: 端のケース、エラーの経路、既存の振る舞いの退行
6. **設計**: 設計書（project.md の「置き場」）の型に乗っているか、層の向き、既存の部品との重複。設計書のルールに反するものは必須（根拠に設計書のファイルと節）、設計書に根拠を書けないものは任意
7. **性能**: N+1、上限の無い取得
8. **読みやすさ・簡潔さ**
9. **コミット**: 1 ステップ 1 コミットか、メッセージに P-n と AC があるか、触るファイル外の変更が申し送りに書かれているか

### 4. 指摘にする前に
- 呼び出し元・ガード・テストで否定されないか確かめる。否定されたら捨てる
- 起点の時点からあった問題は「今回の変更で入った問題」と分ける。前からあった問題は必須にしない（今回の変更で悪化させた場合を除く）。「参考」に書く
- 指摘ゼロは正しい結果。無理に作らない。作った指摘は fix の工数をそのまま奪う
- 重いものから並べる。必須が 1 つでもあれば、任意は 3 つまでに絞る
- 必須には「直し方の方向」を必ず言葉で書く（コードは書かない）。任意は書けるときだけ書く

### 5. 重さ
- **必須**: AC を満たしていない／AC に対応するテストが無い／テストが弱められた／check.sh が落ちる／認可・データ消失・秘密情報の問題／境界・スコープ外への違反／既存の振る舞いの退行／`docs/design/` に書かれたルール（層の向き、設計の型）に反する／ui-check が「期待と違う」とした AC／受け入れテストが落ちる（約束の読み違いが疑われるものを除く）。設計のものは根拠に設計書のファイルと節、ui-check のものは根拠にスクショのパス、受け入れテストのものは根拠にケース名を書く
- **任意**: 振る舞いを変えない改善（簡潔さ、名前、構造の提案）。設計書に根拠を書けない設計の指摘もここ
- **参考**: 前からあった問題、人が確かめること（ui-check の「人が確かめること」など）、既出の任意で未対応のもの、ui-check 未実施（「画面の確認」の頭が「未確認」のままの AC、または画面に関わるのに行が無い AC。ui-check が回っていないものも、fix 後の「再確認」待ちも）、accept-test を draft に戻して直すもの（受け入れテスト側の約束の読み違い）。ID を振らない
- **AC の疑い**: 実装は筋が通っているのに、AC のほうがおかしい（AC 同士が食い違う、設計書や既存の振る舞いと矛盾する、Then がそのままでは成り立たない、ui-check が「AC の疑い」を添えた行で理由に納得できる）。
  必須にしない（必須にすると build fix がコードを AC にねじ込む）。ID は `R<n>-<番号>` で振り、重さを「AC の疑い」にして、根拠（AC と、食い違う相手の AC・設計書の節・スクショのパス）と何がおかしいかを書く。直し方の方向は書かない（決めるのは spec）。
  1 件ずつ todo.md の「spec への差し戻し」に `- [ ] S-n <何がおかしいか>（AC-XXX-n、review-<n> の R<n>-<番号> で発覚）` を足し、レビューと同じコミットに入れる。
  疑いに納得できなければ、ふつうに必須にする（ui-check の疑いの理由が弱いときも）
- `result` は必須も AC の疑いも 0 件なら `pass`、どちらかが 1 件以上なら `fail`
- **採点が成り立たない**: 差分に受け入れテストの写しがある。`result: fail` にし、2 行目に「採点が成り立たない: 受け入れテストの写しがある（<ケース名>）。人が確かめる」と書く。
  AC の照合も指摘も続けない（検査の結果とこの行だけ書いて 7 へ）。指摘ではないので ID を振らない。build fix はこの行を見て直さずに止まる

### 6. 同じ指摘の扱い（ループを止めるため）
- 前の回の**必須**がまだ直っていないなら、新しい ID を振りつつ「前回 R<n-1>-<k> と同じ（未修正）」と書く。build の fix はこれを見て止まる
- 前の回の**任意**がまだ直っていないものは、指摘に出さない。「参考」に「既出の任意（未対応）: R<n-1>-<k> <見出し>」と書く。任意で build を止めない
- 前の回で直った指摘を、言い方を変えてまた出さない
- 前の回に出さなかった指摘を新しく出すときは、「今回の fix のコミットで入った」か「前回見落とした」かを書く
- 前の回の**ui-check 由来の必須**は、「画面の確認」のその AC の行の頭で判定する。頭が「期待と違う」のままなら「前回 R<n-1>-<k> と同じ（未修正）」。
  頭が「未確認」で「（R<n-1>-<k> を直した。再確認）」とあれば、fix は済んで確認だけが残っている状態。必須にも「同じ（未修正）」にもせず、参考に「ui-check 未実施: <AC>（R<n-1>-<k> の再確認待ち）」と書く。build fix はこれで止まらない

### 7. 書いて、コミットして、止まる
`docs/review/<タスク名>-review-<n>.md` に書く。`n` は既存の最大 + 1（初回は 1。`docs/review/` が無ければ作る）。
**1 行目は必ず `result: pass` か `result: fail`**（build の fix モードがこの行を読む）。採点が成り立たないときは 2 行目に「採点が成り立たない: …」（build fix はこの行でも止まる）。
書いたら、そのファイルだけを docs リポジトリで add してコミットする。コミットが無いと、build fix と次のレビューの入口（status が空）で止まる。

    (cd docs && git add review/<タスク名>-review-<n>.md && git commit -m "docs(<略号>): review-<n> <pass|fail>")

AC の疑いで todo.md に S-n を足したときは、`plan/<タスク名>-todo.md` も同じ `git add` に入れる。

docs の git 操作はこのサブシェルの形で書く。`-C docs` を付けた git は deny のパターン（`Bash(git add -A*)` など）に一致しないので使わない。
deny はサブシェルや `cd docs && ...` の中のコマンドにも効く（公式ドキュメントで確認）。

コミットしたら、結果（pass / fail、必須と任意の件数、前回との関係）の 3 行に「次」を 1 行足して出して止まる。コードもテストも触らない。「次」は result で決まる:
- `pass`: 「次は新しいセッションで `/ship <タスク名>`（docs と app の PR。ui-check の OK のスクショは project.md の「PR と課題管理」の方法で添える）」
- `fail`: 「次は新しいセッションで `/build fix <タスク名>`」。AC の疑いが 1 件でもあれば「次は新しいセッションで `/spec <タスク名>`（差し戻し S-n を直す）。そのあと案内に従って `/build fix <タスク名>` か再レビュー」にする（S-n が `[ ]` のままだと build fix は入口で止まる）
- 採点が成り立たない: 「直さずに人が確かめる。この回の結果は無効」

## 書き方

### 指摘 1 件
```
### R2-1 必須: 他の拠点の会議室 ID で絞り込むと、その会議室の名前が出る
- 根拠: AC-RLS-9 / app/reservations/list_controller.ts:148
- 何がおかしいか: `roomNameFor()` が見てよい範囲を確かめずに名前を引いているので、他の拠点の会議室名が画面に渡るデータに載る。AC-RLS-9 は「会議室名は null」を求めている
- 直し方の方向: 名前を引く前に、見てよい範囲の判定で範囲内か確かめ、範囲外なら null を返す。一覧の絞り込みの選択肢と同じ判定を使う
- 前回との関係: 新規（R1 には無い。前回見落とし）
```
根拠は AC か `ファイル:行` のどちらか、または両方。ui-check の「期待と違う」を指摘にするときは、そのスクショのパス（project.md の「スクショ」の基準で書く。git 管理外なので同じマシンでだけ開ける。開き方も project.md のとおり）を根拠に書く。ui-check は上書きせず連番を進めるので、前の回の根拠はそのまま残る。
根拠の無い指摘は書かない。直し方の方向は言葉で書き、コードは書かない。

```
### R1-2 必須: 利用者に管理メモの欄が出る
- 根拠: AC-RMM-7 / local/screenshots/reservation-memo/AC-RMM-7-member-1.png
- 何がおかしいか: ui-check で利用者のログインでも欄が描画された。AC-RMM-7 は「利用者には出ない」
- 直し方の方向: 欄の出し分けを、画面に渡すデータのロールの判定に揃える。テストは描画しないことまで確かめる
- 前回との関係: 新規
```

### 参考 1 件（ID なし）

```
- 前からあった: `ReservationCsvExporter` の列見出しがハードコードで、`ReservationFieldLabels` と二重になっている（起点より前から。今回は触っていない）
- 人が確かめること: ui-check の「人が確かめること: メモ欄の余白が狭く見える（local/screenshots/reservation-memo/AC-RMM-1-admin-1.png）」
- 既出の任意（未対応）: R1-3 `roomNameFor` の早期 return
- ui-check 未実施: AC-RMM-11「未確認: 実機で予約の履歴に管理メモが出る」（ui-check が回っていない）
```

## 出力テンプレート
この構成で書く。節を減らさない（空なら「なし」）。

```markdown
result: fail
採点が成り立たない: 受け入れテストの写しがある（<ケース名>）。人が確かめる（写しがあるときだけ 2 行目に書く。無ければこの行は書かない）
task: <タスク名>
spec: docs/spec/<タスク名>-spec.md
plan: docs/plan/<タスク名>-plan.md
base: <merge-base のハッシュ>（origin/<base>）
head: <HEAD のハッシュ>
reviewed: YYYY-MM-DD
previous: docs/review/<タスク名>-review-<n-1>.md | なし

## 検査
- scripts/check.sh: ALL GREEN | 落ちた（<どのゲート>）
- plan の確認コマンド: <コマンドと結果>
- scripts/accept.sh: ALL GREEN | 落ちた（<ケース名>） | なし（accept.md が無い） | draft（回さない）

## AC の照合
| AC | テスト（ファイル / ケース名） | Then を確かめているか | 実装 | ui-check | 判定 |
|---|---|---|---|---|---|
| AC-XXX-1 | tests/... / test_... | はい | 満たす | OK（スクショ） | OK |
| AC-XXX-2 | （無い） | - | - | - | 必須 R<n>-1 |
| AC-XXX-3 | tests/... / test_... | はい | 満たす | 期待と違う | 必須 R<n>-2 |

ui-check の列は「画面の確認」の行の頭を写す。画面に関わらない AC なら `-`、確認済みなら `OK（スクショ）`、「期待と違う」ならそのとおり、「未確認」なら `未実施`、fix 後の再確認待ちなら `未実施（再確認）`、画面に関わるのに行が無ければ `未実施（行が無い）`。

## 指摘
### R<n>-1 必須: <見出し>
- 根拠:
- 何がおかしいか:
- 直し方の方向:
- 前回との関係: 新規 | 前回 R<n-1>-<k> と同じ（未修正） | 前回見落とし | 今回の fix で入った

### R<n>-2 任意: <見出し>
- 根拠:
- 何がおかしいか:
- 直し方の方向: （書けるときだけ）
- 前回との関係: 新規 | 前回見落とし | 今回の fix で入った

## 参考（ID なし）
- 前からあった:
- 人が確かめること:
- 既出の任意（未対応）:
- ui-check 未実施:
- accept-test を draft に戻して直す:

## コミット
- 1 ステップ 1 コミット: はい | いいえ（<どのコミット>）
- メッセージの P-n と AC: すべてあり | 無いもの（<どのコミット>）
- 触るファイル外の変更: なし | あり（申し送りに記載あり / 無し: <ファイル>）

## 集計
- 必須 <k> 件、任意 <m> 件、参考 <p> 件
- 前回から: 直った <a> 件、残っている必須 <b> 件、新規 <c> 件
```

| 言い訳 | 反論 |
|---|---|
| 申し送りに「check.sh ALL GREEN」とあるから回さなくていい | 申告は材料で、根拠は自分で回した結果だけ。回さずに pass にしたレビューは何も保証しない |
| 指摘が無いと仕事をした気がしない | 指摘ゼロは正しい結果。作った指摘は fix の工数をそのまま奪う |
| ここだけ直したほうが早い | 直すのは build の fix。ここで直すと、レビューの対象と差分がずれる |
| 前からあるバグだから必須にしておこう | 今回の変更で入ったものと分ける。前からあったものは参考に書く |
| テストが通っているから AC は満たしている | テストが Then を確かめていなければ、通っても意味がない。AC → テスト → 実装の順に照らす |

## Red Flags
- `scripts/check.sh` を自分で回さずに result を書いた
- コードやテストを書き換えた（ミューテーションを含む）
- 必須が 0 件なのに `fail`、1 件以上なのに `pass`
- 根拠（AC か `ファイル:行`）の無い指摘を書いた。必須に直し方の方向が無い
- 前回直った指摘を、言い方を変えてまた出した。前回の任意を指摘に出した
- 参考に ID を振った。前からあった問題を必須にした
- 設計書に根拠の無い設計の指摘を必須にした
- ui-check の「期待と違う」を必須にしなかった。ui-check 未実施の「未確認」を参考に書かなかった。ui-check を自分で回した
- 「画面の確認」の行ではなく、申し送りの表の文面にある古い「期待と違う」で必須にした。fix 後の「未確認（再確認）」を「前回と同じ（未修正）」にした
- ロールが並んだ行を頭ではなく途中の状態で判定した。画面に関わる AC に行が無いのを見落とした
- accept.md が approved なのに `scripts/accept.sh` を回さなかった。落ちたのに必須にしなかった。読み違いが疑われるのに必須にして fix に回した。受け入れテストのコードを指摘に引用した
- 差分に受け入れテストの写しが無いかを見なかった。写しがあるのに必須の指摘にした（build は消せない）、または採点を続けた
- 実装した会話の続きでレビューした
- 1 行目が `result:` で始まっていない。`n` が既存の最大 + 1 でない
- レビューファイルを docs リポジトリにコミットせずに止まった。レビュー以外のファイルを add した

## 確認項目（書き出す前に）
- 1 行目が `result:` で、必須の件数と一致しているか。最後の「次」が result と合っているか
- すべての AC が「AC の照合」の表に 1 行ずつあるか
- 指摘すべてに ID・重さ・根拠・何がおかしいか・前回との関係があるか。必須には直し方の方向があるか
- 前回のレビューと照らして、必須の同じ／直った／新規を書き分け、未対応の任意は参考に回したか
- `scripts/check.sh` と plan の確認コマンドを自分で回し、結果を「検査」に書いたか
- 必須があるとき、任意を 3 つ以内に絞ったか
- 設計の必須に、設計書のファイルと節の根拠があるか
- 「画面の確認」の AC の行の頭で判定し、「期待と違う」を必須（根拠にスクショのパス）に、「未確認」（未実施・再確認待ち）と行の無い画面の AC を参考に書いたか
- accept.md が approved なら `scripts/accept.sh` を回して「検査」に書き、落ちたケースを必須（根拠にケース名）か「draft に戻して直す」の参考に振り分けたか。差分に受け入れテストの写しが無いか見たか（あれば 2 行目に「採点が成り立たない」を書いて止めたか）
- docs リポジトリでレビューファイルだけをコミットしたか
