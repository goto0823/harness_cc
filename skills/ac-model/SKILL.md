# ac-model — AC の本文だけから、状態のモデルを書いて回す

認可の表（`/ac-matrix`）は「誰が・何を・できるか」の 1 枚の表で、時間の流れが無い。
状態が移り変わるもの（キャンセル → 返金エラー → 再返金）や、同じ操作が 2 回・同時に来るもの（二重クリック、再送、画面とバッチ）は、表では事故が見つからない。
このスキルは、AC が言っていることだけで Quint のモデルを書き、`quint run` でランダムに何回も動かして、**AC のとおりに作っても起きてしまう事故** を探す。
事故が見つかったら、それは AC の抜け。spec の会話が人に聞いて、AC に防ぎ方（か、起きてよいこと）を書き足す。

## 入口（1 つでも満たさなければ止まる）
- spec を書いた会話ではない（この会話で spec を書いたり直したりしていない）
- `docs/spec/<タスク名>-spec.md` があり、frontmatter が `model: 要る`
- `scripts/ac-model.sh` と `scripts/ac-matrix.sh` がある。無ければ「先に install.sh で入れて」と伝えて止まる
- quint が回る（`scripts/ac-model.sh check` が「quint が無い」で止まったら、そう伝えて止まる。入れ方は README §4）

## 読んでよいもの（これだけ）
- `scripts/ac-matrix.sh ac <タスク名>` が出す、spec の「## 受け入れ条件」の節
- `scripts/ac-model.sh new <タスク名>` が作る枠（`-model.qnt` と `-model.md`）
- Quint の書き方を確かめるための、Quint の公式の文書

**読まないもの**: spec のほかの節（決定ログ・前提・スコープ外）、plan、コード、設計書、受け入れテスト、認可の表。
コードを読むと「実装はロックしているから 2 回は来ない」とモデルに書いてしまう。確かめたいのは、**AC がそれを約束しているか** のほう。

## 進め方

### 1. 枠を作って、AC を読む
    scripts/ac-model.sh new <タスク名>
    scripts/ac-matrix.sh ac <タスク名>

`new` は前のモデルがあっても作り直す。前のモデルを引き継がない。

### 2. モデルを書く（`-model.qnt`）
- **状態（`var`）**: AC に出てくるものだけ（予約の状態、返金した回数、走っている処理の数など）
- **最初の状態（`init`）**: AC の Given のいちばん最初
- **操作（`action`）**: AC の When を 1 つずつ。できる条件（その状態のときだけ押せる、など）は、AC に書いてあるものだけ
- **結果**: AC の Then のとおりに変える。AC が「成功か失敗」と書いていれば、`any { 成功, 失敗 }` で両方ありうるにする
- **終わり（`finished` と `idle`）**: これ以上なにも起きない状態を `finished` に書き、`idle` は `finished` のときだけ足踏みする。
  `idle` をいつでも動けるようにしない（行き止まりが隠れる）
- **小さく保つ**: 予約は 1 件、同時に走る処理は 2 つまで、回数は小さい数。ランダムに試すので、状態が少ないほど見落としが減る

**AC に書いていない振る舞いは、決めつけずに「どちらもありうる」にする。** ここがこのスキルの全部。
- 「同じボタンを 2 回押されたら」「処理が同時に走ったら」「外のサービスが失敗したら」「順番が入れ替わったら」を AC が言っていなければ、起きうるものとして書く（2 つ並べて、順番を決めない）
- AC に無い守り（「走っている処理があれば押せない」「2 回目は弾く」）をモデルに足さない。足すと事故が消えて見えるが、それは誰も約束していない守り
- 「どちらもありうる」にしたものは、全部 `-model.md` の「どちらもありうるにしたこと」に書く

### 3. 確かめることを書く（`-model.md` と `-model.qnt` の `val`）
- **起きてはいけないこと**: AC の Then や「変えないこと」から、どの状態でも成り立つべきこと（「返金の成功は 1 回まで」「返金済みの予約は予約済みに戻らない」）。出典に AC の番号を書く。
  AC にそう読める文が無いものは足さない（それは「未決」）
- **たどり着けること**: AC の Then に出てくる状態（「返金エラー」「返金済み」）に、本当にたどり着けるか。`finished` はいつも入れる。モデルが空回りしていないかの見張りになる
- **未決**: AC から読み取れず、モデルに書けなかったこと。無ければ「なし」

### 4. 回す
    scripts/ac-model.sh check <タスク名>

- 「形の誤り」（名前の打ち間違い・型の誤り・出典の番号）は直して、もう一度回す
- **「破れた」「たどり着かなかった」「行き止まり」は直さない。** それを見つけるのがこのスキルの仕事。モデルを変えて消すのは、AC に無い守りを足すことになる。
  ただし、モデルの書き間違い（AC の読み違いでなく、Quint の書き方の誤り。例: 成功のときに回数を足し忘れた）で起きていると分かるなら直してよい。直したら、何を直したかを出力に書く
- 「古い」が出たら、`new` からやり直す

### 5. 保存して、返す
2 つのファイルを docs リポジトリでコミットする（spec はこのスキルではコミットしない）:

    (cd docs && git add spec/<タスク名>-model.qnt spec/<タスク名>-model.md && git commit -m "docs(<略号>): 状態のモデル（<OK か NG>）" -- spec/<タスク名>-model.qnt spec/<タスク名>-model.md)

出力には、`scripts/ac-model.sh check` の出力をそのまま（要約しない）載せる。「破れた」ものには、道すじを AC の言葉で 1〜2 行に言い直したものを添える（例: 「返金エラーのときに再返金が 2 回押され、両方とも成功すると、返金が 2 回になる」）。
最後の行に「次は `/spec <タスク名>`（状態のモデルの結果を見る）」と書いて止まる。人には聞かない。

## オーケストレーターから呼ばれたとき
プロンプトが「orchestrate から:」で始まるときは、`/orchestrate` のサブエージェントとして動いている。進め方は同じ。「## 質問」は返さない。
出力の最後の「次は `/spec <タスク名>`」の行を、orchestrate が読んで spec に戻る。

## よくある言い訳
| 言い訳 | 反論 |
|---|---|
| 実装ではロックするはずだから、2 回は来ないことにする | AC に無ければ、build はロックしないかもしれない。「どちらもありうる」にして、事故が出たら AC に書いてもらう |
| 事故が出たので、出ないようにモデルを直した | それは AC に無い守りを足しただけ。事故はそのまま返す |
| 状態を細かく書いたほうが正確 | ランダムに試すので、状態が多いほど見落とす。AC が区別しているものだけにする |
| idle をいつでも動けるようにしておけば、エラーが出なくて楽 | 行き止まりが隠れる。行き止まりは AC の抜けそのもの |
| MODEL OK だから、事故は起きない | ランダムに試して見つからなかっただけ。言い方を変えない |

## Red Flags
- AC の節のほか（決定ログ、コード、plan、認可の表）を読んだ
- AC に無い守り（押せない条件、弾く処理、順番の決めつけ）をモデルに足した
- 「どちらもありうる」にしたのに、表に書かなかった
- 「破れた」「たどり着かなかった」「行き止まり」を、モデルを変えて消した（Quint の書き間違いを直したときは、何を直したか書いたか）
- `idle` を `finished` 以外でも動けるようにした
- 起きてはいけないことを、AC に無いのに足した。出典の AC がそれを言っていない
- 結果を「起きない」「安全」と書いた（「見つからなかった」と書く）
- spec や AC を書き換えた。spec を書いた会話の中で動いた
