# ui-check — 動いている画面で AC を確かめ、スクショを残す

plan は画面に関わる AC ごとに、申し送り「画面の確認」の行を「未確認」で作る（build が <内容> を具体にする）。ui-check はそれを、動いている app を Playwright で開いて消化し、同じ行を書き換える。
確かめるのは spec の AC の Then と「完了の見た目」。見つけた不具合は書くだけで直さない（直すのは build の fix）。
Playwright の MCP（`browser_navigate` / `browser_snapshot` / `browser_fill_form` / `browser_click` / `browser_take_screenshot` / `browser_console_messages` / `browser_network_requests`）を使う。
Claude in Chrome は使わない（あなたのログイン済みブラウザを触るので、結果が揺れる）。

## 前提（PJ ごとの値は `.claude/project.md` から読む）
- app は人が上げておく（project.md の「app の起動と URL」）。**ui-check は app を起動しない。** 起動のしかたや、サンドボックスの中で上げてはいけない理由は project.md に書いてある
- 開く URL は、本体なら project.md の「本体の URL」、worktree なら「worktree の URL」
- ログインの手順、ログアウト、失敗したときの見分け方と直し方、確認用のアカウントは project.md の「ログイン」
- ロールの略号（スクショの名前に使う）は project.md の「ロール」
- スクショの置き場、記録に書くパスの基準、app のセッションからの開き方は project.md の「スクショ」。置き場は git 管理外で、本体でも worktree でも同じ場所。docs にはコミットしない。
  PR に要るもの（「完了の見た目」の OK と「期待と違う」）は、`/ship` が PR を作るときに project.md の「PR と課題管理」の方法で付ける。マージ後は消してよい。
  Playwright の MCP がファイルを書けるのは、Claude Code を起動したディレクトリ（workspace root）の下だけ。置き場はその下にあり、絶対パスで指定する
- todo の書き換えは、動かしている app の docs に入れる（worktree なら worktree 側の docs。本体の docs に混ぜない）
- project.md の「ログイン」か「スクショ」が `<ここに: …>` のままなら、どの項目が無いかを伝えて止まる

## 呼び方
- `/ui-check <タスク名>`: spec の画面に関わる AC と「完了の見た目」を全部確かめる
- `/ui-check <タスク名> AC-XXX-n`: その AC だけ
- タスク名が無いときは、`docs/plan/*-todo.md` の申し送り「画面の確認」に「未確認」の行が残っているものを探す。1 件なら確認を取り、複数なら一覧を出して止まり、0 件なら止まる

## 進め方

### 0. 入口を確かめる（1 つでも満たさなければ止まる）
- spec がある（`status` は問わない。確かめるのは AC の文面）
- app が応答する。ログインの入口（project.md の「ログイン」の手順の最初の URL）を開いて、ログインの画面が出る。出なければ「app を上げて（project.md の起動のしかた）」と案内して止まる。自分で起動しない
- worktree で動かすなら、worktree の URL を使う。本体の URL と取り違えない（別の DB を見ていることが多い）。todo は worktree 側の docs に入れる（スクショの置き場は共通）
- 本体の DB にデータを作る操作（登録・保存・削除）が要る AC は、入る前に止まって聞く。worktree の DB なら聞かずに作ってよい。消す操作はどちらでもしない

### 1. 読む
1. spec の「完了の見た目」と、画面に関わる AC（Given にロールがあるものはロールごと）
2. todo.md の申し送り「画面の確認」の「未確認」の行（fix 後の「未確認: …（R<n>-<k> を直した。再確認）」も同じ扱い）
3. plan.md の「確認」に実機の項目があればそれも

### 2. 1 件ずつ確かめる（AC ごと、ロールごと）
1. **ログイン**: project.md の「ログイン」の手順どおりに入る。ログインできたと分かる URL や表示に着けば成功。着かなければ失敗。
   失敗したら project.md の「失敗したときの見分け方と直し方」に当てはめる。当てはまらなければ環境の問題として止まる。コードは直さない。ロールを変えるときはログアウトしてから
2. **操作**: AC の Given を作り、When を操作する。要素は `browser_snapshot` のアクセシビリティツリーで探す（ラベル・role）。座標で押さない
3. **確認**: Then を `browser_snapshot` の文面で確かめる。スクショは証拠で、判定は snapshot で行う
4. **スクショ**: `browser_take_screenshot` で、置き場の `<タスク名>/<AC-ID>-<ロール略号>-<連番>.png` に保存する（絶対パスで指定。ディレクトリが無ければ先に `mkdir -p`）。同じ名前のファイルが既にあれば上書きせず、連番を進める（`-1.png` があれば `-2.png`）。前の回のレビューが根拠にしたスクショを残すため。1 AC に 1〜2 枚。Then の瞬間を撮る
5. **煙の検知**: `browser_console_messages`（level: error）と `browser_network_requests` で、エラーと 4xx / 5xx を見る。あれば AC の判定に関係なく「期待と違う」に入れる
6. 結果を記録して次へ。期待と違っても止まらない（全部見てからまとめて報告する）

### 3. 見ること
- AC の Then が画面で成り立つか（文言、要素の有無、disabled、表示順）
- 「完了の見た目」がそのとおりか
- console のエラー、失敗したリクエスト、500 の画面
- ロールごとに出る・出ないが AC どおりか

### 4. 見ないこと（人に回す）
- 見た目の良し悪し、余白、配色。崩れていそうなら「人が確かめること」に書き、スクショを付ける
- AC に無い振る舞い。気づいたら「気づいたが触っていない」に書く

### 5. 止まる条件
- app が応答しない。ログインできない
- 本体 DB にデータを作る必要がある AC に入る（先に聞く）
- AC の Given を画面から作れない（seed に無いデータが要る）。「人が確かめること」に書いて次へ。全部がそうなら止まる

### 6. 書いて、コミットして、止まる
todo.md の申し送り「画面の確認」で、確かめた AC の行（plan が「未確認」で作ってある）を書き換える。AC ごとに 1 行。行は足さず、同じ行を「確認済み（<スクショのパス>）」か「期待と違う: <何が>（<スクショのパス>）」にする（書き方は下）。spec の画面に関わる AC に行が無いときだけ、行を作って結果を書く。
申し送りの表には ui-check の行を 1 つ足す（日付・範囲・OK と期待と違うの件数）。表の行に AC ごとの結果は書かない。結果の正は「画面の確認」の行だけ。
todo を docs リポジトリでコミットする（docs の git 操作はサブシェルの形。`-C docs` は使わない）。スクショはコミットしない（置き場は git 管理外）。
cwd が worktree なら `docs` は worktree 側の docs を指す。本体の docs に cd しない。

    (cd docs && git add plan/<タスク名>-todo.md && git commit -m "docs(<略号>): ui-check <範囲>")

最後に次の形で出して止まる。コードもテストも触らない。

```
## ui-check: <タスク名>
| AC | ロール | 結果 | スクショ |
|---|---|---|---|
| AC-XXX-1 | <ロール> | OK | <基準からのパス>/<タスク名>/AC-XXX-1-<略号>-1.png |
| AC-XXX-3 | <ロール> | 期待と違う: <何が> | <基準からのパス>/<タスク名>/AC-XXX-3-<略号>-1.png |
- 煙: console エラー <n> 件、4xx/5xx <m> 件（<URL>）
- 人が確かめること: <見た目など>
- 気づいたが触っていない: <内容>
- 次: 別セッション（build と別のモデル）で `/ac-review <タスク名>`。期待と違うものはそこで必須になり、`/build fix` に回る。fix 後の再確認で回したときも同じ
- PR: 「完了の見た目」の OK のスクショは、`/ship` が PR を作るときに project.md の「PR と課題管理」の方法で付ける
```

## 書き方

### ログインの操作
project.md の「ログイン」の手順を、Playwright の操作に置き換えて回す。要素はラベルか role で探し、座標では押さない。
```
browser_navigate   <ログインの入口の URL>
browser_snapshot   → 入れる項目とボタンを、ラベルか role で探す
browser_fill_form  <ログイン ID の項目> = <ID>, <パスワードの項目> = <パスワード>
browser_click      <送信のボタン>
→ project.md に書いた「ログインできたと分かる URL や表示」になればログイン済み。ならなければ失敗
```

### スクショの名前
`<AC-ID>-<ロール略号>-<連番>.png`。ロール略号は project.md の「ロール」の表。
例: `AC-RMM-11-admin-1.png`。PR に添えるときはこのパスをそのまま書く。
連番は撮るたびに進める。既にある名前には上書きしない（fix 後の再確認は `-2`、`-3`…。前の回のレビューが根拠にしたファイルを残す）。
**パスの基準は 1 つ**: 「画面の確認」の行・この報告・ac-review の根拠に書くパスは、project.md の「記録に書くパスの基準」で書く。ほかのセッション（ac-review、build fix）は project.md の開き方で開く。

### 「画面の確認」の行（todo.md の申し送り。AC ごとに 1 行、書き換えて使う）
```
- AC-RMM-7: 未確認: 利用者にメモ欄が出ない                                       ← plan が作る（build は <内容> を具体にする）
- AC-RMM-7: 確認済み（local/screenshots/<タスク名>/AC-RMM-7-member-1.png）        ← ui-check（OK）
- AC-RMM-7: 期待と違う: 利用者にも欄が出る（local/screenshots/<タスク名>/AC-RMM-7-member-1.png）  ← ui-check（NG）
- AC-RMM-7: 期待と違う: 利用者にも欄が出る（…/AC-RMM-7-member-1.png）／管理者は確認済み（…/AC-RMM-7-admin-1.png）  ← ロール 2 つ、1 つが NG
- AC-RMM-7: 未確認: 利用者にメモ欄が出ない（R1-2 を直した。再確認）              ← build fix が書く
```
同じ AC の行は常に 1 つ。ロールが複数なら 1 行の中に「／」で並べ、**行の頭は一番悪い状態**にする: 期待と違う ＞ 未確認 ＞ 確認済み。
ロールのうち 1 つでも「期待と違う」なら行の頭は「期待と違う」。1 つでも「未確認」（seed に無い、再確認待ち）が残れば「未確認」。全部 OK のときだけ「確認済み」。
ac-review は行の頭で判定するので、ここ以外（表の文面、申し送りの他の欄）に結果を書かない。

## よくある言い訳
| 言い訳 | 反論 |
|---|---|
| テストが通っているから画面も大丈夫 | テストは画面に渡すデータと描画を見るが、ビルドの生成物・ルーティング・実データは見ていない。画面は画面で見る |
| スクショだけ撮れば十分 | 判定は snapshot の文面で行う。スクショは人が後で見るための証拠 |
| ついでに直しておく | 直すのは build の fix。ここで直すと、何を確かめたのか分からなくなる |
| app を自分で上げたほうが早い | 上げ方は PJ ごとに違い、サンドボックスの中で上げると外への通信やログインが失敗することがある。人に上げてもらう |
| 本体の DB にデータを 1 件作るくらいいい | 本体 DB は seed の状態が前提。作るなら先に聞く。worktree なら聞かなくてよい |

## Red Flags
- app を自分で起動した（project.md の起動のしかたを自分で打った）
- Claude in Chrome で確かめた
- 判定をスクショの見た目だけで行い、snapshot で確かめなかった
- 本体 DB に聞かずにデータを作った。データを消した
- 期待と違う箇所をコードで直した
- スクショを project.md の置き場の `<タスク名>/` 以外（app のツリー、docs、`.playwright-mcp/`）に置いた。docs にスクショをコミットした。todo をコミットしなかった
- 既にあるスクショを上書きした。パスを project.md の基準以外（絶対パス、別の場所からの相対）で書いた
- 見た目の良し悪しを自分で判定して OK / NG にした

## 確認項目（報告の前に）
- すべての対象 AC が表に 1 行ずつあるか（ロール別なら行を分けたか）
- OK の行にスクショのパスがあり、そのファイルが置き場の `<タスク名>/` に存在するか。パスは project.md の基準で書いたか。前の回のファイルを上書きしていないか
- 期待と違う行に「何が」が書いてあるか
- console と network を各 AC で見たか
- 「画面の確認」の行を書き換えたか（足していないか。無い画面の AC だけ作ったか）。ロールを並べた行の頭が一番悪い状態か。表の行に AC ごとの結果を書いていないか。docs でコミットしたか
